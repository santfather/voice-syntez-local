# Voice_syntez --- Фаза 2: «Сам себе звукорежиссер»

## 1. Цель фазы

Добавить в Voice_syntez отдельный режим, в котором пользователь **сам
озвучивает диалог по ролям несколькими голосами**, записывая каждую роль
или отдельные реплики с микрофона, после чего приложение собирает записи
в единый готовый диалог.

Новая вкладка в основном интерфейсе:

``` text
04 · Сам себе звукорежиссер
```

Режим не заменяет существующую TTS-озвучку. Он является отдельным
production workflow:

``` text
текст диалога
→ разбор по ролям
→ назначение/запись реальных голосов
→ запись реплик
→ минимальная постобработка
→ прослушивание и перезапись отдельных реплик
→ сборка общего трека
→ экспорт
```

Основная идея: пользователь может один или вместе с несколькими людьми
самостоятельно сыграть все роли, а Voice_syntez берёт на себя разметку
диалога, организацию дублей, базовую обработку и монтаж.

------------------------------------------------------------------------

## 2. Связь с текущей архитектурой

Нужно максимально переиспользовать существующие сущности проекта:

-   текущий `dialogue_parser.py` и правила `Спикер: реплика` / `(N)`;
-   существующую разбивку диалога на реплики;
-   существующую систему пауз;
-   существующую обрезку тишины на краях;
-   существующий LUFS final pass и limiter;
-   существующую концепцию вариантов реплики;
-   существующий механизм сборки итогового файла;
-   существующие output formats.

Не нужно превращать пользовательскую запись в новый TTS engine.

Recorded dialogue --- отдельный источник аудио, который после записи
входит в общий audio assembly pipeline уже как готовый waveform.

------------------------------------------------------------------------

# 3. Пользовательский сценарий

## 3.1. Шаг 1 --- вставить диалог

В первой панели пользователь вставляет диалог в уже поддерживаемом
формате:

``` text
Анна: Ты уже приехал?
Игорь: Почти. Буду через пять минут.
Анна: Хорошо, я жду.
Игорь: Только не уходи.
```

Также сохранить поддержку slot-маркеров:

``` text
АННА(1): Ты уже приехал?
ИГОРЬ(2): Почти. Буду через пять минут.
(1) Хорошо, я жду.
(2) Только не уходи.
```

После нажатия:

``` text
Разобрать диалог
```

приложение использует существующий parser и получает:

-   список ролей;
-   список реплик;
-   порядок реплик;
-   принадлежность каждой реплики роли/слоту.

Не создавать отдельный несовместимый parser.

------------------------------------------------------------------------

# 4. Разбивка диалога по голосам

После разбора показать два представления.

## 4.1. «По порядку»

Обычный сценарий записи:

``` text
01 · Анна
Ты уже приехал?

02 · Игорь
Почти. Буду через пять минут.

03 · Анна
Хорошо, я жду.

04 · Игорь
Только не уходи.
```

Пользователь проходит диалог последовательно.

## 4.2. «По ролям»

Сгруппировать все реплики одного персонажа:

``` text
АННА · 2 реплики

01
Ты уже приехал?

03
Хорошо, я жду.
```

``` text
ИГОРЬ · 2 реплики

02
Почти. Буду через пять минут.

04
Только не уходи.
```

Это обязательный режим.

Он позволяет одному человеку сначала записать полностью роль Анны, затем
изменить голос/передать микрофон другому человеку и записать роль Игоря.

Переключатель:

``` text
Порядок записи

○ По диалогу
● По ролям
```

Изменение порядка отображения **не должно менять порядок реплик в
итоговом треке**.

------------------------------------------------------------------------

# 5. Роли и реальные голоса

В этой фазе терминология должна различать:

``` text
роль        = персонаж/слот из текста
голос       = реальный человек или голосовая настройка записи
реплика     = конкретный фрагмент текста
дубль       = конкретная записанная версия реплики
```

Для каждой роли создать карточку.

Пример:

``` text
АННА
2 реплики

Голос: Марья
Статус: 2 / 2 записано
```

Пользователь может:

-   создать новый записываемый голос;
-   выбрать ранее созданный recorded voice profile;
-   назначить один recorded voice нескольким ролям;
-   использовать разные настройки обработки для разных голосов.

------------------------------------------------------------------------

# 6. Recorded Voice Profile

Не смешивать recorded voice profile с существующим TTS voice profile без
явного архитектурного решения.

Предпочтительно создать отдельную сущность:

``` python
RecordedVoiceProfile
```

Минимальная структура:

``` python
@dataclass
class RecordedVoiceProfile:
    id: str
    name: str
    speed: float = 1.0
    pitch_semitones: float = 0.0
    denoise: bool = False
```

Допустимо расширить её позже.

Хранить настройки отдельно от raw recordings.

Изменение pitch/speed должно быть **неразрушающим**: исходный файл
записи не перезаписывается.

------------------------------------------------------------------------

# 7. Запись голоса

## 7.1. Запись из браузера

Использовать browser MediaRecorder / Web Audio API.

Пользователь нажимает:

``` text
● Записать
```

UI:

``` text
00:03.8

■ Остановить
```

После остановки:

``` text
▶ Прослушать
Перезаписать
Сохранить дубль
```

Браузер должен явно запросить разрешение на микрофон.

Если доступ запрещён, показать понятное сообщение, а не generic
`Failed to fetch`.

------------------------------------------------------------------------

# 8. Формат входной записи

Frontend может записывать в формат, реально поддерживаемый текущим
браузером, например WebM/Opus.

Backend должен привести запись к единому внутреннему формату:

``` text
WAV
mono
PCM float/int согласно текущему audio pipeline
единый sample rate
```

Не выполнять монтаж непосредственно над WebM/Opus.

Сразу после upload/decode сохранить **raw master**.

Пример структуры:

``` text
recordings/
  {project_id}/
    raw/
      r0001_take01.wav
      r0001_take02.wav
    processed/
      r0001_take01.wav
```

Raw master не изменяется.

------------------------------------------------------------------------

# 9. Запись реплик

Основная единица записи --- **реплика**.

Карточка активной реплики:

``` text
АННА · Реплика 1 из 2

«Ты уже приехал?»

[ ● Записать ]

Дубли:
✓ Дубль 1   2.1 c   ▶
  Дубль 2   2.4 c   ▶

[ Использовать выбранный дубль ]
```

После сохранения дубля автоматически перейти к следующей незаписанной
реплике выбранного порядка.

Добавить:

``` text
Автопереход к следующей реплике
```

по умолчанию включён.

------------------------------------------------------------------------

# 10. Несколько дублей

Не перезаписывать предыдущий файл при повторной записи.

Для каждой реплики хранить несколько дублей:

``` python
RecordedTake:
    id
    replica_index
    voice_profile_id
    raw_audio_path
    created_at
    duration_sec
    active
```

Пользователь может:

-   прослушать каждый дубль;
-   выбрать активный;
-   удалить неудачный дубль;
-   записать новый;
-   вернуться к старому без повторной обработки исходника.

Это должно вести себя аналогично существующей идее вариантов
синтезированной реплики, но recorded takes и TTS variants не следует
искусственно объединять в одну модель данных, если это усложняет код.

------------------------------------------------------------------------

# 11. Минимальная постобработка

Для каждого recorded voice profile добавить три пользовательские
настройки:

``` text
Скорость речи
Высота голоса
Очистка от посторонних шумов
```

------------------------------------------------------------------------

# 12. Скорость речи

UI:

``` text
Скорость
0.75 ─────●───── 1.25
          1.00×
```

Рекомендуемый диапазон первой версии:

``` text
0.75–1.25
```

Задача --- небольшая коррекция темпа, а не эффект «ускоренной кассеты».

Обязательное требование:

**скорость должна изменяться без изменения pitch.**

Не использовать обычный resample как реализацию speed control.

Нужен time-stretch.

Применять к выбранному дублю при построении processed audio либо
preview.

------------------------------------------------------------------------

# 13. Высота голоса

UI:

``` text
Высота голоса
−6 ─────●───── +6
         0 пт
```

Первая версия:

``` text
−6 … +6 semitones
```

Допускается сохранить более широкий backend limit, но UI должен
оставаться умеренным.

Pitch shift должен:

-   менять высоту голоса;
-   по возможности сохранять длительность;
-   не изменять raw master;
-   применяться независимо для каждого recorded voice profile.

Использовать уже существующий механизм pitch shift проекта, если он
подходит для recorded waveform.

Не писать вторую реализацию без необходимости.

------------------------------------------------------------------------

# 14. Очистка от посторонних шумов

UI:

``` text
Очистка записи
[✓] Убрать фоновый шум
```

Переиспользовать существующий DeepFilterNet subsystem, если он
установлен.

Проект уже умеет выполнять denoise входного reference audio; recorded
dialogue должен использовать тот же backend abstraction, а не отдельную
библиотеку.

Важно:

-   denoise выполняется над копией/raw input;
-   raw master сохраняется;
-   если DeepFilterNet не установлен, control disabled;
-   UI объясняет причину;
-   отсутствие denoiser не блокирует запись.

Не обещать удаление любых звуков.

Подпись:

``` text
Уменьшает постоянный фоновый шум и комнатный гул.
Речь других людей и громкие отдельные звуки может не удалить.
```

------------------------------------------------------------------------

# 15. Порядок постобработки

В первой версии зафиксировать единый pipeline:

``` text
raw recording
↓
decode / resample / mono
↓
denoise (если включён)
↓
edge silence trim
↓
time stretch
↓
pitch shift
↓
gain / peak safety
↓
processed take
```

После сборки всех реплик:

``` text
processed takes
↓
паузы
↓
crossfade при необходимости
↓
LUFS normalization всего трека
↓
limiter
↓
export
```

Если существующие DSP helpers требуют другой технически корректный
порядок pitch/time-stretch, агент может изменить порядок только после
проверки текущей реализации и должен описать решение.

------------------------------------------------------------------------

# 16. Неразрушающее редактирование

Это обязательное требование.

Хранить:

``` text
raw audio
+
processing settings
```

Processed audio можно кэшировать.

При изменении:

``` text
speed
pitch
denoise
```

не выполнять обработку поверх уже обработанного файла.

Всегда:

``` text
raw → current settings → processed
```

Иначе повторное изменение pitch/speed будет накапливать артефакты.

------------------------------------------------------------------------

# 17. Preview обработки

После изменения настроек голосовой карточки пользователь должен иметь
возможность нажать:

``` text
▶ Прослушать обработку
```

Для preview использовать выбранный активный дубль этого голоса.

Не нужно автоматически пересчитывать все реплики при каждом движении
slider.

Рекомендуемое поведение:

``` text
slider changed
→ UI показывает «есть несохранённые изменения»
→ пользователь нажимает «Прослушать обработку»
→ backend создаёт preview
```

При финальной сборке применить текущие параметры ко всем активным дублям
роли/голоса.

# 19. Проект записи

Запись нескольких ролей может занимать долгое время. Состояние нельзя
держать только во frontend memory.

Создать сущность проекта:

``` python
RecordingProject:
    id
    dialogue_text
    parsed_replicas
    role_assignments
    recording_order
    processing_settings
    created_at
    updated_at
```

Состояние должно переживать reload страницы.

Минимум сохранять локально на backend.

``` text
recordings/
  projects.json
```

# 21. Backend modules

Предлагаемое разделение:

``` text
backend/
  recording_store.py
  recording_pipeline.py
  recording_audio.py
```

### `recording_store.py`

CRUD:

-   projects;
-   roles;
-   takes;
-   active take;
-   processing settings.

### `recording_audio.py`

DSP:

-   decode;
-   resample;
-   mono conversion;
-   trim;
-   denoise adapter;
-   time stretch;
-   pitch shift;
-   preview.

### `recording_pipeline.py`

Оркестрация:

``` text
active takes
→ processing
→ pauses
→ assembly
→ LUFS
→ limiter
→ output
```

Не переносить туда TTS inference.

------------------------------------------------------------------------

# 23. Upload security и ограничения

Backend должен валидировать:

-   MIME/container после decode, а не доверять только filename;
-   максимальную длительность одного take;
-   максимальный размер upload;
-   существование project/replica;
-   принадлежность take нужному project;
-   допустимые значения speed/pitch;
-   безопасные генерируемые имена файлов.

Не использовать пользовательское имя роли как filesystem path.

------------------------------------------------------------------------

# 24. Микрофон и UX

До начала первой записи показать выбор входного устройства, если браузер
предоставляет несколько microphones.

Минимально:

``` text
Микрофон
[ MacBook Microphone ▼ ]

Уровень
██████░░░░
```

Во время записи показать level meter.

Добавить предупреждение при очевидно слишком тихом сигнале или clipping,
если это можно сделать лёгким анализом без новой ML-модели.

Это warning, не blocker.

------------------------------------------------------------------------

# 25. Обратный отсчёт

Добавить опциональный:

``` text
Отсчёт перед записью
0 / 1 / 2 / 3 секунды
```

Default:

``` text
1 секунда
```

После нажатия Record:

``` text
1
● запись
```

Это уменьшает обрезанные первые фонемы.

------------------------------------------------------------------------

# 26. Запись длинных реплик

Не применять TTS chunking к человеческой записи.

Одна текстовая replica = один recording slot.

Если пользователь записывает длинную реплику одним take, хранить её
целиком.

Не разбивать запись автоматически на предложения.

------------------------------------------------------------------------

# 27. Паузы

Использовать существующую настройку `pause_ms`.

В recorded workflow пауза вставляется **между активными дублями в
порядке исходного диалога**.

Перед вставкой паузы выполнить существующую edge silence trim, чтобы
реальная пауза не складывалась из:

``` text
тишина внутри записи + pause_ms
```

Сохранить небольшой safety margin вокруг речи по аналогии с текущим
pipeline.

------------------------------------------------------------------------

# 28. Crossfade

Crossfade должен быть минимальным.

Для обычных последовательных реплик с реальной паузой crossfade не
должен съедать атаку следующего голоса.

Переиспользовать существующий helper, но проверить его поведение на
human recordings.

Если `pause_ms > 0`, не применять агрессивный overlap голосов.

------------------------------------------------------------------------

# 29. LUFS и limiter

После сборки полного recorded dialogue использовать существующий
финальный:

``` text
LUFS normalization
+
limiter
```

Не нормализовать каждую роль до полностью одинакового тембра/динамики.

Допускается лёгкое выравнивание отдельных takes перед assembly, но
итоговая воспринимаемая громкость должна контролироваться final pass.

------------------------------------------------------------------------

# 30. Сохранение прогресса

После каждого события:

-   добавлен take;
-   удалён take;
-   выбран active take;
-   назначен voice;
-   изменена обработка;
-   изменён recording order;

обновлять project state.

После reload пользователь должен продолжить с того же места.

# 41. Обязательный финальный результат фазы

Ключевой результат вкладки **«Сам себе звукорежиссер»** — не набор отдельных записей и не набор файлов по ролям, а **один цельный MP3-файл с полностью собранным диалогом**.

Основной целевой сценарий этой фазы:

```text
диалог
→ 2 или 3 роли
→ запись каждой роли своим реальным голосом
→ выбор лучших дублей
→ минимальная постобработка каждого голоса
→ восстановление исходного порядка реплик
→ монтаж
→ единый MP3
```

Пример:

```text
Роль 1 → Голос A
Роль 2 → Голос B
Роль 3 → Голос C
```

Независимо от того, в каком порядке пользователь записывал материал — последовательно по диалогу или сначала все реплики одного персонажа — финальный render обязан восстановить **исходную последовательность реплик диалога**.

На выходе:

```text
output/{project_id}.mp3
```

или эквивалентный безопасный путь, принятый в текущей архитектуре проекта.

MP3 должен содержать:

- все реплики исходного диалога;
- выбранные активные дубли;
- два или три назначенных голоса;
- применённые настройки speed/pitch/denoise;
- корректные паузы между репликами;
- отсутствие лишней тишины на краях записей;
- финальную нормализацию громкости;
- limiter;
- непрерывное воспроизведение от первой до последней реплики.

Отдельные WAV/raw/processed/take-файлы являются внутренними рабочими материалами и **не считаются финальным результатом задачи**.

### Обязательный MP3 export

Даже если внутренний монтаж выполняется в WAV/PCM, последним этапом должен быть MP3 export.

Рекомендуемый порядок:

```text
raw takes
↓
processing
↓
PCM/WAV master assembly
↓
final LUFS normalization
↓
limiter
↓
MP3 encoding
↓
final dialogue.mp3
```

Не выполнять многократное MP3 → decode → MP3 преобразование между этапами.

MP3 создаётся только из финального master.

Если пользователь выбрал две роли, итоговый файл содержит два голоса.

Если пользователь выбрал три роли, итоговый файл содержит три голоса.

Архитектура может поддерживать больше ролей, но acceptance test этой фазы обязан отдельно проверить сценарии **2 voices** и **3 voices**.

# 42. Обязательные интеграционные тесты финального MP3

Следующие тесты являются **blocking**. Фаза не считается завершённой, если хотя бы один из них не выполнен или не имеет явно задокументированной причины `NOT VERIFIED`.

## Test A — цельный диалог на двух голосах

Подготовить тестовый диалог:

```text
Анна: Ты уже приехал?
Игорь: Почти.
Анна: Тогда я тебя жду.
Игорь: Хорошо, скоро буду.
```

Использовать два различных тестовых recorded voice inputs:

```text
Анна → Voice A
Игорь → Voice B
```

Проверить:

1. четыре реплики присутствуют;
2. порядок `A → B → A → B` сохранён;
3. в render используются именно выбранные active takes;
4. между репликами присутствуют заданные паузы;
5. итоговый файл существует;
6. контейнер/кодек результата — MP3;
7. файл декодируется без ошибки;
8. duration > 0;
9. файл содержит единый непрерывный диалог, а не четыре отдельных export-файла;
10. final LUFS normalization и limiter были выполнены.


- остальные реплики не меняются;

Нельзя молча пропускать реплику и создавать неполный MP3.

## Test G — MP3 decode verification

```text
channels >= 1
sample_rate > 0
duration > 0
samples > 0
```

Простого `file.exists()` недостаточно.

- render заблокирован из-за незаписанных реплик.

### Правило синхронизации знаний

README должен описывать **фактически реализованное состояние после изменений**, а не первоначальный план из этого документа.

Если в процессе реализации агент изменил endpoint, storage schema или DSP backend, документация должна отражать реальный код.

# 46. Дополнение к Definition of Done

Помимо ранее перечисленных пунктов итоговый отчёт coding-агента обязан содержать:

```text
FINAL OUTPUT
- MP3 render: PASS / FAIL
- 2 voices dialogue: PASS / FAIL
- 3 voices dialogue: PASS / FAIL
- role-grouped recording order restoration: PASS / FAIL
- MP3 decode verification: PASS / FAIL

TESTS
- full pytest: ...
- recording tests: ...
- failures: ...
- skipped: ...

KNOWLEDGE BASE
- README updated: YES / NO
- API section updated: YES / NO
- project structure updated: YES / NO
- troubleshooting updated: YES / NO
```

Фаза не должна маркироваться `DONE`, если:

- не создан единый MP3;
- не проверены два голоса;
- не проверены три голоса;
- падают обязательные тесты;
- README/библиотека знаний не обновлены.

Если реальный microphone E2E невозможно выполнить в агентской среде, допустимо:

```text
REAL MICROPHONE E2E: NOT VERIFIED
```

но автоматические integration tests на заранее подготовленных fixture-аудиофайлах всё равно обязательны.
