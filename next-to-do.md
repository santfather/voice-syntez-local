# ROADMAP: Плавность звучания, расширенные настройки, запись собственного голоса

## Контекст

Текущий пайплайн (F5-TTS-RUSSIAN + очередь по кускам + склейка) стабилен и даёт разборчивую речь с правильными ударениями. Следующий шаг — не "починить баг", а поднять субъективное качество: убрать "рубленость" на стыках кусков, дать больше ручек управления голосом и позволить пользователю озвучивать своей собственной записью, а не только готовыми референсами.

Пять тем ниже независимы друг от друга и могут делаться в любом порядке, но рекомендованный — как пронумеровано (плавность даёт наибольший субъективный эффект за наименьшие усилия).

## Фаза 1 — Убрать швы между кусками (главный источник "неплавности")

Причина неплавности почти всегда не в самой модели, а в том, что каждый кусок синтезируется независимо и не "помнит" интонацию соседнего — это уже обсуждалось применительно к озвучке целого файла, и то же самое верно для длинных реплик в диалогах, которые режутся по `MAX_REPLICA_CHARS`.

### 1.1 Резать по границам предложений, а не по числу символов
Если сейчас нарезка в `dialogue_parser.py` режет механически по лимиту символов — заменить на накопление предложений до лимита и разрез строго на точке/абзаце. Это не устраняет разрыв интонации между кусками полностью, но не даёт ему возникать **посреди мысли**, что заметно на слух сильнее, чем разрыв между двумя законченными предложениями.

### 1.2 Убрать щелчки и обрезки на границах кусков
Перед склейкой каждого куска — короткий fade-in/fade-out на самой волне (5-15 мс), до применения `cross_fade_duration` между кусками. Модель иногда оставляет короткий шум/щелчок на самом краю сгенерированного фрагмента — кроссфейд между двумя такими краями не убирает щелчок, только смешивает его с соседним звуком. Дешёвый фикс в `audio_pipeline.py`:

```python
def apply_edge_fade(wav, sr, fade_ms=10):
    fade_len = int(sr * fade_ms / 1000)
    if len(wav) < 2 * fade_len:
        return wav
    fade_in = np.linspace(0, 1, fade_len)
    fade_out = np.linspace(1, 0, fade_len)
    wav = wav.copy()
    wav[:fade_len] *= fade_in
    wav[-fade_len:] *= fade_out
    return wav
```

### 1.3 Выровнять громкость между кусками
Если у `target_rms` (параметр F5-TTS) сейчас нет явного значения — куски могут отличаться по громкости в зависимости от того, что попало в конец/начало текста. Зафиксировать единый `target_rms` для всех кусков одного голоса (а не полагаться на дефолт модели) — уберёт заметные скачки громкости на стыках, которые воспринимаются как "неровность", даже если сама интонация в порядке.

### 1.4 Проверить, не идёт ли часть операций тихо на CPU через MPS-фолбэк
`PYTORCH_ENABLE_MPS_FALLBACK=1` (уже отмечено в прошлом аудите как скрытый риск) может незаметно переключать часть вычислений на CPU **внутри одного и того же куска**, что в редких случаях даёт микро-артефакты на конкретных фрагментах, а не системно. Добавить лог-предупреждение при каждом фактическом фолбэке (PyTorch поддерживает включение подробного лога через `TORCH_SHOW_MPS_FALLBACK_WARNINGS=1` при отладке) — если такие срабатывания коррелируют с "рваными" кусками, это отдельная причина, не связанная с нарезкой текста.

**Критерий готовности:** на тестовом диалоге из 10+ реплик подряд, при прослушивании целиком, стыки между кусками не должны быть слышны как отдельное событие (щелчок/скачок громкости/провал темпа) — только естественные паузы между репликами.

## Фаза 2 — Расширенные настройки голоса в UI

Сейчас на спикера: голос (reference), скорость, cfg_strength, nfe_step. Добавить:

| Настройка | Что даёт | Реализация |
|---|---|---|
| **Громкость (gain, дБ)** | Ручная балансировка между голосами в диалоге, независимо от `target_rms` | Простое умножение waveform перед склейкой, `10 ** (gain_db / 20)` |
| **Питч-шифт (полутона)** | Творческий эффект — сделать голос выше/ниже, явно промаркирован как "экспериментально: меняет высоту, не пол голоса" | `librosa.effects.pitch_shift` постобработкой; предупреждение в UI из прошлых рекомендаций про то, что это не замена настоящему референсу |
| **Пауза до/после реплики (мс), персонально** | Сейчас пауза глобальная на весь диалог — персонажу с более "взрывным" темпом речи может требоваться короче/длиннее пауза | Расширить `pause_ms` с глобального параметра до опционального override на спикера |
| **Seed / "перегенерировать эту реплику"** | Если конкретный кусок звучит неудачно — сейчас нужно перегенерировать весь диалог заново | Кнопка на карточке результата напротив конкретной реплики → повторный вызов синтеза с новым random seed только для этого куска, вставка на то же место в готовый файл без пересборки остального |
| **Целевая громкость (target_rms)** | Из 1.3 — сделать управляемым, а не только зафиксированным дефолтом | Слайдер рядом с cfg_strength/nfe_step |

Порядок реализации: gain и персональная пауза — тривиальны, делать первыми. Питч-шифт — постобработка, не трогает сам инференс. "Перегенерировать реплику" — самая полезная фича с точки зрения удобства работы, но требует, чтобы `audio_pipeline.py` хранил метаданные о том, какой кусок какому отрезку финального файла соответствует (уже частично есть, раз склейка идёт по списку `pieces`) — расширить job-статус, чтобы каждый кусок был адресуемым по индексу задним числом.

## Фаза 3 — Запись собственного голоса прямо в приложении

Да, это в точности то же самое, что уже работает для загруженных файлов (Margo и остальные) — F5-TTS клонирует по reference audio + reference text, источник записи (микрофон в браузере или готовый файл) для модели не имеет значения. Разница только в UX: не грузить готовый файл, а записать прямо на странице.

### 3.1 Запись в браузере
- Кнопка «Записать голос» на панели голосов → `navigator.mediaDevices.getUserMedia({ audio: true })` + `MediaRecorder`, запись 10-15 сек
- Индикатор уровня сигнала в реальном времени (простой canvas на основе `AnalyserNode`) — чтобы пользователь видел, что говорит не в тишину и не клипует
- После записи — плеер для прослушивания перед сохранением, кнопка «Записать заново»

### 3.2 Убрать источник прошлой ошибки заранее, а не чинить постфактум
Инцидент с Margo случился из-за рассинхрона `ref_text` с реальной записью. Для голоса, записываемого прямо в приложении, это решается на порядок проще: **показать пользователю фиксированный текст для прочтения заранее**, а не спрашивать "что вы сказали" после записи.

```
Прочитайте вслух и нажмите «Записать»:
«Дайте пройти, пожалуйста. Я вас совсем не знаю, и мне нечего вам сказать.»
```
Так `ref_text` известен точно и заранее, автоматическая транскрипция (Whisper) становится не обязательным шагом, а опциональной подстраховкой — прогнать после записи и сверить, что распознанное совпадает с эталонным текстом (используя уже существующий порог 60% из `transcribe.py`), просто для дополнительной уверенности, а не как единственный источник текста.

Подобрать 3-5 таких эталонных фраз заранее — желательно фонетически разнообразных (разные гласные/интонационные конструкции), чтобы референс давал модели что клонировать, а не одну монотонную фразу.

### 3.3 Проверка качества записи до сохранения
Использовать уже существующую в проекте логику F0/пол-проверки (`audio_analysis.py`) плюс простую проверку на клиппинг (пики около 0 dBFS на протяжении записи) — предупреждать пользователя сразу в интерфейсе записи, а не после того, как голос уже сохранён и используется в диалогах.

**Критерий готовности:** пользователь может записать голос прямо в браузере, не выходя из приложения и не пользуясь внешним диктофоном/редактором, и сразу использовать его в диалоге наравне с загруженными файлами — с теми же настройками скорости/cfg_strength/nfe_step/громкости из Фазы 2.

## Фаза 4 — Оценить альтернативные модели синтеза (не менять движок сразу, сначала сравнить)

F5-TTS-RUSSIAN остаётся оправданным выбором — это единственная модель, файнтюненная именно под ударения русского языка. Но железо (M3 Pro, 18GB) не является узким местом ни для одной из моделей ниже — веса у всех в пределах 1-3 ГБ, разница исключительно в качестве конкретно для русского. Прежде чем вкладываться в дальнейшую доработку текущего движка, имеет смысл потратить день на A/B-сравнение на своих же диалогах.

### 4.1 XTTS v2 (Coqui) — основной кандидат на сравнение
- Из коробки поддерживает русский (один из 17 языков), zero-shot клонирование по 6-15 сек референса, вес модели ~1.8-2.6 ГБ — комфортно на 18 ГБ unified memory
- Более зрелая и широко используемая экосистема, чем у файнтюна F5 — больше готовых интеграций, проще отлаживать
- Есть готовый комьюнити-файнтюн конкретно под русский разговорный стиль (`Ftfyhh/xttsv2_banana` на Hugging Face) — обучен на живой русской речи, по описанию автора лучше держит ударения в разговорной/эмоционально окрашенной лексике, чем базовая XTTS v2. Важная оговорка от автора: файнтюн обучен преимущественно на женских голосах, из-за чего мужские голоса при клонировании через него звучат слегка феминизированно — для твоей задачи (нужны оба голоса) стоит проверить это на слух перед тем, как полагаться на этот конкретный файнтюн для мужских реплик
- Лицензия CC-BY-NC (некоммерческое использование) — для личного проекта ограничений нет

### 4.2 Chatterbox (Resemble AI) — второй кандидат, требует проверки на месте
MIT-лицензия, клонирование по ~5 сек референса, отдельная ручка "эмоция/экспрессия" (не только тембр, но и интенсивность подачи) — потенциально может дать более живую интонацию, чем F5/XTTS. По русскому языку данные противоречивые: часть источников описывает модель как преимущественно англоязычную, другие заявляют многоязычную поддержку — прежде чем тратить время на интеграцию, сначала быстро прогнать несколько тестовых фраз на русском через готовую демо/API и на слух оценить, тянет ли модель русскую фонетику вообще, до того как встраивать в проект.

### 4.3 Что не подходит и почему (чтобы не тратить время)
- **Kokoro-82M** — самая лёгкая и быстрая модель на рынке (2 ГБ CPU-инференс), но русского языка нет в списке поддерживаемых вообще, и нет клонирования голоса (только 54 пресетных голоса) — не подходит по обоим ключевым требованиям
- **Piper, Bark** — English-центричные, русский либо отсутствует, либо поддерживается настолько плохо, что вернёт те же проблемы с ударениями, что уже были у Silero

### 4.4 Альтернативный подход: TTS + voice conversion (RVC) для собственного голоса
Отдельно от выбора базовой TTS-модели — если в Фазе 3 дойдёт до записи и постоянного использования одного и того же собственного голоса, стоит рассмотреть двухэтапную схему вместо прямого zero-shot клонирования:
1. Любая TTS-модель озвучивает текст нейтральным/базовым голосом (даже без клонирования)
2. Результат прогоняется через RVC-модель (Retrieval-based Voice Conversion), заранее обученную на записях конкретно твоего голоса, которая меняет тембр на целевой

Это требует больше исходного материала для обучения (минуты записи вместо секунд) и отдельного шага обучения RVC-модели один раз, но для одного и того же голоса, используемого многократно в проекте, часто даёт более стабильный и естественный результат, чем zero-shot клонирование по короткому референсу при каждом синтезе. Рассматривать как дополнение к пайплайну, не как замену — имеет смысл только если конкретно один голос (например, свой собственный) будет использоваться часто.

**Критерий готовности:** прогнать один и тот же тестовый диалог (5-6 реплик, тот же референс Margo) через F5-TTS-RUSSIAN и XTTS v2 (+ русский файнтюн), сравнить на слух вслепую — только после этого решать, менять ли основной движок или оставить F5 и продолжать с Фазами 1-3.

## Фаза 5 — Выбор движка синтеза на голос (F5-TTS / XTTS v2)

Фаза 4 — это разовое сравнение. Эта фаза — постоянная возможность: пользователь выбирает движок отдельно **для каждого голоса** (не глобально на всё приложение), включая голоса, записанные в браузере из Фазы 3. Ориентир по умолчанию — F5-TTS для мужских голосов, XTTS v2 для женских, но выбор должен быть свободным, а не жёстко привязанным к полю `gender`: пользователь может захотеть XTTS и для мужского голоса, если тот звучит лучше на конкретной записи.

### ⚠️ Отдельно для ИИ-агента, который будет это реализовывать

**XTTS v2 в проекте сейчас не установлен и не развёрнут.** Это не переключатель параметра у существующей модели — это вторая, полностью отдельная модель, которую нужно:
1. Установить как зависимость: `pip install coqui-tts` (актуальный поддерживаемый форк, не архивный `TTS` от Mozilla/Coqui Inc.) — добавить в `requirements.txt`
2. Скачать веса модели `tts_models/multilingual/multi-dataset/xtts_v2` — при первом использовании библиотека загружает их автоматически (~1.8-2.6 ГБ) в свой кеш; явно прописать в `README.md`, что первый запуск с новым движком потребует интернет-соединения для разовой загрузки, дальше работает офлайн
3. Опционально — русский комьюнити-файнтюн `Ftfyhh/xttsv2_banana` с Hugging Face, если по итогам Фазы 4 он даст заметно лучший результат на женских голосах; веса скачиваются отдельно, схема подключения — как у любого чекпоинта Coqui TTS (файлы модели + конфиг в отдельную папку, путь указывается явно, а не через дефолтный автозагружаемый чекпоинт)
4. Проверить лицензию перед использованием: XTTS v2 — CC-BY-NC (некоммерческое использование), для личного проекта ограничений нет, но это не Apache/MIT — не копировать бездумно в предположении, что лицензия как у F5

**Ничего из этого не делать молча "по ходу" — задача явно предполагает установку нового пакета и загрузку новых весов, а не правку существующего кода.**

### 5.1 Архитектура: единый интерфейс движка

Чтобы `audio_pipeline.py` не знал, какой конкретно движок используется на каждом шаге, ввести общий интерфейс:

```python
# engines/base.py
from abc import ABC, abstractmethod

class SynthesisEngine(ABC):
    @abstractmethod
    def synthesize(self, text: str, ref_audio_path: str, ref_text: str,
                   speed: float, **engine_specific_params) -> tuple[np.ndarray, int]:
        """Возвращает (waveform, sample_rate)."""
```

```python
# engines/f5_engine.py
class F5Engine(SynthesisEngine):
    # оборачивает существующий tts_engine.py без изменения его внутренней логики
    ...
```

```python
# engines/xtts_engine.py
class XTTSEngine(SynthesisEngine):
    # новый модуль, использует coqui-tts, загружает модель один раз (singleton),
    # так же, как F5Engine — тёплая модель на весь жизненный цикл процесса
    ...
```

Параметры `cfg_strength`/`nfe_step` специфичны для F5 и не имеют смысла для XTTS (у неё свои ручки — `temperature`, `repetition_penalty`, `speed`) — в UI показывать набор параметров, релевантный выбранному движку конкретного голоса, а не один универсальный набор слайдеров на оба движка.

### 5.2 Хранение выбора движка

В `voices_store.py` / `voices.json` — новое поле у каждого голоса:
```json
{
  "id": "margo",
  "name": "Margo",
  "gender": "female",
  "engine": "xtts",
  "engine_params": { "temperature": 0.7, "repetition_penalty": 5.0 }
}
```
Поле обязательное при создании/редактировании голоса (в т.ч. записанного в браузере в Фазе 3) — дефолт можно подставлять по `gender` (жен. → xtts, муж. → f5) как подсказку в UI, но не как жёсткое ограничение выбора.

### 5.3 Маршрутизация в пайплайне

`audio_pipeline.py`, при синтезе каждого куска — смотрит `engine` у назначенного голоса и вызывает соответствующий объект `SynthesisEngine`. Очередь (`job_queue.py`) остаётся одна общая — движки не должны генерировать параллельно, тот же принцип "один воркер", что уже действует для F5.

### 5.4 Ресурсы: две тёплые модели одновременно

Если держать оба движка загруженными постоянно (а не лениво по требованию) — суммарная память примерно F5 (~1.4 ГБ) + XTTS (~1.8-2.6 ГБ) + буферы аудио-пайплайна на длинных файлах (~0.7-1 ГБ) — реалистичный пик своего процесса **5-5.2 ГБ**. Плюс Whisper при транскрипции добавляет ещё пиково (см. прошлые рекомендации по ресурсам), если транскрипция и синтез совпадут по времени.

**Рекомендованное значение: `MAX_RSS_MB = 5120` (5 ГБ), не 6.** На 18 ГБ памяти это оставляет запас под всё остальное, что реально претендует на память параллельно на этой машине — редактор с `basedpyright`/`dart-code` (индексация монорепо — легко 2-4 ГБ), браузер, через который агент тестирует UI, сама macOS. 6 ГБ технически влезает в бюджет, но уже без запаса — а именно нехватка запаса привела к прошлому инциденту с перегрузкой (там кроме питон-процесса виновниками были и расширения редактора).

**Второй, более надёжный слой защиты — проверка не только своего процесса, а системы в целом.** Текущий `ResourceGuard` (Фаза 4 из roadmap по ресурсам) смотрит на RSS собственного процесса — это не видит ситуацию, когда сама система уже под давлением из-за редактора/браузера, а питон-процесс всё ещё в пределах своего лимита. Добавить вторую, независимую проверку в `resource_guard.py`:

```python
import psutil

SYSTEM_MEM_THRESHOLD_PERCENT = int(os.environ.get("TTS_SYSTEM_MEM_THRESHOLD", "85"))

async def check_system_memory_pressure() -> bool:
    """True, если система в целом под давлением — не только этот процесс."""
    system_mem = psutil.virtual_memory()
    if system_mem.percent > SYSTEM_MEM_THRESHOLD_PERCENT:
        logger.warning(
            "Системная память %.0f%% > порога %d%% — не своя, а общая нагрузка",
            system_mem.percent, SYSTEM_MEM_THRESHOLD_PERCENT,
        )
        return True
    return False
```

Проверять это **перед стартом новой задачи** в `job_queue.py` (не в фоновом цикле `ResourceGuard`, а как предусловие перед взятием job из очереди) — если система под давлением, job остаётся в статусе `queued` с понятным сообщением ("система перегружена, ожидание") вместо того, чтобы стартовать и добавлять нагрузку поверх уже существующей. Это отдельная, дополняющая проверка к своему `MAX_RSS_MB` — обе нужны одновременно: своя не видит чужую нагрузку, системная не различает, кто именно виноват.

Учитывая, что 18 ГБ — не самая тесная конфигурация, начать с этих двух проверок (свой лимит 5 ГБ + системный порог 85%) и переходить к ленивой загрузке движков только если на практике этого всё равно окажется недостаточно.

**Критерий готовности:** пользователь на панели голосов может создать/отредактировать голос (загруженный файл или записанный в браузере), выбрать для него движок F5-TTS или XTTS v2 из выпадающего списка, увидеть релевантный набор настроек под выбранный движок, и сгенерировать диалог, где часть реплик идёт через F5, часть — через XTTS, в одном и том же итоговом аудиофайле без ручного вмешательства.

## Фаза 6 — Громкость трека, двойные паузы, качество референса, предобработка текста

По итогам собственного анализа проекта (заметки агента + текущий README) — часть Фазы 1 уже реализована (микрофейд `TTS_EDGE_FADE_MS`, `target_rms`, per-voice `gain_db`), но за скобками остались более крупные вещи, которые сильнее всего заметны на слух. Ниже — не пересмотр Фазы 1, а её продолжение с учётом того, что уже есть в коде.

### 6.1 LUFS-нормализация всего трека — сделать первым

Сейчас каждый кусок нормализуется по RMS отдельно (`target_rms`), затем куски соединяются тишиной. RMS ≠ воспринимаемая громкость, а F5 и XTTS дают звук разной плотности — отсюда ощущение "скачков" громкости именно на стыке разных движков, даже когда `target_rms` у обоих одинаковый. Добавить финальный проход по уже собранному треку: LUFS-нормализация (ITU-R BS.1770, библиотека `pyloudnorm`) + короткий лимитер на выходе, поверх существующей RMS-нормализации кусков, а не вместо неё — RMS выравнивает пики на уровне кусков, LUFS выравнивает *восприятие* громкости на уровне всего файла.

### 6.2 Убрать двойной зазор между репликами

Модель сама оставляет немного тишины на краях сгенерированного куска, а `pause_ms`/`pause_override_ms` добавляет ещё одну паузу поверх — суммарный зазор между репликами гуляет и звучит неритмично. Перед вставкой явной паузы — обрезать тишину по краям куска по энергетическому порогу (или VAD): тогда пауза между репликами будет ровно той, что задал пользователь, а не "пауза модели + пауза настройки".

### 6.3 Проверка полосы частот референса при сохранении голоса

`audio_analysis.py` сейчас проверяет пол (F0), клиппинг и совпадение с демо-клипами F5-TTS — но не спектр. Узкополосная запись (срез частот выше ~7 кГц, типично для телефонных записей или сильно сжатых mp3) даёт глухой тембр, который никакими настройками синтеза потом не лечится. Добавить простую проверку полосы (спектральный спад) в тот же модуль, рядом с уже существующей F0-проверкой, и показывать предупреждение по аналогии с бейджами `⚠ проверьте пол` / `⚠ расшифровка` — сейчас пользователь узнаёт о плохом референсе только на слух после синтеза, постфактум.

### 6.4 Опциональный денойз/дереверб перед сохранением голоса

Реверб клонируется моделью как "характеристика голоса" и в синтезе звучит как каша — это не лечится на этапе синтеза вообще, только на этапе референса. Если запись не идеальна — прогон через готовую денойз/дереверб модель (например, `DeepFilterNet` — лёгкая, есть под Python, или `noisereduce` для более простого случая) перед сохранением голоса. Это новая зависимость и дополнительная модель в памяти на время обработки одной короткой записи — не постоянно тёплая, только на разовый прогон при сохранении голоса, поэтому в общий ресурсный бюджет (Фаза 5.4) не входит.

Не апскейлить и не нормализовать тихую запись отдельно от этого — апскейл 8→24 кГц и нормализация громкости тихого файла не добавляют информации в референс, только маскируют исходную проблему.

### 6.5 Предобработка текста до модели

Сейчас текст уходит в модель как есть, кроме автоударений у F5. Добавить перед синтезом (общий шаг для всех движков, не зависит от выбора F5/XTTS):
- числа словами ("2026" → "две тысячи двадцать шестой", в зависимости от контекста — год/количество)
- расшифровка сокращений и латиницы (аббревиатуры, вкрапления английских слов)
- явный выбор стратегии нарезки текста в UI — "короткие фразы" (до ~200 знаков, стабильнее интонационно) или "абзацы" (до текущего `TTS_MAX_REPLICA_CHARS=600`, реже разрывы, но выше риск сброса интонации внутри куска). Сейчас это жёстко зашито в один лимит на всех — сделать переключателем в Панели 3, а не средой окружения

### 6.6 История вариантов вместо слепой перегенерации

`POST /api/jobs/{job_id}/replicas/{index}/regenerate` сейчас перезаписывает результат — предыдущий вариант теряется. F5 недетерминирован без фиксации seed, а слепая перегенерация "пока не понравится" без A/B на слух — по сути лотерея. Изменить так, чтобы при перегенерации реплики сохранялись 2-3 последних варианта (не один), и в интерфейсе можно было прослушать и выбрать нужный, а не только принять последний. Отдельно — начать логировать/возвращать в статусе задачи использованный seed для каждого куска, чтобы при желании можно было воспроизвести конкретно понравившийся вариант заново.

**Критерий готовности:** тестовый диалог из 8-10 реплик с обоими движками (F5 + XTTS) при сквозном прослушивании не даёт ощущения "скачка" громкости на стыке движков, паузы между репликами субъективно ровные, а у карточки заведомо узкополосного тестового референса (например, записанного через встроенный микрофон ноутбука в шумном помещении) при сохранении появляется предупреждение до, а не после синтеза.

Фаза 7 — Автоматический QA-цикл: проверка синтеза через Whisper + повторный синтез по бюджету времени

Идея: тратить лишнее время не на слепой перебор ручек, а на объективную проверку каждого куска сразу после синтеза, с автоматической перегенерацией при провале. Инфраструктура для этого в проекте уже есть — тот же Whisper и та же логика сравнения текста, что сейчас проверяет ref_text при сохранении голоса (transcribe.py, порог 60% слов), только применяется не к референсу, а к результату синтеза.

7.1 Цикл на уровне одного куска
python
# audio_pipeline.py, после синтеза каждого куска
async def synthesize_with_qa(engine, text, ref_audio, ref_text, params, qa_config):
    best = None
    deadline = time.monotonic() + qa_config.budget_sec
    for attempt in range(qa_config.max_attempts):
        wav, sr = await synthesize_chunk_with_timeout(engine, text=text, ref_audio_path=ref_audio,
                                                        ref_text=ref_text, **params)
        wer = await transcribe_and_compare(wav, sr, expected_text=text)  # тот же Whisper-воркер
        if best is None or wer < best.wer:
            best = QAAttempt(wav=wav, sr=sr, wer=wer, attempt=attempt, seed=params.get("seed"))
        if wer <= qa_config.wer_threshold:
            return best, "passed"
        if time.monotonic() > deadline:
            return best, "budget_exhausted"
        params = qa_config.nudge(params, attempt)  # новый seed, лёгкая коррекция cfg/nfe в пределах паспорта движка
    return best, "attempts_exhausted"

nudge() — не произвольный перебор, а движение в пределах уже объявленных в паспорте движка границ (см. engines/base.py — там уже есть диапазоны CFG/NFE/температуры для UI, те же границы использовать здесь): для F5 — новый seed + шаг cfg_strength в сторону стабильности, для XTTS — новый seed + шаг repetition_penalty.

7.2 Порог качества — отдельный от порога референса

Порог 60%, которым сейчас сверяется ref_text, рассчитан на то, чтобы поймать грубый рассинхрон (вставлена фраза от другого файла) — для приёмки готового результата этого недостаточно. Завести отдельный, более строгий порог (TTS_QA_WER_THRESHOLD, по умолчанию, например, 0.15 — то есть Whisper должен распознать результат почти дословно), не путать с порогом верификации референса.

7.3 Бюджет — по времени, не только по числу попыток

Ограничивать и то, и другое: TTS_QA_MAX_ATTEMPTS (например, 4) и TTS_QA_BUDGET_SEC (например, 300 — те самые 5 минут на кусок, которыми готов пожертвовать пользователь). Первое, что достигнуто — останавливает цикл. Каждая попытка — это полный синтез (TTS_CHUNK_TIMEOUT_SEC) плюс прогон через Whisper-воркер (transcribe_worker.py, уже изолирован в отдельном процессе) — общий бюджет должен превышать одну попытку синтеза с запасом в несколько раз, иначе цикл не успеет ни одной повторной попытки.

7.4 Что делать при исчерпании бюджета

Не отбрасывать все попытки молча — возвращать лучшую по WER из проверенных (даже если она не прошла порог), а не последнюю по счёту. В статусе задачи явно показывать, что кусок принят без полного прохождения проверки: например, отметка qa_status: "budget_exhausted (WER 0.32)" рядом с этим куском — так же, как уже показываются предупреждения ⚠ расшифровка/⚠ проверьте пол у голосов, тот же принцип "не скрывать, что что-то не идеально, а явно показать степень".

Здесь естественно переиспользовать хранилище вариантов из Фазы 6.6 (история попыток при ручной перегенерации реплики) — QA-попытки заполняют ту же структуру, и пользователь при желании может прослушать не только финальный выбор автоматики, но и отклонённые варианты.

7.5 Ресурсная цена — явно предупредить, не включать по умолчанию

Каждая QA-попытка — это не просто синтез, а синтез плюс запуск Whisper (тяжелее самой модели синтеза по памяти, ~1.6 ГБ, уже изолирован в своём процессе). При 3-4 попытках на кусок и диалоге из 10+ реплик это может кратно увеличить и время, и суммарную нагрузку на систему за время задачи — самое время, когда сработает системная проверка памяти из Фазы 5.4 (TTS_SYSTEM_MEM_THRESHOLD), и задача может подолгу стоять в queued, ожидая освобождения памяти между QA-попытками.

Сделать QA-цикл опциональным, не поведением по умолчанию: тумблер в Панели 3 («Строгая проверка (медленнее)», рядом с тумблером автоударений) — раз не любой диалог требует такой цены, пусть пользователь решает по задаче, а не платит временем и памятью всегда.

Критерий готовности: на тестовом куске, где известно, что синтез иногда выдаёт брак (например, специально заниженный cfg_strength для провокации нестабильности), включённый QA-цикл автоматически отбраковывает неудачную попытку, перегенерирует и в итоге либо проходит порог, либо честно возвращает лучший из вариантов с пометкой о неполном прохождении — без участия пользователя на каждом шаге.

Порядок работы
Фаза 1 (плавность) — наибольший субъективный эффект, не требует новых UI-элементов, чисто бэкенд/аудио-обработка
Фаза 2 (настройки) — делать после Фазы 1, чтобы новые слайдеры сразу применялись к уже сглаженному звуку, а не приходилось перепроверять после
Фаза 3 (запись голоса) — независимая фича, можно параллелить с Фазой 2, но не начинать до готовности Фазы 1, если запись будет использоваться для демонстрации/тестирования качества — иначе новый голос будут сравнивать со старыми "рублеными" результатами и делать неверные выводы о его собственном качестве
Фаза 4 (сравнение моделей) — можно делать параллельно с 1-3 как отдельное исследование, не блокирует остальную разработку
Фаза 5 (выбор движка на голос) — делать после Фазы 4, не вместо неё: без сравнения решение "F5 для мужских, XTTS для женских" — предположение по умолчанию, а не проверенный факт. Технически зависит от Фазы 3 (поле выбора движка должно быть в форме и загрузки, и записи голоса) и частично от Фазы 2 (набор настроек на движок логично вводить в тот же UI-блок, что и остальные слайдеры)
Фаза 6 (громкость трека, двойные паузы, качество референса, предобработка текста) — 6.1 и 6.2 делать первыми и вместе (обе правки — в одном файле, audio_pipeline.py, и чинят один и тот же на слух эффект — неровность между репликами); 6.3-6.4 — расширение уже существующей проверки при сохранении голоса, независимы от остальных фаз; 6.5-6.6 можно делать в любой момент после Фазы 2, они не требуют готовности остальных пунктов
Фаза 7 (QA-цикл) — делать после Фазы 6.6 (нужна общая структура хранения вариантов) и после того, как Фаза 6.1-6.2 стабилизируют звучание отдельного куска — иначе QA будет проверять только текстовое соответствие, а не то, что реально слышит пользователь на стыках. Не блокирует остальные фазы, но по зависимостям — самая поздняя из всех
