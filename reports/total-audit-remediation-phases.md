# План исправлений по TOTAL_AUDIT — фазы с обязательным прогоном тестов

Основа — `total_audit.md` (коммит `908168f`+, 1170 тестов, 10 находок в топе, 15 слоёв). План
переупорядочивает находки аудита не по severity, а по **зависимостям и риску смешивания
изменений**: сначала то, что делает дальнейшие фазы измеримыми и безопасными (иначе
производительность в Фазе 2 будет мериться на нестабильном фундаменте), затем сама
производительность отдельной фазой, затем остальное по убыванию риска. Внутри каждой фазы —
находки из аудита со ссылками на её нумерацию (F-A1, F-E1 и т.д.), чтобы не терять контекст
исходного документа.

## Правило для каждой фазы — без исключений

**Никакая фаза не считается завершённой без зелёного прогона тестов.** После каждой фазы:
```bash
ruff check backend/ tools/ tests/
python -m pytest
```
Оба должны быть чистыми (0 ошибок ruff сверх уже принятого технического долга — см. Фазу 0;
100% тестов зелёные) прежде чем переходить к следующей фазе. Если фаза добавляет новое
поведение — тесты на это поведение пишутся **в той же фазе**, не откладываются в Фазу 6/бэклог.
Аудит сам отмечает пробел (F-X2): гонки, отмена, падение модели тестами не покрыты — исправление
логики без соответствующего теста в этом плане не засчитывается как выполненное.

## Фаза 0 — Подготовка: базовый зелёный прогон и низкорисковые правки

Ничего из бизнес-логики. Цель — чистая стартовая точка, чтобы дальнейшие фазы не путали новые
регрессии со старым техдолгом.

- **F-C1** (Major) — `torch==2.14.0` vs `torchaudio==2.11.0`, разные минорные ряды.
  Свериться с матрицей совместимости PyTorch/torchaudio и f5-tts, запинить один релизный ряд.
- **F-X3** (Minor) — убрать мусор из корня: `dialogue.mp3`, `dialogue-2.mp3`, `total_audit.md`

**Тесты:** `pytest` должен быть зелёным до этой фазы (проверить как есть) и остаться зелёным
после — это фаза без изменения поведения, только конфигурация и файлы. Если после пина

дальше с нерешённым конфликтом версий.

## Фаза 1 — Стабильность: блокировки event loop и незащищённые вызовы

Это не про скорость сама по себе, но без этой фазы измерения производительности в Фазе 2 будут
врать: если event loop блокируется на секунды синхронным LLM-анализом, любой бенчмарк с
параллельными запросами покажет искажённые числа. Делать до Фазы 2, не после.

### 1.1 Топ-2 и топ-3 аудита — блокировки loop

- **F-A1** (Critical) — `main.py:1914`, `render_text`: `_analyze_text_chunks` вызывается
  синхронно в корутине. Обернуть: `llm_report = await asyncio.to_thread(_analyze_text_chunks, text, chunks)`.
- **F-A2** (Critical) — `main.py:1240`, `add_reference`: `get_store().add_reference(...)`
  синхронно. По аналогии с уже исправленным `create_voice` (`main.py:1071`):
  `profile = await asyncio.to_thread(get_store().add_reference, ...)`.
- **F-D2** (Major) — синхронный SQLite в async-роутерах помимо этих двух мест (десятки
  вызовов `get_store()` прямо в корутинах). Не обязательно переводить все разом — но каждый
  роутер, который аудит или профилирование в Фазе 2 отметит как заметно медленный, оборачивать
  тем же паттерном `to_thread`.

### 1.2 Топ-1 аудита — персист очереди

- **F-Q1** (Critical) / **F-D3** — `job_queue.py:285-286`, задачи только в памяти
  (`self._jobs: dict[str, Job] = {}`), таблицы `jobs` в БД нет. После рестарта/краха запись
  исчезает бесследно. Новая таблица `jobs(id, status, created_at, error, result_path, ...)`,
  запись при `submit`/на каждом переходе статуса, восстановление «осиротевших» задач при
  старте (по аналогии с уже существующим `recovery.recover_after_restart()` для реплик —
  не новая философия, а то же самое для очереди).

### 1.3 Топ-4 аудита — MPS fallback

- **F-E1** (Critical) — `xtts_engine.py:188-198`, `except Exception` трактует **любое**
  исключение как сбой MPS и тихо уводит модель на CPU (замедление в 10-30×), при этом
  `release_torch_memory()` перед перезагрузкой не вызывается — старый Metal-пул не
  освобождается, двойной расход unified memory. Сузить фильтр до `"mps" in str(exc).lower()`,
  перед `_load_model("cpu")` вызвать `release_torch_memory()`.

### 1.4 Дополнительно — ffmpeg без таймаута

- Фактически топ-3 аудита: `audio_analysis.py:102-108`, `subprocess.run([...ffmpeg...])` без
  `timeout=`. Битый/зацикленный вход вешает воркер навсегда. Добавить `timeout=` и обработку
  `subprocess.TimeoutExpired` с понятной ошибкой задачи, а не зависанием.

**Тесты Фазы 1:**
```bash
python -m pytest tests/ -k "job_queue or worker or mps or render_text or add_reference"
python -m pytest   # полный прогон
ruff check backend/
```
Обязательно добавить (закрывает F-X2 применительно к этой фазе):
- тест на восстановление задачи из таблицы `jobs` после имитации рестарта (по образцу уже
  существующих `test_worker_recovery.py`/`test_recovery.py`)
- тест на MPS-fallback: заглушка движка кидает **не-MPS** исключение → `raise`, не тихий
  переход на CPU; кидает MPS-исключение → переход на CPU **и** вызов `release_torch_memory()`
  (можно проверить моком/счётчиком вызовов)
- тест на `ffmpeg` таймаут: замокать `subprocess.run` так, чтобы кидал `TimeoutExpired`,
  проверить, что задача получает понятную ошибку, а не висит

**Критерий перехода к Фазе 2:** все три названных выше теста зелёные, полный `pytest` зелёный,
`render_text`/`add_reference` не блокируют `/api/status` во время выполнения (можно проверить
вручную: запустить долгий LLM-анализ и параллельно дёрнуть `/api/status` — должен ответить
мгновенно, не дожидаясь).

## Фаза 2 — Производительность (основная фаза этого плана)

Всё, что аудит отметил в §5 «Узкие места» и §4.3/4.4 как источник лишнего CPU/времени, не
считая MPS-специфики (она в Фазе 3, там своя категория рисков).

### 2.1 Квадратичный парсер диалога — самое дешёвое и самое заметное

- **F-T2** (Major) — `dialogue_parser.py:307-318`, накопление текста реплики через повторную
  конкатенацию строк в цикле — O(n²) по длине реплики. На 100 репликах деградирует раньше,
  чем успевает начаться синтез.
```python
# Было — квадратично
def append(chunk: str, line_number: int) -> None:
    chunk = chunk.strip()
    if not chunk:
        return
    segment = current or start(slot_key(config.DEFAULT_SLOT), {}, line_number)
    if segment.text:
        segment.text = f"{segment.text} {chunk}"
        return
    ...

# Стало — линейно: копить части в список, join один раз при завершении сегмента
def append(chunk: str, line_number: int) -> None:
    chunk = chunk.strip()
    if not chunk:
        return
    segment = current or start(slot_key(config.DEFAULT_SLOT), {}, line_number)
    segment.text_parts.append(chunk)  # список вместо строки
    ...

# при завершении сегмента (там, где раньше читали segment.text):
finalized_text = " ".join(segment.text_parts)
```
Плюс лимит числа реплик в диалоге (аудит упоминает это отдельно в §6 как желаемую защиту от
гигантского ввода) — оба пункта в одном файле, делать вместе.

### 2.2 Словарь произношения — перекомпиляция на каждый проход

- **F-T1** (Major) — `coverage_predicate` даёт O(слов×правил), нормализация и QA перечитывают
  текст заново (2-3 прохода на реплику). На 100 репликах — заметная просадка CPU задолго до
  узкого места MPS.
  Ввести кеш скомпилированного словаря, инвалидируемый по версии (например, по количеству
  записей + хешу последнего изменения `pronunciation_entries`, а не по времени — словарь
  меняется редко, версия дешевле пересчитывать при каждом чтении, чем таймстемп сверять с TTL):
```python
_compiled_cache: dict[int, CompiledDictionary] = {}

def get_compiled_dictionary() -> CompiledDictionary:
    version = get_store().pronunciation_dictionary_version()  # дешёвый COUNT/hash-запрос
    if version not in _compiled_cache:
        _compiled_cache.clear()  # держим только последнюю версию, не накапливаем
        _compiled_cache[version] = _compile_dictionary(get_store().list_pronunciation_entries())
    return _compiled_cache[version]
```
  Плюс свести нормализацию и QA-проверку к одному проходу по тексту реплики вместо
  раздельных 2-3 (там, где сейчас пайплайн вызывается несколько раз подряд на один и тот же
  текст — объединить в единый вызов с одним результатом, переиспользуемым дальше по цепочке).

### 2.3 NFC-нормализация — маленький фикс, но входит в тот же текстовый пайплайн

- **F-T3** (Major, но дёшево — S) — декомпозированная «ё» (`е` + U+0308, отдельный
  комбинирующий диакритик) не распознаётся как «ё» нигде в пайплайне, включая уже
  реализованный модуль восстановления «ё». `unicodedata.normalize("NFC", text)` на входе
  текста, до всех остальных стадий — иначе часть ранее сделанной работы над буквой «ё» просто
  не сработает на файлах, вставленных из источников с другой юникод-нормализацией (некоторые
  macOS-приложения отдают текст в NFD).

**Тесты Фазы 2 — с измерением, не только с зелёным флагом:**
```bash
python -m pytest tests/ -k "dialogue_parser or pronunciation or normalization"
python -m pytest   # полный прогон
```
Обязательно (это ядро «особого внимания производительности» из задачи):
- **Бенчмарк до/после**, не просто «тест прошёл»: прогнать `dialogue_parser.parse_dialogue`
  на синтетическом диалоге из 100+ реплик, замерить время до правки 2.1 (зафиксировать
  текущее число из живого прогона, не из оценки) и после — ожидаемый результат: время растёт
  линейно от числа реплик, не квадратично (проверить на 50/100/200 реплик — если фикс верный,
  отношение времени должно расти пропорционально числу реплик, а не его квадрату)
- Тест на кеш словаря: подтвердить, что повторный вызов `get_compiled_dictionary()` без
  изменений в БД не перекомпилирует (мокнуть/посчитать вызовы `_compile_dictionary`), а после
  добавления новой записи в словарь — перекомпилирует и подхватывает новое правило
- Тест на NFC: реплика с декомпозированной «ё» на входе после нормализации проходит через
  модуль восстановления «ё» так же, как обычная композированная «ё»
- Отдельно зафиксировать числа в `short_utterance_report.md`-подобном формате (или добавить в
  существующий `tools/loadtest.py`) — раз в проекте уже есть культура «не просто починили, а
  измерили и записали», эта правка не должна быть исключением

**Критерий перехода к Фазе 3:** бенчмарк показывает линейный, не квадратичный рост на разборе
диалога; кеш словаря подтверждён тестом на количество перекомпиляций; полный `pytest` зелёный.

## Фаза 3 — MPS-safety (память, OOM, thermal) — отдельно от общей производительности

Аудит выделяет macOS/MPS-специфику в отдельный раздел (§11) неслучайно — часть этих правок
нельзя проверить юнит-тестами вообще (реальная память Metal, троттлинг), поэтому фаза требует
не только `pytest`, но и ручных шагов с живой моделью. Не смешивать с Фазой 2: там правки
были чисто CPU/Python и полностью проверяемы тестами, здесь — часть проверки принципиально
ручная.

### 3.1 Сброс кеша между репликами (не только при выгрузке)

- **F-E2** (Major) — `base.py:77-92`, `release_torch_memory()` (`gc.collect()` →
  `empty_cache()`, порядок верный) вызывается только при выгрузке модели, не между репликами
  длинного диалога. `driver_allocated_memory()` может расти от реплики к реплике — «главный
  симптом утечки» по формулировке аудита (§11.2). Добавить лёгкий `gc.collect(); torch.mps.empty_cache()` в конце обработки каждой реплики (не такой полный, как при
  выгрузке — не убирать саму модель, только промежуточные тензоры) и логировать дельту
  `driver_allocated_memory()` до/после каждого синтеза.

### 3.2 MPS-предохранители

- **F-E3** (Major) — не выставлены `PYTORCH_MPS_HIGH_WATERMARK_RATIO` (аудит рекомендует
  `1.0`, не `0.0`), `PYTORCH_MPS_LOW_WATERMARK_RATIO` (`0.9`), `torch.mps.set_per_process_memory_fraction()`. Без явного потолка модель может занять всю unified
  memory — на 8-16 ГБ это прямой путь к kernel/GPU panic (§11.4), не только к деградации.
  Задать в `configure_torch` при старте, значения — по матрице §11.3 аудита.
- **F-E4** (Major) — загрузка весов без таймаута и проверки целостности (`model_manager`/
  `downloader`, huggingface_hub). Сверять sha256/размер после скачивания, таймаут на HTTP.

### 3.3 OOM с понятной диагностикой

- Раздел §11.4 аудита: нет обработки `RuntimeError: MPS backend out of memory` с выводом трёх
  чисел (MPS allocated / other allocations / max allowed), нет механизма понижения модели при
  нехватке памяти (например, выгрузка `xtts-banana`, самого тяжёлого движка, первым). Добавить
  перехват такого `RuntimeError`, логирование трёх чисел, и хотя бы простейшую стратегию
  понижения — выгрузить неиспользуемые тёплые движки перед повторной попыткой (переиспользовать
  уже существующий механизм выгрузки по простою, просто вызвать его принудительно вне
  расписания).

### 3.4 Thermal — только видимость, не автоматика

- §11.5 аудита: нет логирования времени синтеза каждой реплики → тепловая деградация невидима,
  на 10+ минутах аудио рост времени реплик спишут на «модель тормозит», хотя причина другая.
  Минимально достаточно: логировать `time.monotonic()` до/после каждого синтеза реплики (уже
  собирается ETA — переиспользовать ту же точку измерения, не заводить новую). Полноценный
  кулдаун между репликами — не делать в этой фазе, это уже компромисс скорости ради температуры,
  такое решение должно приниматься осознанно после того, как видно по логам, что троттлинг
  реально происходит, а не заранее вслепую.
- `tools/doctor.py` — добавить проверку `sysctl -n kern.memorystatus_vm_pressure_level` (без
  `sudo`, в отличие от `powermetrics`) как минимальный сигнал, что система под давлением.

### 3.5 Дёшево и рядом

- §11.7 аудита — `torch.set_num_threads()` для CPU-фолбэка не задан: на CPU-откате PyTorch
  может занять все ядра, конкурируя с MPS-потоком. Задать явно (переиспользовать уже
  существующее значение `TTS_THREAD_LIMIT` из общей конфигурации потоков, не заводить новую
  переменную).

**Тесты Фазы 3:**
```bash
python -m pytest tests/ -k "engine or resource_guard or mps"
python -m pytest
```
Плюс обязательные **ручные** шаги (задокументировать результат, как это уже сделано в
`creash_final_report.md` для изоляции воркера — формат «команда → что увидено»):
- Прогнать диалог на 15-20 реплик с тёплой F5 подряд, снять `torch.mps.driver_allocated_memory()`
  до и после каждой реплики из нового лога — подтвердить, что после правки 3.1 число не растёт
  монотонно от реплики к реплике (небольшие колебания — норма, устойчивый рост — сигнал, что
  фикс не сработал)
- `tools/doctor.py` показывает новую проверку давления памяти
- Искусственно смоделировать нехватку памяти (например, временно занизить
  `set_per_process_memory_fraction` до заведомо малого значения) и убедиться, что OOM ловится
  с логом трёх чисел, а не роняет воркер бесконтрольно

**Критерий перехода к Фазе 4:** ручные шаги задокументированы с реальными числами (не «должно
работать», а «увидено X МБ до, Y МБ после»), `pytest` зелёный.

## Фаза 4 — Хранилище и очередь: TTL, целостность, отказоустойчивость

Находки, которые не про производительность и не про MPS, но напрямую про потерю данных
пользователя — вторая по важности категория после Фазы 1.

- **F-S1** (Major) — take'ы копятся без TTL/лимита (`db/repositories/takes.py`). TTL или лимит
  числа take'ов на реплику.
- **F-S2** (Major) — каскадное удаление реплик (`ON DELETE CASCADE`) чистит строки БД, но не
  файлы `output/projects/{id}/` — сироты на диске. Уборка файлов по удалённым id в одной
  транзакции с записью в БД (не после, отдельным шагом — если процесс упадёт между ними,
  снова получаем рассинхрон).
- **F-Q2** (Major) — отмена задачи, стоящей в очереди (ещё не начатой), игнорируется
  (`job_queue.py:730-735`). Проверять статус `cancelled` перед фактическим запуском.
- **F-Q3** (Major) — кооперативная отмена ждёт до 600с, `_wait_for_memory()` без таймаута —
  очередь может встать навсегда. Таймаут ожидания памяти + прерываемая отмена.
- **F-Q4** (Major) — `PriorityQueue()` без `maxsize`, preview может голодать под потоком
  рендера. `maxsize` + резерв слота под preview-запросы отдельно от рендера.
- **§6 «Заполнен диск»** (Major) — нет проверки свободного места перед рендером.
  `shutil.disk_usage` + ранний отказ с понятным текстом, не попытка записи с последующим
  крахом на середине.
