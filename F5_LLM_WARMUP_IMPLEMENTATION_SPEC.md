# Voice_syntez --- LLM Warm-up Prefix для коротких реплик

## 1. Цель задачи

Добавить в пайплайн озвучки диалогов механизм **скрытого текстового
прогрева (warm-up prefix)** для коротких реплик.

Проблема: каждая реплика/кусок синтезируется независимо, поэтому
TTS-модель не имеет контекста предыдущей речи. На очень коротких фразах
это может приводить к неестественному старту, нестабильной интонации и
ухудшению первых слов.

Решение: перед короткой целевой репликой автоматически генерировать
небольшой текстовый контекст. В TTS передавать:

``` text
<warm-up prefix> <target phrase>
```

При этом в итоговом диалоге должен остаться **только звук целевой
реплики**. Звук, соответствующий warm-up prefix, должен быть удалён до
дальнейшей сборки трека.

------------------------------------------------------------------------

## 2. Важное ограничение

Warm-up --- это **внутренний технический контекст**, а не часть
пользовательского текста.

Нельзя:

-   изменять исходный `dialogue_text`;
-   показывать warm-up как дополнительную реплику;
-   включать warm-up в итоговый аудиофайл;
-   учитывать warm-up как ожидаемый текст при QA/WER-проверке целевой
    реплики;
-   сохранять warm-up вместо исходного текста в метаданных реплики;
-   пропускать warm-up через логику определения спикеров как отдельную
    реплику.

Исходная реплика остаётся единственным пользовательским текстом.

------------------------------------------------------------------------

## 3. Когда использовать warm-up

Функция применяется **только к коротким репликам**.

Добавить конфигурацию:

``` text
TTS_WARMUP_ENABLED=true
TTS_WARMUP_MAX_CHARS=80
TTS_WARMUP_MAX_WORDS=12
TTS_WARMUP_MAX_PREFIX_CHARS=180
```

Рекомендуемая логика:

``` python
use_warmup = (
    TTS_WARMUP_ENABLED
    and len(target_text.strip()) <= TTS_WARMUP_MAX_CHARS
    and word_count(target_text) <= TTS_WARMUP_MAX_WORDS
)
```

Порог должен быть централизован в `backend/config.py`, а не захардкожен
в пайплайне.

Warm-up не нужен для пустого текста, служебных фрагментов и реплик,
которые после preprocessing перестали быть короткими.

------------------------------------------------------------------------

## 4. Где разместить новую логику

Не добавлять LLM-логику в `backend/text_preprocess.py`.

`text_preprocess.py` должен оставаться детерминированным этапом
нормализации текста: числа, сокращения, латиница и прочие существующие
преобразования.

Создать отдельный модуль:

``` text
backend/warmup_context.py
```

Ответственность модуля:

1.  определить, нужен ли warm-up;
2.  собрать контекст для LLM;
3.  запросить warm-up prefix;
4.  провалидировать результат;
5.  вернуть структуру с исходной целевой фразой и синтетическим
    префиксом;
6.  безопасно сделать fallback на обычный синтез при любой ошибке LLM.

Пример интерфейса:

``` python
@dataclass
class WarmupContext:
    target_text: str
    prefix_text: str | None
    enabled: bool
    reason: str | None = None

    @property
    def synthesis_text(self) -> str:
        if not self.prefix_text:
            return self.target_text
        return f"{self.prefix_text.rstrip()} {self.target_text.lstrip()}"
```

------------------------------------------------------------------------

## 5. Что должна делать LLM

LLM получает:

-   текущую короткую реплику;
-   предыдущую реплику диалога, если она есть;
-   следующую реплику, если она есть;
-   имя/идентификатор текущего спикера;
-   при наличии --- имя предыдущего и следующего спикера.

LLM **не должна переписывать target phrase**.

Она генерирует только короткий естественный текст, который
непосредственно предшествует целевой фразе и помогает TTS войти в
речевой режим.

### Требования к prefix

Prefix должен:

-   быть на том же языке, что и target phrase;
-   быть естественной разговорной речью;
-   быть примерно 1--2 предложениями;
-   не превышать `TTS_WARMUP_MAX_PREFIX_CHARS`;
-   не содержать имён спикеров, markdown, XML/SSML и технических
    инструкций;
-   не повторять целевую реплику;
-   не добавлять цитаты вокруг target phrase;
-   по возможности подводить к эмоциональной/смысловой функции целевой
    реплики;
-   заканчиваться нормальной пунктуацией.

Пример:

``` text
Предыдущая реплика:
— Ты точно сможешь приехать завтра?

Target:
— Да, конечно.

Допустимый prefix:
Я понимаю, почему ты спрашиваешь, и могу ответить совершенно определённо.
```

В TTS уходит:

``` text
Я понимаю, почему ты спрашиваешь, и могу ответить совершенно определённо. Да, конечно.
```

В финальном аудио остаётся:

``` text
Да, конечно.
```

## 6. Prompt для LLM

Использовать структурированный запрос. LLM должна возвращать **только
prefix**, без объяснений.

Пример system prompt:

``` text
Ты создаёшь скрытый речевой контекст для TTS.

Тебе дана короткая целевая реплика диалога и соседний контекст.
Сгенерируй 1–2 естественных предложения, которые могли бы непосредственно
предшествовать целевой реплике и помогли бы речевой модели начать говорить
с естественной интонацией.

Правила:
- не изменяй и не повторяй TARGET;
- верни только PREFIX;
- используй язык TARGET;
- не добавляй имя спикера;
- не используй markdown, кавычки, XML или SSML;
- PREFIX не должен быть обязательной частью смысла диалога;
- максимум {max_prefix_chars} символов.
```

User payload:

``` text
PREVIOUS:
{previous_text_or_none}

TARGET:
{target_text}

NEXT:
{next_text_or_none}
```

Параметры вызова должны быть консервативными: низкая температура и
небольшой `max_tokens`.

------------------------------------------------------------------------

## 7. Порядок обработки текста

Для короткой реплики пайплайн должен быть таким:

``` text
original target
    ↓
существующий text_preprocess
    ↓
F5: существующий accentizer
XTTS: без accentizer
    ↓
определение необходимости warm-up
    ↓
LLM warm-up generation
    ↓
отдельная подготовка prefix к конкретному движку
    ↓
prefix + target
    ↓
TTS synthesis
    ↓
поиск точной границы target в audio
    ↓
удаление warm-up audio
    ↓
edge trim / RMS / gain / pitch / прочая существующая постобработка
    ↓
QA только по target
    ↓
сборка диалога
```

Важно: не допустить двойной обработки `target_text`.

------------------------------------------------------------------------

## 8. Ударения и preprocessing

У проекта разные правила для F5 и XTTS.

### F5

Warm-up prefix должен пройти тот же релевантный preprocessing, что и
целевой текст, включая расстановку ударений, если `auto_accent=true`.

### XTTS

Не добавлять RUAccent-разметку. Знак `+` для XTTS является обычным
токеном и не должен попадать в текст.

Следовательно, подготовка prefix должна использовать существующие engine
capabilities, а не проверку вида:

``` python
if engine_id == "f5":
```

Предпочтительно:

``` python
if engine.capabilities.supports_accents:
    ...
```

или уже существующий эквивалент из паспорта движка.

------------------------------------------------------------------------

## 9. Ключевая задача: отделение target audio

Нельзя резать warm-up по приблизительной длительности или пропорции
числа символов.

Плохой вариант:

``` python
cut_sec = total_duration * len(prefix) / len(full_text)
```

Так делать нельзя: скорость речи неравномерна, а граница может попасть
внутрь первого слова target.

### Требуемый подход

После синтеза `prefix + target` определить временную границу начала
`target`.

Предпочтительный механизм:

1.  выполнить alignment/forced alignment с полным синтезированным
    текстом;
2.  получить timestamp первого слова target;
3.  обрезать всё до этой точки;
4.  оставить небольшой configurable pre-roll, например 20--60 мс, если
    это необходимо для сохранения атаки первого фонема;
5.  после этого использовать существующую обработку краёв.

Добавить abstraction:

``` python
@dataclass
class TargetBoundary:
    start_sec: float
    confidence: float | None = None
    method: str = "alignment"
```

И функцию уровня:

``` python
locate_target_start(
    audio,
    sample_rate,
    full_text,
    target_text,
) -> TargetBoundary | None
```

### Fail-safe

Если границу target нельзя определить с достаточной уверенностью:

**не использовать потенциально повреждённый warm-up результат.**

Вместо этого повторно синтезировать `target_text` обычным способом без
warm-up.

Это обязательное поведение.

------------------------------------------------------------------------

## 10. Не использовать обычный Whisper WER как единственный резак

Существующий Whisper-процесс полезен для проверки содержимого, но
распознавание всей фразы само по себе не гарантирует достаточно точную
границу первого фонема target.

Если используемая ASR/alignment-библиотека умеет отдавать word
timestamps с приемлемой точностью, её можно переиспользовать. Иначе
добавить отдельный lightweight forced-alignment слой.

Выбор конкретной библиотеки агент должен сделать после проверки уже
установленных зависимостей и API используемой версии Whisper.

Не добавлять тяжёлую модель без необходимости.

## 11. Изменения в `audio_pipeline.py`

Интеграцию выполнять на уровне синтеза отдельной реплики/куска, а не
после сборки всего диалога.

Псевдокод:

``` python
target = prepare_target_text(replica.text, engine, auto_accent)

warmup = await warmup_service.build(
    target_text=target,
    previous_text=...,
    next_text=...,
    speaker=...,
)

if warmup.enabled:
    prefix = prepare_prefix_text(warmup.prefix_text, engine, auto_accent)
    full_text = f"{prefix} {target}"

    audio, sr = await synthesize(full_text, ...)

    boundary = locate_target_start(
        audio=audio,
        sample_rate=sr,
        full_text=full_text,
        target_text=target,
    )

    if boundary is not None:
        audio = audio[int(boundary.start_sec * sr):]
    else:
        audio, sr = await synthesize(target, ...)
else:
    audio, sr = await synthesize(target, ...)
```

После этого должен выполняться существующий постпроцессинг.

Не дублировать код синтеза: вынести общий вызов движка в локальный
helper, если иначе появятся две почти одинаковые ветки.

------------------------------------------------------------------------

## 12. Контекст соседних реплик

Чтобы LLM могла понять функцию короткой фразы, `audio_pipeline` должен
иметь доступ как минимум к:

``` python
previous_replica_text
current_replica_text
next_replica_text
```

Не передавать LLM весь диалог. Это:

-   увеличивает latency;
-   увеличивает расход токенов;
-   повышает вероятность лишней генерации;
-   не требуется для локальной интонации.

Если соседней реплики нет, передавать `None`.

Контекст нужен **только для генерации prefix**. Соседние реплики не
должны добавляться в TTS input.

------------------------------------------------------------------------

## 13. Совместимость с F5 и XTTS

Не считать, что одинаковый warm-up обязательно улучшит оба движка.

Добавить capability/configuration layer:

``` text
TTS_WARMUP_ENGINES=f5,xtts,xtts-banana
```

или эквивалентную настройку в паспорте движка.

Архитектура должна позволять отключить warm-up для конкретного engine
без изменения `audio_pipeline.py`.

На первом этапе провести A/B-тест отдельно для:

-   F5-TTS Russian;
-   XTTS v2;
-   XTTS banana.

Если на каком-либо движке качество ухудшается, исключить его из default
allowlist.

------------------------------------------------------------------------

## 14. QA/WER

Это критическая часть изменения.

Существующий QA должен проверять:

``` text
trimmed_target_audio ↔ target_text
```

Он **не должен** сравнивать:

``` text
full_warmup_audio ↔ prefix + target
```

и не должен ожидать prefix после того, как prefix уже удалён.

Правильный порядок:

``` text
warm-up synthesis
→ target boundary
→ trim
→ QA(target_audio, target_text)
```

При QA retry новый seed/параметры движка могут породить другую
длительность prefix, поэтому boundary необходимо вычислять заново **для
каждой попытки**.

Нельзя переиспользовать timestamp предыдущей попытки.

------------------------------------------------------------------------

## 15. Regenerate и варианты реплик

Warm-up должен работать и при:

``` text
POST /api/jobs/{job_id}/replicas/{index}/regenerate
```

Каждая новая генерация:

1.  получает тот же target;
2.  может заново получить warm-up prefix либо использовать сохранённый
    prefix --- выбрать один детерминированный подход;
3.  синтезирует полный временный audio;
4.  удаляет prefix;
5.  сохраняет в variant **только target audio**.

Рекомендуется сохранять с вариантом техническую метаинформацию:

``` json
{
  "warmup_used": true,
  "warmup_prefix": "...",
  "warmup_boundary_sec": 1.84,
  "warmup_fallback": false
}
```

Эти данные нужны для диагностики, но не обязаны показываться в обычном
UI.

------------------------------------------------------------------------

## 16. Ошибки LLM не должны ломать TTS

Warm-up --- улучшение качества, а не обязательная зависимость.

При любом из событий:

-   LLM недоступна;
-   timeout;
-   пустой ответ;
-   ответ длиннее лимита;
-   некорректный ответ;
-   alignment не найден;
-   confidence ниже порога;
-   исключение warm-up subsystem;

пайплайн должен залогировать причину и продолжить обычным:

``` text
synthesize(target_text)
```

Задача не должна переходить в `error` только из-за warm-up.

------------------------------------------------------------------------

## 17. Кэширование

Чтобы не вызывать LLM повторно без необходимости, добавить небольшой
cache.

Ключ:

``` text
hash(
    engine_id,
    previous_text,
    target_text,
    next_text,
    prompt_version
)
```

Значение:

``` text
prefix_text
```

Кэш может быть in-memory LRU.

Добавить `prompt_version`, чтобы изменение prompt автоматически
инвалидировало старые результаты.

------------------------------------------------------------------------

## 18. Latency

Warm-up добавляет два потенциально дорогих этапа:

``` text
LLM generation
alignment
```

Поэтому:

-   LLM-вызов должен иметь короткий timeout;
-   генерация должна быть ограничена малым количеством токенов;
-   использовать warm-up только для коротких реплик;
-   кэшировать prefix;
-   не запускать warm-up для длинных кусков;
-   не загружать тяжёлую alignment-модель на каждую реплику;
-   если alignment требует модели, держать её singleton/lazy-loaded
    аналогично существующим движкам.

## 24. Порядок реализации для coding-агента

### Шаг 1 --- изучить текущий код

Перед изменениями прочитать:

``` text
backend/config.py
backend/audio_pipeline.py
backend/dialogue_parser.py
backend/text_preprocess.py
backend/accentizer.py
backend/transcribe.py
backend/engines/base.py
backend/engines/registry.py
backend/engines/f5_engine.py
backend/engines/xtts_engine.py
backend/job_queue.py
backend/main.py
tests/conftest.py
tests/test_audio_pipeline.py
tests/test_job_queue.py
tests/test_api.py
tools/loadtest.py
```

Не начинать реализацию до понимания реального порядка preprocessing →
accentizer → engine → postprocessing → QA.

### Шаг 2 --- зафиксировать baseline

Запустить:

``` bash
source venv/bin/activate
python -m pytest
```

Все существующие тесты должны проходить до изменений.

### Шаг 3 --- реализовать `warmup_context.py`

Сначала без интеграции в audio pipeline.

Сделать:

-   config;
-   eligibility;
-   LLM adapter;
-   validation;
-   timeout;
-   cache;
-   fallback;
-   unit tests.

### Шаг 4 --- реализовать boundary/alignment abstraction

Не связывать его напрямую с LLM.

Интерфейс должен принимать:

``` text
audio + sr + full_text + target_text
```

и возвращать начало target либо `None`.

Покрыть unit-тестами.

### Шаг 5 --- интегрировать в одну реплику

Изменить внутреннюю функцию синтеза одного куска.

Не менять сборку трека целиком.

### Шаг 6 --- интегрировать QA

Убедиться, что QA работает уже после trim и сравнивает результат только
с target.

### Шаг 7 --- regenerate/variants

Проверить весь существующий цикл вариантов.

### Шаг 8 --- API/UI

Добавить per-job toggle без изменения формата диалога.

### Шаг 9 --- README

Документировать:

-   назначение;
-   ограничения;
-   env vars;
-   fallback;
-   поддерживаемые engines;
-   влияние на latency.

### Шаг 10 --- полный regression

Запустить:

``` bash
python -m pytest
```

Затем живой A/B-тест.

## 25. Acceptance criteria

Изменение считается готовым только если выполняются все условия:

-   [ ] короткая реплика может синтезироваться с LLM-generated prefix;
-   [ ] исходный текст пользователя не изменяется;
-   [ ] prefix никогда не слышен в итоговом файле;
-   [ ] начало первого слова target не обрезается;
-   [ ] при сомнительной границе выполняется clean fallback без warm-up;
-   [ ] ошибка LLM не роняет job;
-   [ ] QA проверяет только target;
-   [ ] QA retry заново определяет boundary;
-   [ ] regenerate работает;
-   [ ] variants содержат только target audio;
-   [ ] F5 и XTTS получают корректный для своего движка preprocessing;
-   [ ] feature можно отключить глобально;
-   [ ] feature можно отключить для конкретного engine;
-   [ ] feature можно отключить для конкретной job;
-   [ ] существующие тесты не сломаны;
-   [ ] новые тесты проходят без загрузки реальных моделей;
-   [ ] README обновлён;
-   [ ] проведён A/B-тест на реальном F5 до включения функции по
    умолчанию.

------------------------------------------------------------------------

## 26. Что агенту нельзя делать

Необходимо сохранить текущую архитектуру проекта.

Не делать следующее:

-   не переписывать `audio_pipeline.py` целиком;
-   не менять публичный интерфейс `SynthesisEngine` без необходимости;
-   не добавлять warm-up как реальную реплику parser-а;
-   не смешивать LLM generation с `text_preprocess.py`;
-   не использовать оценочную обрезку аудио по длине строки;
-   не принимать повреждённый trim при неуверенном alignment;
-   не заставлять job падать из-за warm-up;
-   не включать RUAccent для XTTS;
-   не поднимать реальные TTS-модели в pytest;
-   не добавлять крупную ML-зависимость до проверки, нельзя ли решить
    alignment уже имеющимися средствами;
-   не менять существующую семантику QA, вариантов и regenerate для
    реплик без warm-up.

------------------------------------------------------------------------

## 27. Definition of Done для агента

В конце работы агент должен предоставить:

1.  список изменённых/добавленных файлов;
2.  краткое описание архитектурного решения;
3.  название и способ вызова LLM backend;
4.  описание выбранного alignment-механизма;
5.  описание fallback;
6.  список новых env vars;
7.  результат полного `pytest`;
8.  результат A/B smoke test на F5;
9.  известные ограничения;
10. подтверждение, что существующие API остаются backward-compatible.

Если какой-либо пункт не реализован, агент должен явно указать это как
незавершённую часть, а не скрывать за успешным статусом.
