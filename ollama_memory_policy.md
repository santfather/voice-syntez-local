# Ollama, TTS и Whisper на одной машине: политика памяти

Документ — источник истины по совместному использованию тяжёлых ML-задач в проекте
VOICE_SYNTEZ: локальной LLM (Ollama), синтеза (F5/XTTS) и распознавания (Whisper QA).
Написан по реальным замерам на целевой машине (MacBook Pro M3, 18 GB unified memory),
а не по общим соображениям.

Дата: 2026-09-17. Код: `backend/llm/memory_policy.py`, `backend/llm/runner.py`,
`backend/memory_monitor.py` (для синтеза).

## 1. Почему политика вообще нужна

LLM, TTS и Whisper в этом проекте делят **одну и ту же** физическую память: на Apple
Silicon нет отдельной VRAM, и «модель в Metal» — это те же страницы, что и у системы.
Когда памяти не хватает, macOS уходит в компрессию и swap: зависает не бенчмарк, а вся
машина, включая сессию, из которой он запущен. Плюс замеры становятся недостоверными —
модель выглядит медленной, хотя она просто ждала страниц.

Отсюда два правила:

1. **Тяжёлая задача одна за раз.** LLM-инференс, синтез F5/XTTS и Whisper не
   выполняются одновременно (лёгкие HTTP-ручки приложения — можно).
2. **Свободная память не «до нуля».** Под macOS и UI держится резерв: цель 4 GB,
   жёсткий минимум 3.5 GB (значения проверены замерами, см. §4).

## 2. Состояния и пороги

Пороги задаются конфигом и переменными окружения (стартовые значения из постановки):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_MEMORY_NORMAL_MAX_PERCENT` | 70 | выше — режим роста: задача разрешена, событие логируется |
| `LLM_MEMORY_WARNING_PERCENT` | 75 | WARNING: новую тяжёлую задачу не запускать |
| `LLM_MEMORY_CRITICAL_PERCENT` | 82 | CRITICAL: остановить запуск новых задач, выгрузить неиспользуемые модели |
| `LLM_MEMORY_HARD_STOP_PERCENT` | 88 | HARD STOP: ничего не начинать; идущую работу безопасно прервать |
| `LLM_MEMORY_RESERVE_GB` | 4.0 | целевой резерв под macOS/UI |
| `LLM_MEMORY_RESERVE_MIN_GB` | 3.5 | жёсткий минимум свободной памяти |

Дополнительно проверяются:

- **влезает ли модель с резервом**: `свободно >= размер модели + reserve_min`; если
  модель не влезает вовсе — CRITICAL;
- **давление памяти macOS** (`kern.memorystatus_vm_pressure_level`): жёлтое — не ниже
  WARNING, красное — HARD STOP. Давление имеет приоритет над процентом: система может
  экономить память при формально низком проценте.

Различие «не начинать» и «прервать» принципиально (`must_abort_running`):

- процентный CRITICAL запрещает **новую** работу, но идущий benchmark не убивает —
  иначе замер посередине модели даёт обрезанные данные вместо результата;
- работу прерывают только жёсткие факты: HARD STOP или исчерпанный абсолютный резерв.

## 3. Тяжёлая конкуренция: gate

`HeavyGate` (`backend/llm/memory_policy.py`) пропускает одновременно не более одной
тяжёлой задачи. Внутри процесса это честная блокировка; занятость чужих процессов
(очередь синтеза) подключается через `external_busy`, который передаёт вызывающий.
Занятый ресурс — это отказ с причиной в отчёте, а не «подождать и попробовать»:
конкурентный инференс ломает и замеры, и машину.

## 4. Реальные замеры (M3, 18 GB, 2026-09-17)

Замеры сняты во время smoke/full прогонов benchmark'а; `available` — оценка
`psutil.virtual_memory().available`, `ollama ps` — фактический размер загруженной
модели вместе с KV-кэшем под контекст 8192.

| Модель | файл, GiB | загружено (`ollama ps`) | пик занятой памяти | минимум свободной | pressure |
|---|---|---|---|---|---|
| `qwen3:4b-instruct-2507-q4_K_M` | 2.33 | ~3.6 GiB | 79.3 % | не замерялся в том прогоне | green |
| `gemma3:4b` | 3.11 | ~3.6 GiB | 80.6 % | не замерялся в том прогоне | green |
| `qwen3:4b-instruct-2507-q8_0` | 3.99 | ~5.2 GiB | 82.7 % | не замерялся в том прогоне | green |
| `qwen3:8b` | 4.87 | 6.17 GiB | 86.0 % | 2.51 GB | green |

«Не замерялся в том прогоне» — честная формулировка: поле `min_available_gb`
появилось в runner'е уже после первых трёх прогонов, а пересчитать его из сырых
ответов нельзя (замер снимается во время работы модели). Пик занятой памяти и
события pressure есть по всем четырём моделям; для `qwen3:8b` — полный набор.

Отдельный замер `qwen3:8b` (загрузка → первый ответ → выгрузка):

```text
до загрузки:     60.7 % занято, 7.07 GB свободно
после загрузки:  85.7 % занято, 2.58 GB свободно, pressure green
после выгрузки:  56.8 % занято, 7.77 GB свободно (память возвращается полностью)
```

Выводы из замеров:

1. **Файл модели — не её след в памяти.** Фактический след больше размера файла:
   `qwen3:8b` — 4.87 GiB файл против 6.17 GiB загруженной модели (+27 %) из-за
   KV-кэша на 8192 токена и накладных расходов. Проверять «влезает ли модель» по
   размеру из `/api/tags` — недостаточно; в Task 2 стоит добавить коэффициент
   (≈1.3) или калибровочную загрузку.
2. **`/api/ps` пуст раньше, чем память вернулась.** После выгрузки страницы
   возвращаются системе за секунды, но не мгновенно: без ожидания следующая модель
   блокируется остатками предыдущей. Runner ждёт возврата (до 60 c, с логом).
3. **Восстановление полное.** После выгрузки свободная память возвращается к исходной
   (`7.07 → 2.58 → 7.77 GB`), утечек нет.
4. **Пик 85.7 % при зелёном давлении** — это рабочий режим для 8B-модели на 18 GB,
   а не авария: swap не начался, компрессия не включилась. Именно поэтому пороги —
   «стартовые»: их проверяют замерами на конкретной машине.
5. Резерв 3.5 GB на этой машине запрещает запуск `qwen3:4b-q8_0` и `qwen3:8b` при
   типичных 6.7--7.6 GB свободной памяти (пользовательские приложения занимают
   ~10 GB). Для benchmark'а этих двух моделей резерв был явно снижен до 2.0 GB
   (решение пользователя), замеры пиков записаны в отчёт. Для production-режима
   Analyzer резерв остаётся 3.5--4 GB: там модели работают рядом с синтезом.
6. **Повторный прогон `qwen3:8b` дал те же метрики качества** (`issue_f1` 0.1928,
   `critical_error_rate` 0.3422) при пике 86.0 % против 84.7 % в первом прогоне:
   ответы модели детерминированы (`temperature=0`, `seed=0`), а разброс пика памяти
   — это уже свойство машины, а не модели.

## 5. Порядок принятия решения

```text
1. Собрать: system_percent, available_gb, memory_pressure.
2. Спросить gate: не идёт ли другая тяжёлая задача (LLM/TTS/Whisper).
3. Проверить давление macOS: red → HARD STOP, yellow → не ниже WARNING.
4. Проверить абсолютный резерв: < reserve_min → CRITICAL, < reserve → WARNING.
5. Проверить, влезает ли модель вместе с reserve_min.
6. Проверить процент: 88/82/75/70 → HARD STOP/CRITICAL/WARNING/рост.
7. Запускать только в NORMAL; причину решения сохранить в отчёт.
```

## 6. Что делать при отказе

Отказ политики — это нормальный результат, а не сбой: он попадает в отчёт с причиной
(`status: blocked|hard_stop`, `reason`), а прогон получает код возврата 1, чтобы
автоматика не приняла частичный результат за полный. Молчаливого продолжения в
условиях нехватки памяти нет; молчаливого «нет данных — значит можно» тоже: если
датчики не прочитались, политика не применяется, но флаг `sensor_ok: false` остаётся
в отчёте.

## 7. Связь с синтезом

`backend/memory_monitor.py` решает ту же задачу для очереди синтеза (NORMAL/WARNING/
CRITICAL по системной памяти, RSS бэкенда и RSS воркеров). Общий принцип один:
тяжёлая работа не начинается, когда машина уже на пределе, а отказ виден в
`/api/status`. Отличие LLM-политики — абсолютный резерв, приоритет macOS pressure и
явное разделение «не начинать» / «прервать».
