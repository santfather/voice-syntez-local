# TTS-дашборд: озвучка русских диалогов

Локальное веб-приложение: вставляете диалог в формате `Спикер: реплика`, назначаете каждому
спикеру голос (клонируется из вашего reference-аудио) и параметры речи — на выходе один готовый
аудиофайл со всем диалогом. Второй режим — **«Сплошной текст»**: загрузка `.txt`/`.md` и озвучка
одним голосом, без спикеров и маркеров.

Работает полностью локально; интернет нужен только для первой загрузки весов (F5-TTS качает
их сам, остальные модели — вкладка **`05` «Модели»**, см. «Менеджер моделей»).

## Движки синтеза

Движок выбирается **отдельно для каждого голоса** — не глобально на приложение. Один и тот же
текст может звучать разными моделями, и в одном диалоге допустимо смешивать голоса на разных
движках: файл всё равно соберётся один.

| Движок | Что это | Ударения | Ручки |
|---|---|---|---|
| `f5` — **F5-TTS Russian** | [F5-TTS](https://github.com/SWivid/F5-TTS) + веса [Misha24-10/F5-TTS_RUSSIAN](https://huggingface.co/Misha24-10/F5-TTS_RUSSIAN) (`F5TTS_v1_Base_accent_tune` — обучен с полной разметкой ударений). Движок по умолчанию | да | CFG strength, NFE steps |
| `xtts` — **XTTS v2 (базовая)** | [Coqui XTTS v2](https://huggingface.co/coqui/XTTS-v2), многоязычная модель, клонирование по 6–15 с референса. Веса ~1.9 ГБ | нет | Температура, штраф за повторы |
| `xtts-banana` — **XTTS v2 + русский файнтюн** | [Ftfyhh/xttsv2_banana](https://huggingface.co/Ftfyhh/xttsv2_banana) — разговорный русский файнтюн базовой XTTS. Обучен преимущественно на женских голосах, поэтому мужские референсы на нём звучат менее предсказуемо | нет | Температура, штраф за повторы |

F5-TTS берёт из записи только первый фрагмент (до ~12 с), XTTS — до 30 с.
Расшифровка референсов — Whisper (`openai/whisper-large-v3-turbo`), он же проверяет,
что введённый текст действительно соответствует записи.

Длинный текст XTTS режет на предложения сам, потому что у модели есть лимит на длину
входной фразы (для русского — 182 символа, у нас реплики бывают до 600). За это отвечает
spacy: coqui-tts его вызывает, но в зависимостях не объявляет, поэтому он прописан в
`requirements.txt` отдельно — без него любая XTTS-реплика длиннее 182 символов падала
с `ImportError: enable_text_splitting=True requires Spacy`.

Ударения расставляет [RUAccent](https://github.com/Den4ikAI/ruaccent) **только для F5**:
токенизатор XTTS кодирует знак `+` как отдельный токен, поэтому размеченный текст для него —
мусор. Для XTTS-голосов тумблер «автоударения» ни на что не влияет, текст уходит как есть.

> **Лицензии.** Код F5-TTS — MIT, но его веса (включая русский файнтюн `Misha24-10/F5-TTS_RUSSIAN`)
> распространяются под **CC-BY-NC-4.0**: обучены на датасете Emilia и некоммерческие.
> Веса XTTS v2 — под **Coqui Public Model License (CPML)**, тоже некоммерческой. То есть
> проект целиком годится для личного и исследовательского использования, но не для
> коммерческого продукта без отдельного согласования.

## Требования

- macOS на Apple Silicon (M1/M2/M3), ≥ 16 ГБ ОЗУ. Поднятые движки остаются в памяти до конца
  работы процесса: F5-TTS ~1.4 ГБ, XTTS базовая ~1.9 ГБ, banana-файнтюн ~5.2 ГБ — то есть
  набор «F5 + обе XTTS» занимает порядка 9 ГБ. Если памяти мало, используйте один движок.
- Python 3.11 (`brew install python@3.11`)
- ffmpeg (`brew install ffmpeg`) — нужен для MP3 и m4a/mp3-референсов

## Установка

```bash
python3.11 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Веса моделей скачиваются отдельно и по желанию: F5-TTS — сам при первом старте, остальные —
кнопкой «Скачать» во вкладке `05` «Модели» (см. «Менеджер моделей»). Если веса уже лежат на
диске, приложение работает офлайн и вкладка нужна только для диагностики.

### Очистка референса (необязательно)

Если референсы пишутся в шумном помещении, можно поставить DeepFilterNet — тогда при
сохранении голоса появится тумблер «очистить запись от шума и реверба»:

```bash
source venv/bin/activate
pip install --no-deps -r requirements-denoise.txt
```

`--no-deps` здесь обязателен: пакет тянет `numpy<2.0` и `packaging<24.0` и откатил бы уже
проверенные версии из `requirements.txt`. Без установленного пакета тумблер просто погашен,
всё остальное работает как раньше.

### Веса F5-TTS

Веса скачиваются автоматически при первом старте (~1.4 ГБ) в `./models`:

```
models/
├── F5TTS_v1_Base/vocab.txt
└── F5TTS_v1_Base_accent_tune/model_last_inference.safetensors
```

Чтобы поставить их вручную (или заранее, до запуска) — но проще нажать «Скачать» во вкладке
`05` «Модели» (см. «Менеджер моделей»):

```bash
source venv/bin/activate
python -c "
from huggingface_hub import hf_hub_download
for f in ['F5TTS_v1_Base_accent_tune/model_last_inference.safetensors', 'F5TTS_v1_Base/vocab.txt']:
    print(hf_hub_download('Misha24-10/F5-TTS_RUSSIAN', f, local_dir='models'))
"
```

Ещё один файл докачается при первом запуске — вокодер Vocos (`charactr/vocos-mel-24khz`, ~54 МБ)
в стандартный кэш Hugging Face. RUAccent также скачивает свои модели при первом использовании.
Whisper для расшифровки референса (`openai/whisper-large-v3-turbo`, ~1.6 ГБ) докачивается при
первом распознавании — то есть при первом сохранении голоса или нажатии «распознать».

### Веса XTTS v2

Веса XTTS **внутри задачи не подкачиваются**: подкачивать ~1.9 ГБ посреди синтеза нельзя,
поэтому без файлов движок не поднимется вовсе (в логе будет понятная ошибка с ожидаемым путём).
Поставить их заранее можно двумя способами — кнопкой «Скачать» во вкладке `05` «Модели»
(см. «Менеджер моделей») или вручную, командой из блока ниже.

```
models/
├── xtts_v2/                              # coqui/XTTS-v2 — базовая модель
│   ├── config.json
│   ├── model.pth                         # ~1.9 ГБ
│   ├── dvae.pth
│   ├── mel_stats.pth
│   ├── speakers_xtts.pth
│   └── vocab.json
└── xtts_v2_banana/model_banana/v2.0.2/   # Ftfyhh/xttsv2_banana — русский файнтюн
    ├── config.json
    ├── model.pth                         # ~5.2 ГБ
    └── speakers_xtts.pth
```

```bash
source venv/bin/activate
python -c "
from huggingface_hub import snapshot_download
snapshot_download('coqui/XTTS-v2', local_dir='models/xtts_v2')
snapshot_download('Ftfyhh/xttsv2_banana', local_dir='models/xtts_v2_banana')
"
```

Ручной запуск нужен только там, где дашборд недоступен (например, при первом развёртывании на
чистой машине): в остальных случаях то же самое делает вкладка «Модели» с прогрессом и ошибками.

У banana-файнтюна чекпоинт лежит в подпапке (`model_banana/v2.0.2`), и `huggingface_hub`
раскладывает репозиторий по своим путям — движок сам ищет в каталоге пару `config.json` +
`model.pth` на любой глубине, так что перекладывать файлы руками не нужно.

Веса поднимаются **лениво**: при старте приложения грузится только F5-TTS, а XTTS —
при первом голосе на этом движке (в шапке дашборда чип `ENGINE` показывает `XTTS загружается` →
`XTTS готов`). Обе модели остаются тёплыми в одном процессе, пока их не выгрузят вручную или по
простою (см. «Контроль ресурсов»), а память под них считается в лимите watchdog'а.

## Запуск

Самый простой способ — **двойной клик по `VOICE_SYNTEZ.command` в Finder** (то же самое:
`bash VOICE_SYNTEZ.command` в терминале). Специально готовить окружение не нужно: лаунчер сам
находит Python 3.11+, создаёт `venv`, ставит зависимости, запускает backend и открывает браузер.

Что происходит при **первом** запуске:

1. лаунчер определяет каталог проекта по своему пути (а не по текущему каталогу), поэтому
   корректно работает и из Finder, и из любого места терминала, в том числе если путь содержит
   пробелы или кириллицу;
2. ищет Python 3.11+ (`python3.11`, затем `python3`, затем `python`) и объясняет, что поставить,
   если его нет;
3. создаёт `venv` и ставит `requirements.txt` — сеть нужна только к PyPI; веса моделей лаунчер
   не трогает;
4. проверяет `ffmpeg` и предупреждает, если его нет (без него не работает MP3-экспорт), но не
   падает;
5. поднимает backend на свободном порту (`PORT=8010 bash VOICE_SYNTEZ.command` — начать поиск
   с 8010) и открывает браузер.

При **повторных** запусках зависимости не переустанавливаются: лаунчер сравнивает хеш
`requirements.txt` с сохранённым в `venv/.requirements.sha256` и ставит их только если файл
изменился. Если приложение уже запущено (замок `.voice_syntez.lock` или отвечающий
`/api/status`), второй инстанс не поднимается — лаунчер просто открывает браузер на уже
работающий сервер и говорит об этом.

**Логи.** Весь вывод backend пишется в `logs/voice_syntez.log` и одновременно показывается в окне
терминала, чтобы оно не выглядело зависшим, пока грузится модель. Файл дописывается между
запусками; каталог `logs/` в git не попадает.

**Остановка.** `Ctrl+C` в окне лаунчера — backend получает сигнал, завершает текущую задачу,
закрывает сокет и освобождает замок; процессов после этого не остаётся.

Старый способ тоже работает и никуда не делся — для тех, кто уже активировал venv и хочет
видеть вывод в консоли:

```bash
./run.sh
# Открыть http://localhost:8000
```

Порт по умолчанию 8000; если он занят (частый случай — на нём может слушать другой проект),
лаунчер и `run.sh` сами берут следующий свободный и печатают выбранный.

Диагностика без запуска сервера: `bash VOICE_SYNTEZ.command --paths` печатает все пути, которыми
пользуется лаунчер (`PROJECT_DIR`, `VENV_PY`, `LOG_FILE`, маркер зависимостей).

Модель грузится в фоне при старте (~15 с на MPS) — индикатор в шапке дашборда показывает готовность.

### Почему лёгкий лаунчер, а не упаковка Python-рантайма

Выбран **lightweight launcher**: он готовит venv и запускает тот же `uvicorn backend.main:app`,
что и `run.sh`, — просто без ручной активации окружения. Упаковка (PyInstaller и подобные) эту
задачу здесь ухудшает, а не решает:

- **размер и обновление.** torch, `f5-tts`, `coqui-tts` и `transformers` вместе весят десятки
  гигабайт; их запекание в один бинарь превращает каждое обновление зависимостей в новую
  многогигабайтную сборку, тогда как `pip install -r requirements.txt` обновляет только
  изменившееся;
- **MPS.** Metal-контекст и нативные библиотеки torch плохо переносят замороженный рантайм:
  PyInstaller не умеет надёжно собирать динамически подгружаемые `.dylib` и Metal-шейдеры, а
  отладка «почему MPS не поднялся» в собранном бинаре заметно дороже;
- **ffmpeg.** Это внешний бинарник, которым пользуются pydub и чтение референсов. Его всё равно
  пришлось бы либо тащить внутрь (и терять обновления), либо требовать отдельно — то есть
  «одного файла» не получается;
- **локальные модели и логи.** Веса (`models/`, кеш `huggingface_hub`) должны лежать рядом и
  обновляться независимо от кода; понятные текстовые логи в `logs/voice_syntez.log` полезнее
  «тихого» GUI-приложения.

Лаунчер при этом не скачивает ничего, кроме pip-зависимостей при первом запуске: backend остаётся
локальным, offline-first и без облачных требований.

## Диагностика окружения

`tools/doctor.py` — самопроверка одной командой: она отвечает, что настроено не так, **до** первого
синтеза. Модели при этом не поднимаются, сеть не трогается, запущенный дашборд не мешает.

```bash
./venv/bin/python tools/doctor.py            # человекочитаемый отчёт
./venv/bin/python tools/doctor.py --json     # тот же отчёт машинночитаемым JSON
```

Проверяется: версия Python и venv, актуальность зависимостей, `ffmpeg`, наличие и размер каждой
модели (через реестр `model_manager`), свободное место, права на запись в `data/` и `output/`,
состояние порта и замка единственного инстанса, пробелы/не-ASCII в пути проекта и доступность MPS
(best-effort). Каждый пункт — со статусом `ok`/`warn`/`ОШИБКА` и подсказкой, что делать.
**Код возврата: 0 — всё в порядке, 1 — есть проблемы.**

## Тесты

```bash
source venv/bin/activate
python -m pytest          # весь набор, ~3 секунды
python -m pytest tests/test_job_queue.py -v
```

Модели при прогоне не поднимаются: реестр движков подменяется заглушкой `StubEngine`
(`tests/conftest.py`), которая отдаёт синусоиду и ведёт журнал вызовов, а каталоги `voices/`
и `output/` уводятся в `tmp_path`. Поэтому тесты идут секунды, не требуют весов и не трогают
рабочие файлы проекта. Поведение проверяется настоящее — реальные функции пайплайна, очереди
и роутов, — подменяется только сама модель.

### Нагрузочный тест

`tools/loadtest.py` — отдельный инструмент поверх живого сервера: ничего не мокает, ходит по
сети и поднимает настоящие модели. Нужен запущенный дашборд; в репозитории не является частью
pytest.

```bash
./venv/bin/python tools/loadtest.py               # все фазы
./venv/bin/python tools/loadtest.py light queue   # только выбранные
./venv/bin/python tools/loadtest.py --base-url http://127.0.0.1:8001 engines
```

| Фаза | Что меряет |
|---|---|
| `light` | Латентность `/api/status`, `/api/engines`, `/api/voices` и `/api/parse` последовательно |
| `load` | Те же ручки при 1/5/20/50 одновременных клиентах: RPS, p50/p99, счёт ошибок |
| `heavy` | Отзывчивость API, пока идёт настоящая задача с `qa=strict` |
| `queue` | Шесть задач разом: серийность очереди, ожидание и время работы каждой |
| `qa` | Один и тот же текст в режимах `qa=off`, `qa=smart` и `qa=strict`: время, число запусков Whisper и попытки |
| `engines` | XTTS холодный и прогретый плюс смешанный диалог F5 + XTTS |

Параллельно фоновый сэмплер снимает RSS сервера, RSS его дочерних процессов (Whisper-воркер),
CPU и занятость памяти системы, а в конце печатает пики отдельно по каждой фазе. Голоса для
прогона заданы константами `F5_VOICE` и `XTTS_VOICE` в начале файла — это id из `voices/voices.json`.

`tools/memory_check.py` — отдельный инструмент памяти: по шагам поднимает F5, затем XTTS,
выгружает их и печатает RSS, заполненность системы и счётчики MPS у torch после каждого шага,
а в конце — таблицу «до/после». Тоже не входит в pytest и запускается вручную. Дашборд перед
прогоном лучше остановить: два процесса с поднятыми моделями не влезут в память Apple Silicon.

```bash
./venv/bin/python tools/memory_check.py                          # F5 + базовая XTTS
./venv/bin/python tools/memory_check.py --xtts-engine xtts-banana
```

Инструмент не утверждает, сколько памяти вернётся: `current_allocated_memory()` учитывает то,
что видит сам torch, `driver_allocated_memory()` — то, что Metal выделил процессу, а в RSS на
Apple Silicon память MPS не попадает вовсе. Освобождение измеряется, а не предполагается.

**Замеры** (Mac, 18 ГБ, `mps`, F5 и XTTS прогреты):

| Что | Результат |
|---|---|
| Лёгкие ручки, 50 одновременных клиентов | ~5200 RPS, p50 9.5 мс, p99 10.2 мс, 0 ошибок из 1250 запросов |
| Тяжёлая задача под опросом `/api/status` десятью потоками | 16 944 запроса за 92 с, p99 4.4 мс, 0 ошибок — цикл событий синтезом не блокируется |
| Очередь из 6 задач | строго по одной (максимум 1 в работе, пересечений 0), ожидание растёт на ~6.5 с на задачу |
| QA на чистом диалоге, 3 реплики (16 с аудио) | `off` 30.0 с · `smart` 28.5 с (0 запусков Whisper) · `strict` 83.9 с (3 запуска) — ×2.9 к `smart` |
| XTTS: холодный и прогретый старт | 23.2 с на первую задачу (21 с из них — загрузка движка) против 1.8 с на прогретом |
| XTTS против F5 на одной реплике | XTTS +6.9…9.4 с, F5 +1.3…1.5 с — разница в 5-6 раз |
| Память | в режиме `strict` системная до 86.2 %, RSS сервера до 2.4 ГБ, RSS Whisper-процесса до 0.85 ГБ; в `smart` на чистом диалоге Whisper не поднимается вовсе |

Отсюда же видно, что дефолт `qa=off` выбран верно: `strict` стоит почти ×3 по времени даже когда
все куски проходят порог с первой попытки, а его настоящая задача — ловить редкий брак. `smart`
на нормальном тексте по времени не отличается от `off`: Whisper не запускается ни разу.

### Финальная проверка

`tools/smoke.py` — ручной end-to-end прогон по финальному сценарию roadmap на **живом** сервере и
реальных моделях. Инструмент проходит путь пользователя целиком: создать проект → назначить два
голоса (F5 и XTTS) → разобрать диалог со смешанными спикерами → рендер F5 + XTTS → Smart QA →
перегенерировать реплику → вернуть старый take → перезапустить backend → открыть проект заново →
выгрузить WAV → выгрузить SRT → экспортировать проект → импортировать его → отрендерить снова.
Шаги печатаются по одному, в конце — сводка PASS/FAIL/SKIP.

Инструмент ничего не мокает и не поднимает модели сам: их поднимает сервер. Если сервер
недоступен, полный прогон завершается понятной ошибкой **до** первого синтеза. Порты не
узурпируются: без `--base-url` адрес ищется по уже отвечающему `/api/status`.

```bash
./venv/bin/python tools/smoke.py --dry-run        # план шагов и проверка доступа к API, без синтеза
./venv/bin/python tools/smoke.py                  # полный прогон (реальные модели, долго)
./venv/bin/python tools/smoke.py --no-restart     # без шага ручного перезапуска backend
./venv/bin/python tools/smoke.py --base-url http://127.0.0.1:8001
```

Два голоса берутся из уже созданных в дашборде — по одному на `f5` и на `xtts`/`xtts-banana`
(можно задать явно: `--f5-voice ID --xtts-voice ID`). Файлы экспорта складываются в
`output/smoke/`, созданные проекты по умолчанию остаются в дашборде для осмотра (`--cleanup`
удаляет их). Шаг «перезапуск backend» выполняется человеком: инструмент печатает приглашение,
ждёт Enter и проверяет, что сервер снова отвечает и проект восстановился. `--dry-run` — единственный
режим, который безопасно запускать без сервера и без моделей.

## Как пользоваться

Дашборд состоит из пяти вкладок, они же пронумерованы в интерфейсе: **`01` «Голоса»** —
подготовка и проверка голосов, **`02` «Озвучка диалога»** — сборка диалога,
**`03` «Сплошной текст»** — озвучка целого файла одним голосом (и панель «Предложения для
словаря»), **`04` «Словарь»** — правила чтения терминов и ударений, **`05` «Модели»** — веса на
диске, их загрузка и удаление.
Логичный порядок работы — сначала голоса, а словарь можно заполнять когда угодно: он общий для
всех проектов. Над карточками реплик вкладки «Озвучка диалога» есть **таймлайн**: клик по блоку
открывает карточку реплики, так что нужное место в готовом файле находится глазами, а не
поиском по длинному текстовому списку.

Обычный путь один: вставьте текст → посмотрите панель «Что услышит модель» (там видно, что
сделали числа, восстановление «ё», словарь и ударения) → нажмите «Найти слова для словаря»,
подтвердите или отклоните кандидатов → озвучьте файл. Подтверждённое правило сразу появляется
во вкладке `04` и работает во всех будущих текстах; автоматически меняются только бесспорные
слова, а неоднозначные («все/всё») спрашивают один раз.

Там же, в панели `06 · Экспорт и импорт`, диалог можно сохранить архивом `.ttsproject` и открыть
на другой машине (см. «Экспорт и импорт проекта»), а также выгрузить готовый трек, реплики,
stems, транскрипт и субтитры. Выгрузка ничего не синтезирует: файл собирается из уже
сгенерированных take'ов, поэтому занимает секунды и не встаёт в очередь.

### Шапка дашборда

Слева — название студии, справа — кластер состояния: пять чипов, которые обновляются раз в
4 секунды, пока что-то не готово, и прекращают опрос, когда всё устоялось.

| Чип | Что показывает |
|---|---|
| `BACKEND` | Готовность сервера и цветную точку: зелёная — работает, жёлтая — идёт загрузка, розовая — ошибка. Значения: `загрузка`, `готов`, `ошибка`, `нет связи` |
| `DEVICE` | Устройство синтеза: `mps` или `cpu` |
| `ENGINE` | Состояние каждого поднятого движка: `F5 готов · XTTS загружается`. До первого голоса на движке — `не загружен` |
| `MEMORY` | RSS процесса в мегабайтах и полосу занятости памяти всей системы |
| `ACCENTIZER` | Состояние RUAccent: `загружается`, `вкл`, `ОШИБКА` |

Подробности, которые раньше занимали всю шапку одной строкой, переехали в подсказки: наведите
курсор на `BACKEND` — там полная строка про модель (`модель готова · mps · ударения: вкл`),
текст ошибки движка или причина, по которой не поднялся RUAccent; на `MEMORY` — сколько именно
занято системной памяти. Полоса у `MEMORY` показывает занятость памяти всей системы, а число
рядом — RSS этого процесса, то есть это намеренно разные метрики.

На узком окне чипы скрываются по одному, чтобы шапка не ломалась: до 1180 px — `DEVICE` и
`MEMORY`, до 700 px — ещё и `ENGINE`.

Внизу страницы — футер с названием студии и списком движков.

### Вкладка «Голоса»

Панели подписаны на экране: `01 · Мои голоса` (слева) и `02 · Новый голос` (справа). Шаги ниже —
это порядок работы, он обратный: сначала голос, потом его настройка в списке.

1. **Новый голос (панель 02).** Перетащите reference-аудио (или кликните по зоне и выберите файл),
   задайте имя, **движок синтеза** и расшифровку того, что сказано в записи. Референс:
   5–15 секунд чистой речи одного человека, без музыки и шума. Нажмите **«Сохранить голос»**.

   Движок предлагается по полу (женский → XTTS v2, иначе F5-TTS), но выбор можно переопределить
   в любой момент — и здесь, и потом в карточке готового голоса. Под списком показана подсказка
   по выбранному движку, в том числе про ударения.

   Расшифровку можно не набирать вручную: кнопка **«распознать»** заполняет поле по выбранному
   файлу, а если оставить поле пустым, текст распознается при сохранении. Кнопка заодно
   показывает, сколько секунд записи реально уйдёт в модель (см. ниже про обрезку).

   Расшифровка сверяется с записью по словам. Если совпало меньше 60 %, голос всё равно
   сохраняется, но получает жёлтый бейдж `⚠ расшифровка` и текст, который на самом деле
   распознан: так выглядит случай, когда в поле вставлена фраза от другой записи. Именно
   из-за такого рассинхрона синтез звучит невнятно, поэтому бейдж стоит воспринимать серьёзно.

   Из записи используется не всё: F5-TTS берёт первый фрагмент до ~12 секунд, отрезая по
   длинным паузам, XTTS — до 30 секунд. Остаток файла в синтезе не участвует.

   При сохранении дашборд измеряет высоту тона (F0) записи и сверяет её с выбранным полом:
   у карточки появляется бейдж `~N Гц`, а при расхождении — жёлтый `⚠ проверьте пол`
   (загрузку это не блокирует). Там же проверяется полоса частот: если выше 7 кГц в записи
   практически ничего нет (так звучат телефонные записи и сильно сжатые mp3) — появится
   бейдж `⚠ узкая полоса`, а в подсказке будет измеренный уровень верха. Синтез унаследует
   глухой тембр, и настройками это не лечится: лучше записать референс заново в полной полосе.
   Если запись оказалась копией демо-клипа из пакета F5-TTS,
   к имени автоматически добавляется `[demo]` и бейдж `demo` — такие файлы не стоит
   принимать за реальные голоса.

   Отдельный тумблер **«очистить запись от шума и реверба»** (нужен установленный
   DeepFilterNet, см. «Установка») прогоняет загруженный файл через денойзер *до* всех
   проверок и до записи в `voices/`: и F0, и полоса, и расшифровка считаются уже по
   очищенной записи — той самой, что уйдёт в модель. Это разовая операция при сохранении,
   поэтому на синтез она не влияет и после сохранения голоса галочка снимается. Помогает
   от гула, шипения и эха комнаты; от узкой полосы (см. бейдж выше) не спасает — там верх
   срезан навсегда. Файл после очистки всегда сохраняется как wav.
2. **Мои голоса (панель 01).** У каждого голоса выберите движок синтеза и настройте его ручки, впишите
   фразу для проверки и нажмите **«Прослушать»** — фраза синтезируется тем же движком, что
   и диалог, поэтому по превью слышно, как голос будет звучать в озвучке. Подберите параметры
   и только потом переходите к диалогу.

   Смена движка у готового голоса не трогает запись референса: можно перевести один и тот же
   голос с F5-TTS на XTTS и обратно и сравнить звучание. Набор настроек следует за движком —
   у F5 это CFG strength и NFE steps, у XTTS температура и штраф за повторы. Ручки другого
   движка не показываются, чтобы не создавать впечатления, что они на что-то влияют.

Подобранные при прослушивании параметры в диалог сами не попадают — их записывает явное
действие. Кнопка **«сохранить настройки»** в карточке голоса берёт то, с чем вы только что
прослушали фразу (скорость, CFG, NFE и ручки движка), и делает это **пресетом голоса**: под
кнопкой появляется строка «настройки голоса: скорость 0.90x · CFG 2.3 · NFE 24». С этого
момента пресет — нижняя ступень настроек любого диалога с этим голосом: новый проект
открывается уже с ним, а правки участника и реплики ложатся поверх и пресет не портят
(см. «Параметры синтеза»). Так голос настраивается один раз, а не заново в каждом диалоге.

Кнопка **«удалить»** на карточке голоса стирает запись вместе с файлом референса; задачи,
уже стоящие в очереди, после этого упадут с сообщением о потерянном файле.

#### Фразы для начитки референса

Если референс записывается с микрофона, блок **«Записать голос с микрофона»** предлагает готовые
фразы — их **11** вместо прежних пяти. Текст показывается до записи, потому что F5-TTS клонирует
голос по паре «запись + её дословная расшифровка», и совпадение здесь важнее всего.

Список намеренно неоднороден по интонации: вопрос, восклицание, просьба, а с добавлением —
радость/восторг, огорчение/сочувствие, лёгкая ирония, строгий приказ, ровное перечисление и
быстрая взволнованная речь. Модель копирует то, что слышит, поэтому на пяти однотипных
утверждениях она клонирует слишком узкий кусок голосового диапазона. Вторая причина — буква
«ё»: теперь она гарантированно звучит в референсе в разных словах и позициях, а не только
встречается случайно.

Правило начитки при этом не меняется: **одна эмоция и ровный темп на всю фразу**, разнообразие —
между фразами, а не внутри одной. Ни одну фразу не нужно читать «через силу», меняя интонацию
посередине: рваный темп портит референс сильнее, чем узкий набор звуков.

Длительность. Фразы остались короткими: исходные читаются примерно за 4.9–7.4 с, новые — за
7.0–8.8 с (оценка тем же грубым оценщиком, что использует Smart QA). Это чуть длиннее прежних,
но с запасом укладывается в первые ~12 с, которые F5 берёт из референса, и намеренно не
растянуто под 30-секундный лимит XTTS: чем короче ровная начитка, тем чище клон. За этим
следят два теста — по пределу 12 с и по отсутствию растягивания относительно исходных.

Отдельно есть **тестовая фраза с плотной «ё»** («Ёж и ёлка стоят у забора…»). Это тестовые
данные, а не фраза для записи: в списке начитки её нет и при записи референса она не
предлагается. В панели «Что услышит модель» (вкладки «Озвучка диалога» и «Сплошной текст») её
подставляет кнопка **пример с «ё» — только для проверки**, чтобы сразу увидеть стадии
нормализации и восстановления «ё» (см. «Восстановление буквы «ё»» и «Что услышит модель
(preview)»). Причина запрета прямая: противоестественная плотность одного звука ломает ровный
темп начитки, от которого зависит качество клонирования. По той же логике в список не добавлена
подпись под шёпот: проверка пола голоса по F0 (см. выше про бейдж `⚠ проверьте пол`) на шёпоте
ненадёжна, поэтому регистр «тихо, доверительно» читается обычным, но негромким голосом.

### Сравнение движков

Кнопка **«⇄ Сравнить движки»** в карточке голоса отвечает на вопрос «какая модель читает этот
голос лучше»: вы задаёте одну тестовую фразу и набор движков, система синтезирует **эту фразу
тем же reference-аудио и тем же `ref_text`** отдельно каждым движком и складывает takes в
`output/benchmarks/{run_id}-{engine}.wav`. Дальше остаётся прослушать их в таблице.

```
F5            [Play]  Render: 1.4 сек   WER: 0.04
XTTS v2       [Play]  Render: 7.3 сек   WER: 0.02
XTTS Banana   [Play]  Render: 8.1 сек   WER: 0.08
```

- **Фраза и reference общие, отличаются только модели.** Иначе сравнение превращалось бы в
  сравнение разных условий: у голоса один и тот же файл референса и одна и та же расшифровка,
  а движок меняется только на время прогона.
- **Параметры движков не смешиваются.** Резолв настроек применяет только те ручки, что
  объявлены в паспорте движка (`EngineInfo.params`): температура и штраф за повторы XTTS не
  доедут до F5, а CFG/NFE F5 — до XTTS. Общий пресет голоса (скорость, громкость) при этом
  действует на все движки — сравнение идёт на одних настройках, а не на дефолтах каждой модели.
- **Недоступный движок не рушит сравнение.** Нет весов, не хватило памяти, модель не
  поднялась — в строке этого движка будет статус `error` с понятной причиной, остальные
  движки доработают, а запуск завершится `done`.
- **`render_sec` — это время синтеза**, а не загрузки модели: подъём весов (десятки секунд,
  один раз) в замер не входит. С включённой проверкой качества (`smart`/`strict`) в него
  попадают и повторы с расшифровкой Whisper, а WER появляется в строке результата.
- **Система не выбирает лучший движок по WER.** Никакого ранжирования и авто-выбора «победителя»
  нет: WER и время — справка, решение принимает человек. Кнопка **«Выбрать этот движок»**
  меняет у голоса **только** движок (reference, его расшифровка и пресет остаются как были);
  до этого запускается вручную, автоматически ничего не переключается.
- **Движки идут строго по одному** — тем же единственным inference-воркером, что и рендер:
  сравнение не поднимает модели параллельно и не синтезирует в обход очереди.
- **Файлы сравнения не чистит TTL.** Они лежат в подкаталоге `output/benchmarks/`, а очистка
  проходит только по файлам верхнего уровня `output/` (как и куски проектов в `output/projects/`).

### Вкладка «Озвучка диалога»

1. **Панель 1 — два представления.** По умолчанию открыт **Visual editor**: карточки реплик, на
   которые разобран текст. Сам текст с маркерами живёт во втором представлении —
   **Source / Advanced**, там же кнопка **«Применить и разобрать»**. Правка текста не запускает
   разбор сама: пока он не применён, «Сгенерировать» заблокирована и рядом видно, что есть
   неразобранные правки. Голос задаётся **маркером-слотом прямо в тексте**:

   ```
   АРТЕМ(1): Привет! МАРГО(2): И тебе привет. Как дела? (3) — спросила девушка.
   ```

   | Запись | Смысл |
   |---|---|
   | `(1)` | переключить голос на слот 1 |
   | `АРТЕМ(1): ` | то же + имя-метка «АРТЕМ», в аудио не читается |
   | `Иван: ` | старый формат: имя спикера само служит ключом голоса |
   | `(1 speed=1.2 cfg=2.5 nfe=16)` | слот 1 + параметры синтеза для этого куска |

   Правила:

   - маркер работает **в любом месте текста** и держится до следующего маркера;
   - текст между маркерами синтезируется отдельными кусками (пауза между ними не вставляется);
   - текст до первого маркера читает **слот 1**;
   - слоты и имена спикеров можно свободно смешивать в одном тексте;
   - маркером считается только `(цифры)` от 1 до 20 — `(тихо)`, `(2024)`, `12:30` остаются текстом;
   - параметры из маркера **важнее** настроек карточки в Панели 2;
   - строка без маркера и без `Имя:` — продолжение предыдущего куска.

2. **Панель 2.** Карточка на каждый голос, встреченный в тексте: «Слот N» — для маркеров `(N)`,
   имя — для реплик вида `Имя:`. В карточке выберите сохранённый голос, а при необходимости
   поправьте скорость и ручки движка этого голоса. Это настройки **всего спикера**: отдельная
   реплика может взять свой голос и свои параметры в своей карточке (см. ниже).

   Голос у карточки не подставляется автоматически: пока для любого голоса из текста не выбран
   его собственный голос, кнопка «Сгенерировать» остаётся неактивной. Чего не хватает — видно в
   сводке над карточками реплик: она показывает число реплик и участников, а при незаполненных
   карточках добавляет «без голоса: N» и подсвечивается жёлтым. Так диалог не может случайно
   уйти в озвучку одним голосом.

3. **Панель 3.** Пауза между репликами, кроссфейд, автоударения, режим проверки качества, формат вывода.

4. **Панель 4.** «Сгенерировать» → прогресс «реплика N из M» → плеер и кнопка скачивания.
   Пока задача ждёт или считается, рядом с прогрессом видна **«Отменить»**: ожидающая задача
   отменяется сразу, идущая — на ближайшей безопасной точке (между репликами), и в обоих
   случаях статус становится `cancelled`, а часть собранного аудио не остаётся на диске.
   Отдельную реплику пересобирают не здесь, а в её карточке (кнопка «Regenerate»): это стоит
   одного куска, а не всего диалога. Если кусок не прошёл проверку полностью, у варианта
   появляется отметка с WER и причиной.

   Тот же порядок у режима «Сплошной текст»: у его прогресса — своя кнопка «Отменить».

#### Карточки реплик (Visual editor)

После разбора диалог превращается в карточки — по одной на реплику:

```text
АРТЕМ · Replica 12
Voice: Vlad
Engine: F5

Привет! Рад тебя видеть.

[Play] [Regenerate]

Take: 2
Speed: 1.00
Pause before: 350 ms
```

В карточке можно:

- **выбрать голос реплики** — «как у спикера» (строка «— как у спикера: … —») возвращает
  назначение из Панели 2; у карточки спикера остаются остальные реплики;
- **увидеть движок** — он берётся из карточки выбранного голоса, поэтому у соседних реплик
  одного диалога движки могут быть разными (F5 и XTTS в одном файле);
- **поправить `Speed` и `Pause before`**, а в блоке «Ещё настройки реплики» — ручки движка,
  громкость, питч-шифт и целевую громкость;
- **запустить `Regenerate`** — пересинтез только этой реплики: соседние не трогаются, а
  результат ложится новым вариантом (`take`) и сразу становится активным. Пока реплика занята,
  рядом появляется **«Отменить»**: отмена снимает пересборку, оставляет прежнее звучание и
  убирает транзитные варианты этой попытки;
- **прослушать варианты и выбрать активный** — `Play` играет активный, список вариантов даёт
  сравнить с прежними звучаниями. Выбор мгновенный: варианты — готовые файлы, синтез при нём
  не запускается;
- **вернуть параметр к наследуемому** кнопкой сброса у ползунка.

Правки реплики — надстройка над карточкой спикера, а не её замена: пока у реплики ничего не
тронуто, в ползунках стоят значения спикера, а у ручек движка — его настройки. Сброс возвращает
параметр к наследуемому значению, а не «замораживает» текущее. Текст реплики правится только в
**Source / Advanced**: карточка показывает его как есть.

У каждого параметра подписано, откуда взято значение: `наследуется от голоса «Anna»` — так
настроен сам голос, `наследуется от участника` — переопределено в Панели 2, `правка этой
реплики` — изменено здесь. Кнопка **«сброс»** появляется только там, где значение перекрыто
**этим** слоем, и возвращает параметр на ступень ниже — в её подсказке видно, к какому именно
значению (например `вернуть наследуемое значение → 0.90x`). Унаследованное сбрасывать из
карточки нечем: правка участника живёт в Панели 2, настройка голоса — в карточке голоса, и
снимают их там же. В Панели 2 те же подписи читаются со своей стороны: правка слота подписана
`правка участника`, правка конкретной реплики — `правка этой реплики`.

Разбор и правки — разные слои, и источник истины для состава реплик — исходный DSL. Поэтому
**разбор применяет текст, а не наоборот**: параметры из маркеров (`(3 speed=1.2 cfg=2.5 nfe=16)`)
при повторном разборе перекрывают то, что выставлено в карточках. Зато у реплик, чей текст и
спикер не менялись, варианты и выбранный take остаются на месте — правится одна строка, а не
весь диалог.

#### Таймлайн

Над карточками реплик — дорожка готового файла: по одной строке на спикера, внутри — блоки
реплик. Место и ширина блока считаются **по реальным длительностям take'ов**, а не по числу
знаков: длина куска зависит от движка, скорости, обрезки тишины и подготовки куска
(`_prepare_chunk`), и оценка «по символам» разошлась бы с файлом на первом же рендере.

```text
00:00      00:20      00:40      01:00      01:20      01:42

АРТЕМ  ████████       █████████
МАРГО          ███████         ███████
```

Как он устроен:

- **Границы — по активному take.** У каждой реплики берётся длительность того варианта, которым
  она звучит сейчас (`duration_sec` из базы), и пауза перед ней по тем же правилам, что и при
  сборке: личный `pause_override_ms` реплики важнее паузы спикера, а её отсутствие — общая
  `pause_ms`; перед первой репликой паузы нет. Смешанные движки на время не влияют: все движки
  отдают 24 кГц, а длительность берётся из take'а.
- **`start`/`end` не хранятся в базе.** Таймлайн считается заново на каждый запрос
  (`GET /api/projects/{id}/timeline`). Хранить их значило бы держать вторую правду, которая
  разошлась бы с файлом после первой же замены take.
- **Замена take пересчитывает хвост.** Выбрали более длинное звучание — все реплики после него
  сдвинулись вправо, короткое — влево; пересчёт получается сам собой, потому что границы
  считаются по активным take'ам при каждом запросе.
- **Кроссфейд границ не двигает.** `cross_fade_duration` — ручка F5 для сшивания батчей
  **внутри** куска; склейка реплик — `np.concatenate` без перекрытия, а `_finalize_track` длину
  не меняет, поэтому сдвигать границы от него нечему (зафиксировано тестом).
- **Реплика без take не ломает таймлайн:** она нарисована пустым штрихованным блоком с подписью
  («нет take»), не двигает курсор и не тянет за собой чужие границы. Именно за неё и надо
  взяться, чтобы сгенерировать реплику.

**Клик по сегменту открывает инспектор** — это та же карточка реплики: страница прокручивается к
ней, карточка подсвечивается, а фокус встаёт на `Play` (или на `Regenerate`, если звука ещё нет).
Внутри — номер реплики, спикер, голос, прослушивание активного take, список вариантов,
`Regenerate`, пауза, скорость, ручки движка и отметка QA. Второго редактора нет намеренно:
правки живут в одном месте, и таймлайн лишь ведёт к ним. Кнопка **«обновить»** в углу дорожки
перечитывает длительности, а после рендера и после выбора take таймлайн обновляется сам.

### Экспорт и импорт проекта

Панель `06 · Экспорт и импорт` на вкладке «Озвучка диалога» выгружает проект, его аудио и
субтитры и принимает архив обратно. Ни одно из этих действий **не запускает инференс**: файл
собирается из уже готовых take'ов, поэтому выгрузка мгновенная и не занимает очередь.

**Архив проекта `.ttsproject`** — это ZIP-контейнер с тремя частями:

```text
project.json        метаданные проекта, спикеры, реплики и take'ы
references/         референсы только тех голосов, что используются проектом
takes/              файлы take'ов реплик
```

В `project.json` лежат: версия формата, имя, режим, `source_text`, `render_settings` и статус
проекта; спикеры (ключ, подпись, назначенный голос, правки); реплики (порядок, текст, спикер,
свой голос, правки, выбранный take, статус); take'ы (подпись, имя файла внутри архива, сид,
движок, параметры, длительность, `qa`, `quality`) и описания используемых голосов — имя, пол,
`ref_text`, движок, пресет и имя файла референса внутри архива.

**Веса моделей в архив не попадают никогда** — ни `models/`, ни кеш Hugging Face. Архив переносит
диалог и референсы голосов, а не чекпоинты: имена внутри архива генерирует сам бэкенд
(`references/ref-01.wav`, `takes/r001-t001.wav`), поэтому пользовательские имена в путях не
участвуют, и «сходить наружу» через имя файла нечем. Это зафиксировано тестом: в архиве нет
путей, похожих на веса, и нет файлов `.pth`/`.safetensors`/`vocab.json`.

**Импорт** (`POST /api/projects/import`, поле `file`) создаёт **новый** проект: исходный диалог не
перезаписывается, повторный импорт того же архива даёт второй проект. Перед распаковкой каждая
запись проверяется — абсолютные пути, `..`, символические ссылки и записи вне целевого каталога
отклоняются, а распаковка идёт во временный каталог; проект создаётся только после того, как
`project.json` прочитан и версия формата признана совместимой. Битый ZIP, архив без `project.json`
или архив «из будущего» дают понятную ошибку 400, а не трейсбек и не половину проекта.

Что происходит с голосами: они сопоставляются **по имени**. Если голос с таким именем уже есть на
этой машине, он используется как есть — движок, пресет и референс не перезаписываются. Если голоса
нет (новая машина), он создаётся из референса и расшифровки внутри архива, после чего `voice_id`
спикеров и реплик переназначаются на актуальный. Голос, у которого в архиве не оказалось
референса или его расшифровки, пропускается с предупреждением: проект импортируется, но спикеру
придётся выбрать голос заново.

**Экспорт аудио и субтитров** (тоже панель `06`):

| Вариант | Что внутри |
|---|---|
| Итоговый трек — WAV / MP3 | Активные take'ы, склеенные с теми же паузами, что у рендера; длительность совпадает с таймлайном |
| Реплики (ZIP) | По одному WAV на каждую звучащую реплику — `r001.wav`, `r002.wav` |
| Stems (ZIP) | Дорожка на спикера: чужие реплики — тишина, поэтому stems синхронны друг с другом и с итоговым треком |
| Транскрипт (JSON) | Реплика, спикер, голос, текст и реальные `start_sec`/`end_sec` |
| SRT / VTT | Субтитры по реальным таймстемпам таймлайна (формат `HH:MM:SS,mmm` / `HH:MM:SS.mmm`) |

Реплика без звука в субтитры и транскрипт не попадает: у неё нет ни начала, ни конца, а выдумать
ей место значило бы рассинхронизировать файл с дорожкой. Ограничение формата — только
вышеперечисленные варианты; произвольный набор дорожек и «выгрузить только часть реплик» не
поддерживаются.

### Вкладка «Сплошной текст»

Озвучка целого текста **одним голосом**, без маркеров и спикеров.

1. **Панель 1.** Перетащите `.txt`/`.md` (или кликните по зоне) либо просто вставьте текст.
2. **Панель 2.** Выберите голос и при необходимости поправьте скорость и ручки его движка.
3. **Панель 3.** Пауза между кусками, кроссфейд, автоударения, режим проверки качества, формат вывода.
4. **Панель 4.** «Озвучить текст» → прогресс «кусок N из M» → плеер и кнопка скачивания.
   Если какие-то куски не прошли проверку полностью, под статусом появляется строка
   «Проверка качества: N из M кусков приняты без полного прохождения, лучший WER …».
5. **Панель 5.** «Что услышит модель»: стадии обработки текста до синтеза, включая
   восстановление «ё». Синтез при этом не запускается и TTS-модель не поднимается.
6. **Панель 6.** «Предложения для словаря»: кнопка «Найти слова для словаря» прогоняет текст по
   тем же стадиям и показывает кандидатов — неоднозначные «е/ё», омографы ударения и редкие
   слова. У каждого кандидата видна причина и редактируемая замена, рядом кнопки «Добавить» и
   «Отклонить», сверху — «Добавить все». Пустой список подписан «Слов для уточнения не
   найдено», ошибки и процесс поиска видны прямо в панели. Подтверждённое правило появляется
   во вкладке `04` как обычное, отклонённое — как выключенное (см. «Предложения для словаря»).

Текст режется на куски **по границам предложений и абзацев**, а не по числу символов:
Движок синтезирует каждый кусок с нуля и не помнит предыдущие, поэтому обрыв внутри фразы
дал бы сброс интонации посреди мысли. Пунктуация передаётся модели как есть — паузы и
интонацию она расставляет сама. На стыках кусков возможен небольшой сброс темпа: это
свойство блочной генерации, кроссфейд сглаживает только громкость.

### Вкладка «Словарь»

Вкладка `04` — это единственное место, где задаётся произношение слов. Словарь **общий для
всех проектов**: правило достаточно добавить один раз, и оно подхватится и в диалоге, и в
сплошном тексте, и в прослушивании голоса.

1. **Панель 1 (слева).** Список правил: `источник → замена`, бейджи режима и два
   переключателя — «включено» и «учитывать регистр». Выключенное правило остаётся в списке,
   но приглушено: его видно и легко вернуть. Рядом кнопки «правка» и «удалить».
2. **Панель 2.** «Проверить текст»: вставьте фразу и нажмите кнопку — панель покажет
   **две стадии**: «после нормализации» (что сделали числа, даты и сокращения) и «уйдёт в
   модель» (что сделал словарь). Ниже — список сработавших правил со счётчиком замен.
   Синтез при этом не запускается, TTS-движок не поднимается, в базу ничего не пишется.
3. **Панель 3 (справа).** Форма правила: источник, замена, заметка, «только целое слово»,
   «учитывать регистр», «правило включено». Кнопка «Сохранить правило» создаёт правило или
   обновляет выбранное (при нажатии «правка» заголовок меняется, появляется «отменить правку»).

Если словарь пуст, вместо пустого экрана показана подсказка с примером. Если правило с таким
же источником уже есть, повторное сохранение **обновляет** его, а не создаёт второе — так
случайный двойной клик не оставляет мусор. При ошибке сети или запроса причина пишется
прямо над списком, понятным текстом.

Здесь же видны правила, созданные из предложений вкладки `03`: подтверждённые — как обычные
включённые, отклонённые — как выключенные с заметкой «отклонено в предложениях». Второе не
мусор и не ошибка: выключенная запись работает **памятью** о решении, поэтому то же слово
больше не предлагается, а вернуть его можно одним переключателем «включено».

### Вкладка «Модели» (менеджер моделей)

Вкладка `05` показывает, какие веса уже лежат на диске, какие подняты в память и сколько
места всё это занимает. Ручной `snapshot_download` для установки больше не нужен.

Что показывает карточка модели:

- **установлена / не установлена** и, если файлов не хватает, их список поимённо;
- **размер** — сколько занимает сама модель (а не весь каталог: у F5 файлы лежат прямо в
  `models/`, рядом с чужими весами);
- **`в памяти`** — движок этой модели уже поднят, **`выгружен`** — движок создан, но модель
  освобождена (вручную или по простою), **`движок занят`** — он поднят или прямо сейчас синтезирует;
- **путь** к файлам модели и HF-репозиторий, из которого она берётся;
- **состояние скачивания**: прогресс-бар, «скачано N из M», ошибка текстом.

Кнопки: **«Скачать»** (запускает загрузку в фоне, прогресс виден на этой же странице),
**«Выгрузить»** / **«Загрузить»** (возвращает память и поднимает модель обратно без синтеза),
**«Удалить»** (с подтверждением) и **«Обновить»** — перечитать список. Справа — сводка по
диску: занято моделями и свободно на диске.

Четыре модели проекта: **F5-TTS Russian** (~1.4 ГБ, `models/`), **XTTS v2 базовая** (~1.9 ГБ,
`models/xtts_v2`), **XTTS v2 banana** (~5.2 ГБ, `models/xtts_v2_banana`) и **Whisper
large-v3-turbo** (~1.6 ГБ, кеш `huggingface_hub` — не в `models/`). Whisper и вокодер Vocos
скачиваются самими библиотеками: ими дашборд не управляет, он только показывает, что они уже
есть, и определяет это **без обращения к сети**.

**Скачивание не обязательно.** Приложение offline-first: если веса уже лежат на диске
(или их положили вручную), всё работает без интернета — вкладка нужна только для установки
и диагностики. Скачивание запускается **только по кнопке** (при старте сервера ничего не
качается), идёт в фоновом потоке по одной модели за раз и не проходит через очередь
синтеза: сеть и диск — не инференс. Повторное нажатие «Скачать» на установленной модели
ничего не делает — файлы не перезаписываются и не меняются. Прерванная загрузка не считается
установкой: в карточке останется пунктир недостающих файлов, а повторный запуск доведёт дело
до конца.

**Почему удаление запрещено при занятом движке.** Файлы `model.pth` и чекпоинт F5 читает
работающая модель: удалить их из-под неё — уронить синтез. Поэтому `DELETE` отвечает `409`,
пока движок поднят (`в памяти`) или пока в очереди идёт задача, которая синтезирует этим
движком. Сначала выгрузите движок кнопкой **«Выгрузить»** (это и есть освобождение памяти без
рестарта), затем удаляйте файлы. Модель, которая ни разу не поднималась, удаляется свободно.

**Выгрузка и загрузка движка.** Кнопка **«Выгрузить»** у поднятой модели вызывает
`POST /api/engines/{id}/unload`: движок отпускает модель, память возвращается системе, а
запись в очереди и история рендеров не трогаются. Отказ приходит честным текстом: `409`
«движок занят синтезом», если он прямо сейчас читает модель, и `409` «очередь занята задачей»,
если в очереди есть работа (в том числе перегенерация) — выгружать модель, которая понадобится
следующей реплике, незачем. Кнопка **«Загрузить»** (`POST /api/engines/{id}/load`) поднимает
движок заранее, без синтеза. Следующий синтез поднимет выгруженный движок сам: `synthesize()`
вызывает `load()`, если модель не в памяти, — выгрузка никогда не «ломает» рендер, она только
добавляет к нему время загрузки. Память после выгрузки действительно освобождается; точный
объём измеряется инструментом `tools/memory_check.py`, а не обещается заранее.

Ниже, отдельной секцией, эта же вкладка умеет чистить **свой** кеш приложения (транзитные
файлы, а не веса) — см. «Очистка кеша приложения».

### Очистка кеша приложения

Ниже списка моделей, в той же вкладке `05`, есть отдельная секция **«Очистка кеша
приложения»**: три чекбокса с текущими размерами, кнопка **«Очистить выбранное»** и
**«Обновить»**. Размеры берутся из `GET /api/cache` при открытии вкладки, после очистки
перечитываются, а в ответе видно, сколько освобождено всего и по каждой категории отдельно.

| Категория | Что удаляется | Почему |
|---|---|---|
| Готовые файлы задач | Файлы **в корне** `output/` (`job1.mp3`, варианты кусков и т. п.) | То же, что чистит TTL (`TTS_OUTPUT_TTL_HOURS`), только немедленно, не дожидаясь срока |
| Сравнение движков | `output/benchmarks/*.wav` | Эти файлы **не попадают под TTL вообще**: очистка обходит только корень `output/`, а сравнение лежит в подкаталоге. Запуски сравнения при этом забываются — иначе панель показывала бы строки со ссылками на уже удалённые файлы |
| Временные файлы | Промежуточные `*.tmp.wav` рядом с целью в `output/` и `output/projects/*/`, а также наши остатки в системном temp (`tts-export-`, `tts-import-`, `voice-denoise-`, `voice-syntez-`) старше часа | Файлы такого вида остаются только при сбое процесса между созданием и удалением; активные операции (экспорт, импорт, очистка записи) моложе порога и не трогаются |

**Как этим пользоваться.** Откройте вкладку `05` «Модели»: секция «Очистка кеша приложения» —
под двумя панелями о весах и диске, она третья по счёту в этой вкладке. Отметьте нужные
категории (рядом с каждой — текущий размер), нажмите **«Очистить выбранное»** и посмотрите на
итог: он покажет освобождённое место и число файлов по каждой категории, а размеры подтянутся
заново. Пока не отмечено ничего, кнопка неактивна и подсказка объясняет почему. Кнопка
**«Обновить»** просто перечитывает размеры, ничего не удаляя.

**Что в очистку не попадает — и не может попасть.** Ни одна из трёх категорий не ведёт в
`data/` (база проектов и словарь произношения), `voices/` (референсы и `voices.json`),
`models/` и кеш `huggingface_hub` (веса), `output/projects/` (take'ы проектов — это данные
проекта, а не транзитный кеш). Путь каждой категории жёстко задан в коде
(`backend/cache_cleanup.py`), а перед удалением файла проверяется, что его реальный путь
лежит внутри ожидаемого корня; символические ссылки не разворачиваются. Поэтому даже
отметка всех трёх чекбоксов сразу не может задеть базу, словарь, голоса или веса. Удаление
весов — отдельный осознанный поток: кнопка **«Удалить»** в списке моделей выше. `.gitkeep`
в `output/` и `output/benchmarks/` остаётся всегда.

**После очистки ссылки на удалённые файлы перестают работать.** Готовое аудио задачи, ссылка
на прослушивание take'а сравнения, кнопки скачивания готовых файлов прошлых задач — всё это
указывает на файлы, которых больше нет: их придётся синтезировать заново. Именно поэтому
очистка ручная и по явному выбору, а не автоматическая. Проекты при этом не страдают: их
реплики, take'ы и таймлайн лежат отдельно и переживают очистку — заново понадобится только
итоговый файл задачи.

### Громкость и паузы всего трека

Куски выравниваются по `target_rms` по отдельности, но RMS не равен воспринимаемой громкости:
у F5 и XTTS разная плотность звука, и на стыке движков слышен скачок даже при одинаковом RMS.
Поэтому по уже собранному файлу идёт финальный проход — **нормализация по LUFS**
(ITU-R BS.1770, `pyloudnorm`) до `TTS_OUTPUT_LUFS`, а сразу за ней **лимитер** (потолок 0.99),
без которого подъём до целевого LUFS клипует на пиках. Тот же проход повторяется после
перегенерации одной реплики — иначе заменённый кусок остался бы на другой громкости, чем файл.

Второе в том же проходе — **обрезка тишины на краях куска**. Модель сама добавляет к
сгенерированному фрагменту немного тишины, и `pause_ms` ложился поверх неё: зазор между
репликами гулял от куска к куску. Теперь края тише `TTS_EDGE_SILENCE_DB` срезаются (с запасом
30 мс вокруг найденной речи), и пауза между репликами равна ровно заданной в настройках.

Управлять интонацией конкретной фразы («прочитай с сарказмом») нельзя ни параметрами, ни
текстом — единственный канал влияния на интонацию это reference-аудио.

### Параметры синтеза

Общие — действуют у любого движка. В скобках — ключ, которым параметр передаётся в API:

| Параметр | Диапазон | Смысл |
|---|---|---|
| Скорость речи (`speed`) | 0.5–2.0 | Темп речи, у каждого спикера свой |
| Пауза между репликами (`pause_ms`) | 0–2000 мс | Тишина между репликами диалога (в сплошном тексте та же ручка подписана «Пауза между кусками») |
| Кроссфейд (`cross_fade_duration`) | 0–0.5 с | Склейка внутри длинной реплики при её разбивке на чанки |

Эти три ручки влияют на звук **до** синтеза: они уходят в модель или в склейку дорожки.
Остальные спрятаны под «Ещё настройки голоса» в карточке голоса, «Ещё настройки» в панели
«Сплошной текст» и «Ещё настройки реплики» в карточке реплики — они работают **после** синтеза,
поверх любого движка, и потому доступны одинаково у всех моделей:

| Параметр | Диапазон | Смысл |
|---|---|---|
| Громкость (`gain_db`) | −20…+20 дБ | Балансировка голоса по громкости: применяется после выравнивания RMS, когда один голос тише другого и это не лечится на уровне модели |
| Питч-шифт (`pitch_semitones`) | −12…+12 пт | Меняет высоту тона, но не пол голоса: тембр остаётся от референса. Пометка «экспериментально» в интерфейсе — по делу |
| Целевая громкость куска (`target_rms`) | 0.02–0.3 | Уровень, к которому подтягивается каждый кусок. Одно и то же значение идёт и в модель F5, и в пост-нормализацию — иначе куски приходят с разным уровнем и «скачут» на стыках. Ниже 0.02 звучит как шёпот, выше 0.3 модель упирается в клиппинг |
| Пауза перед репликами (`pause_override_ms`) | 0–5000 мс | Пауза только для этого спикера или для одной реплики (в её карточке), вместо общей по диалогу. Тумблер «как в общих настройках» возвращает общую и блокирует ползунок |

Ручки движка — набор зависит от того, какая модель выбрана у голоса. В скобках — ключ,
которым параметр передаётся в API:

| Движок | Параметр | Диапазон | Смысл |
|---|---|---|---|
| F5 | CFG strength (`cfg_strength`) | 1.0–4.0 | Меньше — выразительнее, больше — стабильнее |
| F5 | NFE steps (`nfe_step`) | 8/16/32 | Больше — качественнее, но дольше (по умолчанию 32) |
| XTTS | Температура (`temperature`) | 0.1–1.5 | Ниже — ровнее и предсказуемее, выше — живее и рискованнее (по умолчанию 0.75) |
| XTTS | Штраф за повторы (`repetition_penalty`) | 1.0–20.0 | Лечит заикание и «залипание» на слоге (по умолчанию 5.0) |

Значения вне диапазона не отклоняются, а зажимаются к ближайшей границе; незнакомые движку
ключи игнорируются. В карточке голоса ручки движка сохраняются на самом голосе; в API их можно
переопределить на одну задачу полем `engine_params` (см. ниже) — тогда настройка голоса
не меняется. Маркер в тексте диалога умеет задавать только `speed`, `cfg` и `nfe`; ту же скорость,
паузу перед репликой и ручки движка можно задать у одной строки в её карточке — правка реплики
перекрывает карточку спикера и на соседние реплики не влияет.

Ползунки в интерфейсе уже, чем принимает API: пауза между репликами — до 2000 мс (API зажимает
до 5000), кроссфейд — до 0.5 с (API — до 1.0). Если через API нужны крайние значения, задавайте
их напрямую.

#### Иерархия настроек

Значения складываются лесенкой, и каждая ступень перекрывает предыдущую:

| Ступень | Где задаётся | Подпись в интерфейсе |
|---|---|---|
| Дефолты движка | паспорт движка (`/api/engines`) | нет — это исходное значение |
| Пресет голоса | карточка голоса, кнопка «сохранить настройки» | `наследуется от голоса «Anna»` |
| Участник | Панель 2, карточка спикера | `правка участника` здесь и `наследуется от участника` — в карточках его реплик |
| Реплика | карточка реплики | `правка этой реплики` |

Слои хранятся **разреженно**: в слое лежит только то, что пользователь выбрал сам, а остальное
наследуется снизу. Поэтому «настроить голос один раз» и работает — сохранение слота не
переписывает пресет своими значениями, — а сброс возвращает параметр ровно на ступень ниже, а
не к дефолту движка. Ручки чужого движка в резолве не участвуют: они относятся к другому
паспорту и при смене движка у голоса не применяются. Значения вне диапазона зажимаются уже
после склейки слоёв.

Считает это одно место — [settings_resolution.py](backend/settings_resolution.py); и синтез, и
API получают один и тот же резолв, поэтому подпись в карточке не может разойтись с тем, что
ушло в модель. В ответах API `settings` есть и у реплик, и у спикеров: у каждого параметра —
`value`, `source` (`engine`, `voice`, `speaker` или `replica`) и, если значение перекрыто,
`inherited` со значением ступенью ниже. Логику склейки ни API, ни фронтенд не повторяют.

### Ударения

Расставляются автоматически (RUAccent, знак `+` перед ударной гласной). Отключается тумблером
в Панели 3.

Ручное ударение (`молок+о`) сохраняется **по словам**, а не отменяет акцентуацию всей реплики,
как было раньше. Слова с `+` уходят в модель дословно, а остальной текст всё равно отдаётся
RUAccent — причём промежутками между размеченными словами, а не по одному слову: на одиночных
словах модель ошибается чаще, чем на фразе. Так одна запись словаря с ударением больше не
лишает ударений всю реплику. Если размечено каждое слово, RUAccent вообще не поднимается.

Словарь произношения (вкладка `04`) ставит ударения тем же способом: в замене пишется
`звонит → звон+ит`. Правило применяется **до** RUAccent, поэтому ручная разметка из словаря
побеждает автоматическую — и только в своём слове.

Работает это **только для голосов на F5-TTS** — акцент-тюн обучен на размеченном тексте.
Для XTTS-голосов ударения не расставляются независимо от тумблера, а знак `+` из замены
словаря вырезается: иначе движок прочитал бы его как отдельный символ. Подсказка под списком
движка это показывает.

Состояние RUAccent видно в шапке: чип `ACCENTIZER` показывает `загружается` → `вкл`.
Если модель ударений не поднялась, чип показывает `ОШИБКА`, точка у `BACKEND` становится
розовой, а причина видна в подсказке при наведении на `BACKEND`. Синтез при этом продолжает
работать, но идёт **без ударений** — то есть тихое отключение ударений больше не выглядит как
ошибки модели. Размер модели омографов задаётся `TTS_OMOGRAPH_MODEL_SIZE`;
он влияет только на выбор варианта для слов-омографов (`зáмок`/`замóк`), остальные ударения
берутся из словаря.

### Текст до модели: числа, сокращения, латиница

Перед синтезом текст проходит общий для всех движков шаг нормализации
(`backend/text_normalization/`, точка входа — `normalize`), а уже потом (только у F5)
по нему идут ударения. Происходит это на каждой реплике, независимо
от того, каким движком она озвучивается, — цифры и сокращения оба движка читают плохо.
Порядок шагов важен и живёт в `pipeline.py`: сначала прячутся технические строки,
потом разбираются даты, время и деньги, и только в конце числа читаются «по остаточному
принципу». Так «12.05.2026» становится датой, а «1.2.3» остаётся версией.

- **Числа и согласование.** `2026` → «две тысячи двадцать шесть», а существительное после
  числа получает правильную форму: `2 км` → «два километра», `5 км` → «пять километров»,
  `21 рубль` → «двадцать один рубль», `22 рубля` → «двадцать два рубля», `25 рублей` →
  «двадцать пять рублей». Форма выбирается правилом по последним двум цифрам (1 / 2–4 /
  остальное), без морфологического разбора. Нерегулярные пары вроде «год/года/лет» лежат
  таблицей. Если слова нет в таблице единиц, число всё равно читается, а слово остаётся
  как было: `2 яблока` → «два яблока», а не выдуманное «два яблок».
- **Даты.** Числовая и словесная записи читаются одинаково: `12.05.2026`, `12/05/2026` и
  «12 мая 2026 года» → «двенадцатое мая две тысячи двадцать шестого года». Порядок всегда
  день → месяц → год, поэтому слэш и точка равнозначны, а «12/05» не превращается в
  пятое декабря. Невалидная дата (`32.13.2026`, `31.02.2026`) не трогается: прочитать её
  наугад хуже, чем оставить как есть.
- **Время.** `12:30` → «двенадцать часов тридцать минут», `12:00` → «двенадцать часов»,
  `00:05` → «ноль часов пять минут». Нулевые минуты не читаются совсем — «ноль минут» в
  речи звучит неестественно; во всём остальном минуты читаются и согласуются
  (`12:01` → «двенадцать часов одна минута»). Главное — время не распадается на два
  независимых числа.
- **Деньги и проценты.** `25 руб.` и `25 ₽` → «двадцать пять рублей», `5 коп.` → «пять
  копеек», `$5` и `5$` → «пять долларов», `€5` → «пять евро» (евро не склоняется).
  `5%` → «пять процентов», `1%` → «один процент», `2,5%` → «две целых пять десятых
  процента». Дроби остаются на `num2words`: `1,5` → «одна целая пять десятых».
- **Диапазоны.** `5–10 км`, `5-10 км` и `5 — 10 км` читаются одной конструкцией
  «от … до …»: «от пяти до десяти километров». Диапазон лет — «2020–2025 годы» →
  «от две тысячи двадцатого до две тысячи двадцать пятого года».
- **Римские числа и №.** `XXI век` → «двадцать первый век», падеж задаёт слово рядом
  (`в XXI веке` → «в двадцать первом веке»). Римские числа разбираются до латиницы, иначе
  «XXI» ушло бы в чтение по буквам. `№ 15` → «номер пятнадцать»; решётка `#` знаком номера
  не считается и остаётся как есть.
- **Сокращения.** «т.е.» → «то есть», «руб.» → «рублей», «ул.» → «улица» и т.п. Список
  закрытый (см. `abbreviations.py`), ищутся только как отдельные слова: «см» внутри «смех»
  — не сантиметры.
- **Латиница.** Аббревиатуры читаются словарём известных (`API` → «апи», `Python` →
  «питон»), незнакомые — по буквам (`GPU` → «джи-пи-ю»). Английские *слова* намеренно не
  транслитерируются: XTTS v2 многоязычная и читает их сама, а русская транскрипция только
  испортила бы произношение.
- **Технические строки защищаются.** URL, email, версии (`1.2.3`) и IP (`192.168.1.1`)
  уходят в модель без изменений — внутри них есть цифры и латиница, и любая нормализация
  там была бы разрушительной. Телефоны, наоборот, читаются цифра за цифрой:
  `+7 999 123-45-67` → «семь-девять-девять-…»; как количество такой номер был бы суммой
  в десятки миллиардов. Числа с ведущими нулями (`007`) не трогаются — это код, а не семь.

Чего шаг не делает: не разбирает морфологию по-настоящему. Падеж существительного зависит
только от числа, но не от предлога, поэтому «к 5 годам» останется «к пять годам» —
правильный ответ «к пяти годам» требует морфоразбора, которого в проекте нет. По той же
причине версия с одной точкой (`Python 3.11`) читается как дробь: отличить её от «3,14»
без контекста нельзя, а защищаются только цепочки от трёх групп (`1.2.3`). Если фраза
критична к падежу, напишите её словами сразу: готовый текст не переписывается.

### Восстановление буквы «ё»

«е» и «ё» — **разные символы** на входе модели, и ударение их не подменяет: если в тексте
физически стоит «е», никакой `+` не заставит модель произнести «ё». Русская типографика почти
всегда пишет «е» («ежик», «шел», «черный»), поэтому перед синтезом идёт отдельный
детерминированный шаг — `backend/text_normalization/yo_restoration.py`. Он встроен в
`pipeline.py` **после чисел и сокращений** (там уже готовые слова) и **до словаря
произношения**: явное правило пользователя обязано побеждать автоматику, как и в остальных
шагах.

Что меняется автоматически. Только **бесспорные** случаи, где «е» на месте «ё» — издательская
привычка, а не другое слово. Данные лежат в репозитории:
`backend/text_normalization/data/yo_safe.tsv.gz` — **106 298** пар вида `ежик → ёжик`, собранных
из открытого словаря проекта `eyo-kernel` (лицензия MIT; её текст — рядом, в
`data/LICENSE.eyo-kernel.txt`, и обязан сохраняться). Ключи записаны без «ё», значения — всегда
с «ё», в нижнем регистре; регистр исходного слова переносится на замену: `Ежик → Ёжик`,
`ЕЖИК → ЁЖИК`, `ежик → ёжик`.

Что **не** меняется автоматически. Настоящие неоднозначные пары («все/всё», «небо/нёбо»,
«пчелы/пчёлы», фамилии «Ежиков/Ёжиков») лежат отдельно —
`data/yo_ambiguous.tsv.gz`, **33 686** пар — и этим шагом не применяются **никогда**. Их
разрешает пользователь, и тем же механизмом, что и остальные кандидаты: через панель
«Предложения для словаря» (см. ниже). Подтверждённая пара — обычное правило
`pronunciation_entries`, отдельного поля или таблицы для неё нет.

Границы и безопасность:

- меняются **только целые слова** — границы заданы тем же явным классом символов, что и в
  `pronunciation.py` (кириллица, латиница, цифры), поэтому «ежик2» и «2ежик» не трогаются;
- слова с ручным `+` не трогаются вовсе: иначе разметка ударения разъехалась бы с текстом;
- URL, email, версии и IP к этому моменту уже спрятаны в плейсхолдеры, а английские слова и
  аббревиатуры остаются латиницей — шаг их не видит;
- слово, покрытое **включённым** правилом словаря, тоже не меняется: правило приоритетнее;
- шаг идемпотентен: в ключах словаря нет «ё», поэтому повторный проход ничего не находит.

Надёжность. Словарь грузится **лениво, один раз на процесс**, под блокировкой, и **никуда не
ходит по сети**. Если файла данных нет или он повреждён, шаг не падает: работает встроенный
список из полусотни самых частых слов (`ежик`, `шел`, `еще`, `черный`…), в лог уходит
однократное предупреждение, и синтез продолжается как обычно. Ошибка словаря «ё» не имеет
права уронить озвучку.

Видно в preview. В панели «Что услышит модель» восстановление «ё» — **отдельная стадия**
(`original → normalized → yo → dictionary → accented → final`), и по ней понятно, сработала она
или нет: если стадия равна нормализации, значит слов с гарантированной «ё» в тексте не
нашлось. Обещание «что услышит модель» держится конструкцией: и синтез, и preview считают
стадии **одним проходом** `normalize_stages`, а не двумя реализациями.

Взаимодействие с RUAccent — честно. RUAccent в своём `process_all` сам вызывает `_process_yo`:
для F5 с включёнными ударениями библиотека дополнительно ё-фицирует текст по своему словарю и
моделью омографов. Это не отменяет наш шаг и не дублирует его без пользы:

- наш шаг работает **для XTTS**, при **выключенных ударениях** и при **недоступном RUAccent** —
  во всех этих случаях `process_all` не вызывается вообще;
- он **виден в preview** отдельной стадией, а чужая ё-фикация внутри библиотеки — нет;
- правило пользователя остаётся приоритетнее: словарь применяется до RUAccent, и если он уже
  заменил слово, библиотека получит готовый текст.

Мы не трогаем частные API `ruaccent` и не подавляем его ё-фикацию: когда ударения включены,
работают оба механизма — сначала наш детерминированный, затем библиотечный.

### Словарь произношения

Нормализация угадывает чтение по правилам, а словарь произношения позволяет **сказать прямо**:
«вот это слово читай вот так». Он нужен там, где правило бессильно: имена, бренды, узкие
термины и ударения. Словарь **глобальный** — правило работает во всех проектах сразу, а не в
одном диалоге, и хранится в SQLite (`pronunciation_entries`) в `data/voice_syntez.db`.

Задаётся правило парой «источник → замена»:

```text
OpenAI       → оупен эй-ай
PostgreSQL   → постгрес
SQL          → эскьюэль
звонит        → звон+ит
```

Что важно про совпадение:

- **Целое слово по умолчанию** (`whole_word`). `SQL` заменится в «используем SQL», но не
  внутри `PostgreSQL` и не внутри `MySQL`. Границы заданы явным набором символов
  (кириллица, латиница, цифры), а не `\b`: у `\b` подчёркивание тоже считается буквой, и на
  стыке алфавитов он ведёт себя неочевидно. Если всё-таки нужно менять внутри слов,
  переключатель «только целое слово» снимается — тогда заменяется подстрока.
- **Регистр не важен по умолчанию** (`case_sensitive=0`): `sql`, `Sql` и `SQL` — одно правило.
  Включается переключателем «учитывать регистр», и тогда совпадёт только точная запись.
- **Несколько правил применяются по очереди**, длинный источник идёт раньше короткого. Иначе
  `OpenAI API` развалилось бы на `OpenAI` + `API`. Каждое следующее правило видит результат
  предыдущего, поэтому «калькулятор → SQL», а рядом «SQL → эскьюэль» прочитают слово полностью.
- **Спецсимволы экранируются**: `C++` и `a.b` — это буквально `C++` и `a.b`, а не шаблон.
- Правило **не трогает защищённые технические строки**: URL, email, версии и IP к моменту
  применения спрятаны в плейсхолдеры, и случайно переписать их словарь не может.
- Словарь применяется **после чисел и сокращений** (правило ловит «25 рублей», а не «25 руб.»),
  но **до шага латиницы** — поэтому `SQL` можно прочитать как «эскьюэль», хотя без словаря шаг
  латиницы прочитал бы его по буквам.

Ударения. Для F5 в замене можно писать знак `+` перед гласной (`звонит → звон+ит`) — это
ручная разметка, и она применяется **раньше RUAccent**, поэтому автоматика её не переписывает,
а остальной текст всё равно акцентируется. Движку без поддержки ударений (XTTS) знаки `+`
не отправляются: для него замена становится «совместимой» и уходит очищенной, иначе модель
прочитала бы `+` вслух. `+` не перед гласной разметкой не считается и остаётся как есть.

Политика ошибок. Пустой источник, пустая замена, источник из одних пробелов, замена не строка
или непонятная запись — правило **пропускается с предупреждением в логе**, синтез продолжается
(одна кривая строка не должна рушить длинный рендер). Через API такое правило не создать:
400 с понятным текстом. Если правило с таким же источником и режимом регистра уже есть,
повторное добавление **обновляет** его (без дублей), а попытка правкой свести два правила в
один источник возвращает 409. Проверить правило без синтеза можно в панели «Проверить текст»
вкладки `04` — она показывает стадии обработки и сработавшие правила.

### Предложения для словаря

Словарь пополняется вручную, и это правильно: правило должно быть осознанным решением. Плохо
другое — искать неоднозначные слова каждый раз заново. Поэтому во вкладке `03` «Сплошной
текст» есть панель `06` «Предложения для словаря» с кнопкой «Найти слова для словаря»:
приложение само находит в тексте слова, которые стоит уточнить, и предлагает их один раз.

Кандидаты считаются **тем же путём**, что и preview: нормализация → восстановление «ё» →
словарь → акцентуация. То есть ищутся они по фактическому тексту, который уйдёт в модель, а не
по сырому исходнику, — иначе кандидаты расходились бы с тем, что реально услышит модель.
Ничего при этом не пишется в базу и не синтезируется.

Источники кандидатов:

- **`yo_homograph`** — неоднозначные «е/ё» из `data/yo_ambiguous.tsv.gz`. Предлагается вариант
  с «ё» (`все → всё`), альтернатива — «оставить как есть». Автоматически такие пары не
  меняются никогда, решает пользователь.
- **`stress_homograph`** — омографы ударения (`за+мок/замо+к`) из словаря установленной
  библиотеки `ruaccent` (`ruaccent/dictionary/omographs.json.gz`, 19 741 слово). Предлагается
  тот вариант, который **реально выбрал RUAccent** (он виден в акцентированном тексте),
  альтернативы — остальные. Файл только **читается на месте**: его лицензия
  (CC BY-NC-ND) запрещает копирование и производные, поэтому в репозиторий из него не
  попадает ничего. Нет библиотеки или файла — источник просто пропускается.
  Уверенность по ударению здесь не используется намеренно: `ruaccent` считает вероятности
  внутри (`OmographModel.classify`, `AccentModel.put_accent`), но наружу отдаёт только
  выбранный вариант — per-word `score` у ударений не получить, и подделывать его мы не стали.
  Поэтому «неуверенные» слова ударения определяются по курируемому списку омографов, а не по
  числу: список омографов и есть те слова, где выбор неочевиден.
- **`yo_low_confidence`** — предсказания модели ё-омографов RUAccent там, где она **сама
  отдаёт `score`** и не уверена (ниже порога). Модель недоступна, не поднята или не отдаёт
  уверенность — источник пропускается, а не получает выдуманный `score`.
- **`rare`** — консервативный эвристический fallback: длинные слова (от 12 знаков), которых
  нет ни в одном из списков. Идут **последними**, и замена у них пустая: угадывать ударение за
  пользователя нельзя, он вписывает его сам.

Слово не предлагается, если оно уже покрыто правилом словаря по той же проверке целого слова,
что и замена. Проверяются **и выключенные** правила — это и есть память об отклонённом
предложении, иначе одно и то же слово возвращалось бы в панель на каждом новом тексте.
Отсеиваются также слова без кириллицы, слова с ручным `+`, слова, уже содержащие «ё», и
дубликаты. Порядок — сначала ё-омографы, затем омографы ударения, затем редкие; внутри —
по позиции в тексте. Список ограничен (20 кандидатов).

**Две области словаря.** Правило можно принять только для проекта или для всех проектов
сразу — и это часть решения, а не деталь. Омограф почти всегда зависит от контекста: «замок» в
одном диалоге и «замок» в другом читаются по-разному, и правило, уехавшее во все будущие тексты,
сломало бы там другое чтение. Термины и бренды наоборот читаются одинаково везде — им место в
общем словаре.

Приоритет: **правило проекта → глобальное правило → автоматика**. Правила применяются в этом
порядке (внутри каждой области — длинный источник раньше короткого), поэтому проектное правило
для того же слова побеждает глобальное. Важное следствие порядка: глобальное правило видит
**результат** проектного, а не исходный текст. Если замена проекта сама содержит слово из
глобального правила, сработают оба — это порядок применения, а не нарушение приоритета.

Хранятся области в разных таблицах (`pronunciation_entries` и
`project_pronunciation_entries`), поэтому одинаковые идентификаторы правил в них не конфликтуют,
а уникальность источника внутри области сохраняется.

Поток подтверждения — **без нового хранилища**:

1. **Подтверждение для проекта** — `POST /api/projects/{id}/pronunciation/review` с
   `scope: project` (кнопка «Только в этот проект»): правило действует в этом диалоге и не
   меняет другие. Замена в карточке **редактируется** до отправки.
2. **Подтверждение глобально** — тот же эндпоинт с `scope: global` (кнопка «Во все проекты»):
   правило попадает в общий словарь вкладки `04` и работает во всех будущих текстах.
3. **Пропуск** — тот же вызов с пустой заменой (`enabled: false`, заметка «пропущено при
   подготовке диалога»). Пропущенное слово больше **не предлагается** (фильтр смотрит и на
   выключенные правила), но и **не влияет на синтез**; на вкладке `04` оно видно как выключенное
   правило, и его можно включить.
4. После любого решения затронутые реплики пересчитываются — и только они: слово встретилось
   именно в них, а пересобирать весь проект из-за одного слова незачем.
5. **«Добавить все»** (вкладка `03`) добавляет кандидатов с непустой заменой; редкие слова без
   замены пропускаются с понятной подписью. После любого действия и словарь, и список предложений
   перечитываются.

Эндпоинт — `POST /api/pronunciation/suggestions` (тело `{text, engine?}`), ответ
`{candidates: [...], considered: N}`, где `considered` — сколько слов вообще просмотрено.
Он ничего не пишет, не синтезирует и не поднимает TTS-движок; RUAccent подняться может (он
один из источников), но его недоступность — не ошибка.

### Что услышит модель (preview)

Preprocessing незаметен: на входе «В 2026 году цена выросла на 5%.», а в модель уходит «В две
тысячи двадцать шестом году цена выросла на пять процентов.» — и узнать об этом можно было
только по готовому аудио, то есть уже после дорогого синтеза. Preview показывает путь текста по
стадиям **до** синтеза:

```text
Исходный текст        В 2026 году ежик прошел 5 км.
Нормализация          В две тысячи двадцать шестом году ежик прошел пять километров.
Восстановление ё      …бесспорные слова получают «ё» («ежик» → «ёжик»), или стадия не меняется
Словарь произношения  …здесь же видно, какие правила сработали и сколько раз
Ударения (RUAccent)   …только у движка, который понимает «+»
Итог: что услышит модель
```

Стадия «Восстановление ё» показывает, что сделал детерминированный шаг: если её текст равен
стадии нормализации, значит слов с гарантированной «ё» не нашлось, а неоднозначные «е/ё» этот
шаг не трогает намеренно — их уточняют в панели предложений (см. «Восстановление буквы «ё»»).

Панель «Что услышит модель» есть в двух вкладках сразу — `02` «Озвучка диалога» (рядом с
глобальными настройками) и `03` «Сплошной текст», — это один и тот же компонент, а не две
копии. У каждой реплики в визуальном редакторе добавлено действие «Что услышит модель»: оно
показывает стадии для текста и голоса **этой** реплики, включая её собственный голос поверх
голоса спикера. Тумблер ударений по умолчанию повторяет панель настроек: preview обязан
отвечать про текущие настройки, а не про собственные. Рядом с кнопкой «Показать» есть кнопка
**пример с «ё» — только для проверки**: она подставляет тестовую фразу с плотной «ё», на
которой сразу видно работу стадий нормализации и восстановления «ё». Это тестовые данные, а не
фраза для записи референса (см. «Фразы для начитки референса»).

Preview **не запускает синтез**: TTS-движок не создаётся и не грузится, в базу ничего не
пишется, исходный текст не меняется. `supports_accents` берётся из паспорта движка
(`ENGINE_INFOS`), а не из живой модели, поэтому проверка стоит миллисекунды и не занимает
память. Единственное исключение — RUAccent: он и есть предмет проверки. Если модель ударений
не поднялась, ответ всё равно 200, но рядом со стадией «Ударения» видно `accentizer.error`
(«RUAccent не поднялся: …»), а текст показан без ударений: молчаливое отсутствие ударений
выглядело бы как «так и надо».

Совпадение preview и синтеза обеспечено конструкцией, а не дисциплиной: обе стороны зовут одну
функцию `audio_pipeline.preview_text(...)`, и синтез берёт из неё только `final`. Двух
реализаций порядка шагов (нормализация → восстановление «ё» → словарь → RUAccent) в проекте
просто нет, поэтому показанное не может разойтись с тем, что реально получит модель. Стадии
считаются срезами **одного** прохода `normalize_stages`, а не повторными прогонами.

### Нарезка текста на куски

Длина куска выбирается в Панели 3 — «абзацы» (до 600 знаков, `TTS_MAX_REPLICA_CHARS`) или
«короткие фразы» (до 200 знаков). Подпись одна и та же в обеих вкладках («Нарезка на куски»)
и в параметре задачи (`chunk_strategy`): это одна настройка, а не два режима. Режется всегда
**по границам предложений и абзацев**,
а не по счётчику символов: движок синтезирует каждый кусок с нуля и не помнит предыдущие,
поэтому обрыв внутри фразы даёт сброс интонации посреди мысли. Короткий кусок ровнее по
интонации, длинный — реже рвёт мысль, но внутри него интонация успевает «уплыть».
Отдельно это лимит и для реплик диалога: реплика длиннее выбранного лимита разрезается,
её части читает тот же голос с теми же параметрами.

### Почему режимы звучат по-разному

«Сплошной текст», «Озвучка диалога» и рендер проекта — это три входа в **один** пайплайн:
все они сходятся в `audio_pipeline.render_dialogue`, а текст до модели проходит один и тот же
preprocessing — нормализация → восстановление «ё» → словарь произношения → ударения. Отдельного
«диалогового» препроцессинга или второго пути к движку нет: и синтез, и preview зовут одну
`preview_text`, поэтому «что услышит модель» не может разойтись с тем, что реально уходит в
`synthesize()`.

Отсюда следствие, которое легко проверить: при одинаковом тексте, голосе, движке и настройках
кусок читается одними и теми же параметрами — текст, `speed`, ручки движка, `target_rms`,
`gain_db`, `pitch`, пауза и референс. На границе `engine.synthesize()` это видно буквально:
совпадают `text`, `speed`, `params` (включая сид) и `ref_audio_path` + `ref_text`. Это закреплено
parity-тестами `tests/test_dialogue_continuous_parity.py`: заглушка-шпион записывает фактические
вызовы движка, и тесты сравнивают именно их, а не тела ответов API. То же подтверждает живой A/B
на весах F5 (артефакты для прослушивания — в `output/parity-ab/`, замеры — в
`output/parity-ab/README.txt`): при одном и том же состоянии RNG «Сплошной текст» и «Озвучка
диалога» дали побитово идентичные файлы, а повтор одного режима — тем более.

**Реальная причина разницы на слух — недетерминированность F5-TTS, а не дефект диалога.**
Сид выбирается случайно на каждый кусок (`random.randrange(config.SEED_MAX)` в
`audio_pipeline._synthesize_chunk`), а пользователем не задаётся. Поэтому один и тот же текст в
**одном и том же** режиме каждый раз звучит иначе: в живом примере тот же текст с другим сидом
дал длительность 6.24 с против 5.22 с (≈20 %), корреляцию волны −0.04 и разницу спектров ~17 дБ.
Сравнивать два рендера «на слух» без закреплённого сида нельзя — это сравнение двух случайных
розыгрышей, а не двух режимов.

Что в режимах действительно различается **намеренно**:

- **Нарезка.** Диалог режет текст по репликам спикеров (а слишком длинную реплику — той же
  `split_into_chunks`), сплошной текст — по предложениям и абзацам. Для реплики, которая не
  превышает лимит, разбиение совпадает.
- **Паузы.** Диалог вставляет паузу перед каждой репликой (первая идёт без паузы), сплошной
  текст — между кусками нарезки. При одинаковом тексте, разбитом на реплики разных спикеров,
  число пауз поэтому разное. Это семантика режима, а не потеря качества.

Что с этим делать практически:

- **Перегенерировать неудачную реплику и выбирать take** — история вариантов для этого и нужна:
  «перегенерировать» сохраняет прежнее звучание вариантом, а не затирает его.
- **Смотреть диагностику take'а** (клиппинг, тишина, LUFS, длительность, WER) — она объясняет
  техническую причину, почему конкретный кусок звучит плохо.
- **Для честного A/B закреплять сид.** Сид каждого куска сохраняется в take (и виден в карточке
  как «сид …»), поэтому два варианта можно сравнить при одинаковом сиде — тогда разница будет
  разницей настроек или текста, а не броском RNG.

### Обязательная подготовка диалога

Раньше текст готовился к синтезу только в момент синтеза: нажимаешь «Сгенерировать» — и уже
внутри задачи выясняется, что в реплике есть неоднозначное «е/ё» или слово с плавающим
ударением. Увидеть это заранее было нечем, а сравнить два прогона — не с чем: подготовленный
текст нигде не сохранялся. Теперь подготовка отделена от синтеза и **фиксируется**.

Порядок работы во вкладке «Озвучка диалога»:

```text
текст (вставлен или из файла)
  → Применить и разобрать      (структура: спикеры, слоты, реплики)
  → Анализировать диалог       (текст: нормализация → «ё» → словарь → ударения)
  → Слова для проверки         (подтвердить или пропустить неоднозначное)
  → Сгенерировать              (только когда состояние «готов»)
```

Состояния подготовки видны в Панели 1 рядом с кнопкой анализа:

| Состояние | Что значит | Синтез |
|---|---|---|
| `не подготовлен` | анализ ещё не запускали или текст/голос/словарь изменились | запрещён |
| `анализируется` | анализ идёт прямо сейчас | запрещён |
| `нужно подтверждение` | найдены слова, которые нельзя решать за пользователя | запрещён |
| `готов` | у каждой реплики есть итоговый текст | разрешён |
| `ошибка анализа` | подготовить реплики не удалось (причина рядом) | запрещён |

**Запрет держит сервер, а не кнопка.** Прямой `POST /api/projects/{id}/render` по
неподготовленному проекту возвращает **409** с причиной: «текст ещё не подготовлен», «найдены
слова, требующие подтверждения», «исходный текст изменён» и т. п. Погашенная кнопка — только
подсказка; обойти правило через API нельзя.

Что устаревает подготовку (и возвращает проект в «не подготовлен»):

- **правка исходного текста** — устаревают все реплики: разбор ещё и не выполнялся заново;
- **повторный разбор** — реплики пересоздаются, старые стадии к ним не относятся;
- **смена голоса или движка спикера** — устаревают реплики этого спикера: разметка ударений
  зависит от движка (F5 понимает «+», XTTS — нет);
- **правка текста или голоса одной реплики** — устаревает только она, остальные остаются
  готовыми: пересчитывать весь большой проект из-за одной строки незачем;
- **изменение словаря произношения** — устаревают реплики, в которых встретилось слово
  правила: правило меняет текст, уходящий в модель, и по прежнему словарю он уже неверен.
  Это касается и добавления, и правки, и удаления правила; проверяются только те проекты,
  которых правило может касаться (правило проекта — один, глобальное — все).

А вот ползунки синтеза (скорость, cfg, nfe, громкость, тембр) подготовку **не** сбрасывают:
они не меняют текст, и требовать из-за них повторный анализ было бы наказанием за движение
слайдера.

**Кандидаты в словарь.** Анализ показывает слова, которые нельзя разрешить молча:
неоднозначные «е/ё» («все/всё»), омографы ударения и редкие слова. Пока слово не подтверждено
(«Добавить в словарь») или не пропущено («Пропустить» — оставить как есть), проект не станет
готовым. Подтверждение добавляет обычное правило словаря и пересчитывает только затронутую
реплику; пропуск оставляет слово в покое и больше его не предлагает. Автоматически такие слова
не меняются никогда — см. «Восстановление буквы «ё»» и «Предложения для словаря».

**Рендер берёт сохранённый текст.** В модель уходит ровно тот `final_text`, который был получен
при анализе и показан в карточке реплики (раскрытие «Что услышит модель»). Если словарь или
ударения изменились после анализа, рендер это **не** подхватит — сначала нужен повторный анализ.
Так «что вижу» и «что слышу» не могут разойтись: то, что ушло в модель, всегда можно посмотреть
в карточке.

Stages каждой реплики лежат в базе (миграция 5): `normalized_text`, `yo_text`,
`dictionary_text`, `accentized_text`, `final_text`, а рядом — `analysis_status`, версия,
причина ошибки, сработавшие правила (`dictionary_matches`), кандидаты и эффективные параметры
движка. `source_text` — это существующее поле `text`: второй копии исходника нет, чтобы не
держать два расходящихся источника правды.

Анализ дешёвый: он не поднимает веса F5/XTTS и не зовёт Whisper (ударения — единственная
модель, которая может понадобиться). На диалоге из сотен реплик стадии считаются один раз на
реплику, а не дважды: поиск кандидатов получает уже посчитанные стадии.

### История вариантов реплики

F5-TTS недетерминирован: одна и та же реплика с теми же настройками каждый раз звучит немного
по-новому. Поэтому «перегенерировать» не должно означать «потерять то, что было» — сравнивать
новую версию было бы не с чем.

При первой перегенерации реплики её текущее звучание вырезается из готового файла и сохраняется
**вариантом** — отдельным файлом `output/{job_id}-r{номер}-{id}.wav`, который можно прослушать
и поставить обратно. Дальше у реплики копится список вариантов («исходный», «вариант 1»,
«вариант 2»…), в файле при этом всегда звучит ровно один из них — в списке он помечен «в файле».

- **Вариант — это готовое аудио, а не рецепт.** Поэтому возврат к прежнему звучанию мгновенный
  и не запускает синтез, а вариант с одинаковым сидом на MPS не обязан воспроизводиться
  побитово — повторный прогон не даёт гарантии того же результата.
- **У проекта вариант живёт в каталоге проекта** (`output/projects/{id}/r{номер}-{хэш}.wav`), а не
  рядом с транзитным `output/`: он не чистится по TTL и переживает перезапуск. Рядом с файлом
  сохраняются движок, сид и параметры, которыми он получен, — видно, чем версия отличается от
  соседней.
- **Варианты нормализуются одинаково.** Каждый вариант проходит тот же LUFS-проход и лимитер,
  что и трек: иначе выбор на слух превращался бы в сравнение громкости, а не голоса.
- **Хранится не больше `TTS_MAX_REPLICA_VARIANTS` (по умолчанию 3) вариантов на реплику.**
  Самый старый неактивный вытесняется вместе со своим файлом.
- **Сид генерации виден у каждой реплики** и у каждого варианта («сид 1234567890»). Он выбирается
  пайплайном для движков, которые его принимают (`supports_seed`: F5 — разброс инференса,
  XTTS — `torch.manual_seed`), уходит в модель и записывается рядом с куском. У движка без
  поддержка сида на месте сида стоит «без сида».

### Проверка качества синтеза (QA-цикл)

Выбор «Проверка качества реплик / кусков» в Панели 3 — в обеих вкладках — задаёт режим на задачу:
`off`, `smart` или `strict`. Режим приходит в `/api/generate`, `/api/render-text` и
`/api/projects/{id}/render` (поле `qa`) и хранится в настройках сборки проекта; переменной
окружения он не задаётся.

- **`strict` — прежнее поведение.** Каждый кусок после синтеза распознаётся тем же Whisper'ом, что
  проверяет референс, и сравнивается с текстом, который в него отправляли. Расхождение выше
  порога — кусок синтезируется заново, с подстройкой ручек движка; в файл попадает **лучшая по WER
  попытка**.
- **`smart` — сначала дешёвый отбор по самому аудио, и только подозрительные куски уходят в
  Whisper.** Отбор (`qa_screening.py`) не требует ни модели, ни отдельного процесса: он считает по
  waveform длину относительно текста, слишком короткий и слишком длинный результат, долю тишины,
  перегруз, уровень вне допустимого, пустой выход и подозрительные повторы участка
  (нормированная автокорреляция при сдвиге 0.4–2 с — так выглядит зацикленная модель). Куски, по
  которым ни одного признака не сработало, принимаются сразу, с `wer = null`. Границы отбора
  намеренно широкие: лишний запуск Whisper стоит времени, пропущенный брак — качества готового
  файла. Все числа — в `QA_SCREEN_*` ([config.py](backend/config.py)) с пояснением, почему выбрана
  каждая граница.
- **`off` — цикл не запускается вовсе**, отметки у реплик нет (`qa: null`); это дефолт.
- **Замеренная цена** (3 реплики, 16 с готового аудио, движок прогрет): `off` 30.0 с · `smart`
  28.5 с **без единого запуска Whisper** · `strict` 83.9 с (3 запуска) — **×2.9** к `smart`. То
  есть на чистом диалоге `smart` неотличим от `off` по времени, а `strict` стоит полного цикла.
  По памяти `strict` поднимает заполненность системы до ~86 % (порог `TTS_SYSTEM_MEM_THRESHOLD` —
  85 %), так что ожидание освобождения памяти между попытками — реальная ветка, а не теоретическая.
- **Цена `strict` — отдельный процесс на кусок.** Одна попытка — это полный синтез плюс процесс
  Whisper (~1.6 ГБ весов в unified-памяти; в RSS дочернего процесса видно лишь ~0.8 ГБ): на
  диалоге из 10+ реплик это кратно увеличивает и время, и нагрузку. В `smart` Whisper поднимается
  только на подозрительных кусках.
- **Порог строже референсного.** Референс сверяется на 60% совпавших слов (`MATCH_THRESHOLD`) —
  этого хватает, чтобы поймать «текст от другого файла». Для приёмки готового результата порог
  свой и много строже: `TTS_QA_WER_THRESHOLD` (0.15) — распознанное должно совпасть с исходным
  текстом почти дословно.
- **Цикл ограничен и попытками, и временем:** `TTS_QA_MAX_ATTEMPTS` (4) и `TTS_QA_BUDGET_SEC`
  (300 с на кусок). Останавливает то, что наступит раньше.
- **Подстройка — шаг, а не перебор вслепую.** За попытку `cfg_strength` растёт, температура XTTS
  падает, штраф за повторы растёт — всё в границах, объявленных паспортом движка, и от значения,
  которое реально ушло в модель.
- **Принятое без полной проверки видно.** Если цикл исчерпал бюджет или попытки, в файл идёт
  лучшая проверенная попытка, а у реплики появляется отметка: «⚠ WER 0.32 · время проверки
  вышло». Если расшифровка не удалась вовсе, кусок принимается с отметкой «расшифровка не
  удалась» — терять уже сгенерированное аудио ради формальности незачем. У реплик, прошедших
  порог, отметки нет: это норма, а не событие. Отдельная отметка есть у `smart`: сколько кусков
  прошли отбор без расшифровки и по каким причинам остальные сочтены подозрительными.
- **Проверка переиспользует историю вариантов.** Перегенерация реплики идёт через тот же цикл,
  а отметка хранится у каждого варианта отдельно — при выборе варианта к реплике возвращается
  именно его отметка.
- **Перед повтором очередь ждёт освобождения памяти** (`TTS_SYSTEM_MEM_THRESHOLD`) — так же, как
  перед взятием задачи: Whisper на каждой попытке поднимается заново.

### Диагностика take'а

WER отвечает не на каждый вопрос: кусок может быть распознан верно и всё равно звучать плохо.
Поэтому вместе с take'ом (`backend/take_quality.py`) сохраняются объективные измерения — те, что
видно в самом waveform и тексте, а не в модели:

- **WER** (если проверка шла) и **доля клиппинга** — сколько отсчётов упёрлось в потолок шкалы;
- **доля тишины** и **длительность** куска, **секунды на знак** (`duration_per_char`);
- **peak dBFS**, **RMS dBFS**, **LUFS** (интегрированная громкость, ITU-R BS.1770);
- **попытки QA**, **режим QA** и **причины дешёвого отбора** (те же коды, что у `qa_screening`).

Своих порогов у диагностики нет: длительность, тишина и уровень считаются по `QA_SCREEN_*`, а
перегруз — общим с референсом детектором (`CLIPPING_LEVEL`/`CLIPPING_MIN_RATIO`). Иначе
«подозрительный кусок» и «предупреждение у take'а» разошлись бы при первой же правке порога.
Метрики считаются по **подготовленному** куску — по тому, что реально попадёт в файл, а не по
сырому выходу модели: после выравнивания громкости часть дефектов уже неотличима от нормы.

- **Обычному пользователю показываются только предупреждения** — компактной строкой у take'а:
  «Обнаружен клиппинг», «Высокая доля тишины», «Необычно длинная реплика», «Реплика короче
  своего текста», «Слишком короткая реплика», «Низкий уровень» (и «Слишком высокий уровень»,
  если кусок перегружен по уровню).
- **Подробности лежат в раскрывающемся блоке «Диагностика»** у каждого take'а: WER, число знаков,
  длительность, секунды на знак, peak, RMS, LUFS, доли тишины и клиппинга, попытки и режим QA,
  причины отбора. Метрика, которой нет, не показывается пустой строкой — строки просто нет.
- **Система не выставляет автоматическую оценку естественности голоса.** Эти числа не
  сворачиваются в один «балл качества», и take'ы не ранжируются: LUFS, WER и доля тишины
  описывают разные вещи, а похожесть на живую речь ими не измеряется. Диагностика объясняет
  *техническую* причину («клиппинг», «много тишины»), но решение «этот вариант лучше» принимает
  человек на слух — ровно так же, как сравнение движков не выбирает победителя автоматически.
- **Метрики опциональны.** Куски короче 400 мс и цифровая тишина не имеют LUFS — там `null`
  (не `-inf` и не исключение); остальные поля тоже могут отсутствовать, и это норма. У take'ов,
  сохранённых до этой фазы, диагностики нет вовсе (`quality: null`) — карточка показывает их как
  раньше.
- **Хранение** — колонка `takes.quality` (JSON, миграция 4 в `backend/db/migrations.py`). Старые
  записи читаются как `null`: обратная совместимость обязательна.

### Прогресс и ETA (сколько ещё ждать)

Статус задачи показывает не только «реплика N из M», но и оценку остатка
(`backend/eta.py`):

```text
18 / 47 реплик, ≈ 2 мин 40 сек
```

Оценка **engine-aware**: она считается по плану рендера, а не по числу реплик. Для каждой
реплики известны её движок, длина текста, режим проверки и то, первая ли она для ещё не
поднятого движка, — поэтому диалог, где F5 и XTTS стоят вперемешку, оценивается по
составляющим, а не одним средним.

- **Статистика по каждому движку отдельно.** Копятся секунды инференса на знак текста
  (warm), стоимость холодного старта и множитель проверки по режимам `off`/`smart`/`strict`.
  Наблюдения одного движка не сдвигают оценку другого: XTTS в этом проекте заметно
  медленнее F5, и усреднять их вместе значило бы врать про оба.
- **Обновление — EWMA** (`EWMA_ALPHA = 0.3`): новое наблюдение подтягивает прежнее
  значение, а не переписывает историю одним случайным куском и не игнорирует её. Значения
  сходятся к наблюдаемым: чем больше кусков движка прошло, тем точнее оценка.
- **Холодный старт считается один раз на движок.** Загрузка модели (десятки секунд у XTTS)
  добавляется только первому куску движка, который ещё не поднят. Её фактическая
  длительность запоминается отдельно от скорости инференса и вычитается из времени того
  куска, на котором она случилась, — иначе «холодный» кусок выглядел бы медленным
  движком. Прогретый движок надбавки не получает.
- **Проверка качества — множитель, а не догадка.** Скорость движка учится только на кусках
  без проверки, а цена проверки живёт отдельно и по режимам: `strict` (Whisper на каждом
  куске) заметно дороже `off`, `smart` — только на подозрительных. Множитель выводится из
  фактических времён (`backend/eta.py`, константы `DEFAULT_QA_FACTOR`) и уточняется
  наблюдениями, поэтому «дороже» — проверяемое свойство, а не подобранное число.
- **Выполненная работа уменьшает остаток.** После каждого куска факт уходит в статистику, и
  `eta_sec` пересчитывается по оставшейся части плана; по завершении — `0`. Прежнее
  «среднее по длительности аудио × число реплик» убрано: одно число не различало ни движки,
  ни длину текста, ни cold start, ни QA.
- **Статистика живёт в процессе** и копится между задачами: второй рендер того же движка
  оценивается точнее первого. При отсутствии истории работают приблизительные дефолты по
  движкам (F5 быстрее XTTS, у каждого своя цена загрузки) — оценка остаётся конечной,
  положительной и разной для разных движков, но это именно прикидка до первых наблюдений.
- **Форматирование — на бэкенде.** `GET /api/jobs/{job_id}` отдаёт готовую строку `eta_text`
  («2 мин 40 сек», «1 ч 4 мин 12 сек»); русские формы числительных не дублируются в UI.
  Поле `eta_sec` осталось на месте — по нему считают старые клиенты.
- **ETA не бывает отрицательным**: пустой план — `0`, «осталось 0 кусков» — `0`, шум
  статистики не уводит оценку ниже нуля.

Фактические времена, на которых учится статистика, видны в нагрузочном тесте: фаза `qa`
сравнивает `off`/`smart`/`strict` на одном тексте, фаза `engines` — XTTS холодный и
прогретый плюс смешанный диалог F5 + XTTS (`tools/loadtest.py`).

`engine_params` — ручки движка, переопределяющие настройки голоса на одну задачу; объявленные
границы зажимаются, незнакомые ключи движок игнорирует. Пока задача пересинтезирует реплику
или ставит вариант, `status` остаётся прежним (`done`), а индекс занятой реплики лежит в
отдельном поле `regenerating_replica` (`null` в покое); при неудаче текст ошибки — в `regen_error`
(отмена пересборки тоже пишет туда `"Отменено"`, а сам рендер остаётся `done`).
Необязательное поле `background: true` у рендер-запросов (`/api/generate`, `/api/render-text`,
`/api/projects/{id}/render`) опускает задачу в приоритет 3: её пропустят вперёд прослушивание и
перегенерация. У задачи есть поле `cancel_requested` — `true` между запросом отмены и безопасной
точкой; статусы: `queued`, `processing`, `done`, `error`, `cancelled` (см. «Очередь и отмена»).
У реплики в `replicas` есть `seed` (текущее звучание) и `variants` — список
`{id, label, seed, duration_sec, active, quality, audio_url}`; выбор и постановка варианта идут через
ту же очередь, что и синтез, поэтому одновременно движутся только по одному. Поле `qa` —
итог проверки качества этого звучания (`{status, wer, attempts, mode, screening}`) или `null`,
если проверка не гонялась. Поле `quality` — диагностические метрики этого звучания
(`{duration_sec, chars, clipping, clipping_ratio, silence_ratio, duration_per_char, peak_dbfs,
rms_dbfs, lufs, wer, qa_attempts, qa_mode, screening_reasons, warnings}`) или `null`, если
метрик нет: так выглядят take'ы, сохранённые до появления диагностики. Каждое поле внутри
необязательно (`null` — «не измерено»); `warnings` — список `{code, text}` с русскими
формулировками, `screening_reasons` — коды причин `qa_screening`. Оценки естественности голоса
среди них нет: метрики не сворачиваются в балл и take'ы по ним не ранжируются (см.
«Диагностика take'а»). `quality` есть у take'ов проекта (`GET /api/projects/{id}`), у вариантов
задачи и у активного звучания реплики в `GET /api/jobs/{id}`. Режим задаётся строкой `qa: "off" | "smart" | "strict"` в
`/api/generate`, `/api/render-text` и `/api/projects/{id}/render`; в проекте он лежит среди
настроек сборки, поэтому незаданное поле в запросе сохранённый режим не сбрасывает. Старое
булево значение принимается как есть (`true` → `strict`, `false` → `off`), неизвестное — 422.
Числа цикла берутся из `TTS_QA_*`, границы отбора — из `QA_SCREEN_*`
(см. «Проверка качества синтеза»). У `smart` в `screening` видно, что решил отбор: `suspicious`
и причины (`empty`, `too_short`, `duration_short`, `duration_long`, `silence`, `clipping`,
`level`, `repeat`), а `wer` у принятого без расшифровки куска — `null`.

### Проекты против задач

Задача (`/api/generate`, `/api/render-text`) — разовая: файл готов, а её карточка живёт только
в памяти процесса и исчезает при перезапуске. **Проект** — сохраняемая сущность: исходный текст,
настройки сборки, назначенные голоса, разобранные реплики и варианты их звучания лежат в SQLite
(`data/voice_syntez.db`) и переживают перезапуск backend. Файлы кусков проекта пишутся отдельно
от транзитного `output/` — в `output/projects/{id}/` — и не удаляются по 24-часовому TTL.
У каждого take там же лежат `qa` (вердикт проверки) и `quality` (диагностические метрики,
колонка `takes.quality`, миграция 4); записи, сделанные до её появления, читаются с
`quality: null`.

Порядок работы: создать проект → положить текст → `PATCH` с назначением голосов спикерам →
`parse` → **`analyze`** → `render`. Разбор и состав реплик — отдельный шаг: правка текста не запускает синтез
сама по себе. Голоса, уже назначенные спикерам, при повторном `parse` сохраняются, а у реплик,
чей текст и спикер не менялись, остаются их варианты и выбранный take — правится одна строка,
а не весь диалог. Возвращает проект целиком каждый изменяющий запрос: интерфейсу не нужно
досбирать состояние из нескольких ответов.

**Синтез возможен только по подготовленному тексту.** Обязательный шаг `analyze` считает для
каждой реплики стадии подготовки (нормализация → восстановление «ё» → словарь произношения →
ударения) и сохраняет итог в `final_text`; рендер берёт именно его и ничего не пересчитывает.
Подробности — в разделе «Обязательная подготовка диалога».

Статусы проекта: `draft` → `rendering` → `rendered` (или `error` с текстом в `last_error`).
Статус `rendered` ставится после того, как куски записаны вариантами реплик: открытый следом
проект уже показывает этот рендер, а не пустую историю.

Правки реплик идут точечным `PATCH`: непришедшее поле значит «не трогать», а `null` — «вернуть
наследуемое у спикера» (голос, параметр, отдельную ручку движка). Ответ содержит только карточку
правленой реплики, поэтому смена голоса или скорости одной строки не задевает соседние —
сравнение вариантов на слух не должно пересобирать весь диалог. Параметры реплики ложатся поверх
карточки спикера, карточка спикера — поверх пресета голоса, пресет — поверх дефолтов движка
(см. «Иерархия настроек»), а `reset_overrides` разом снимает все правки строки.

В ответе у реплик и у спикеров есть `settings` — разрешённые значения вместе с источником
(`engine` / `voice` / `speaker` / `replica`) и значением, к которому вернёт сброс. По ним
интерфейс и подписывает, что унаследовано, а что задано здесь; своей копии правил склейки у
фронтенда нет.

В интерфейсе с проектом работает вкладка «Озвучка диалога»: Панель 1 — редактор реплик,
Панель 4 — сборка файла. `/api/generate` и `/api/render-text` остаются для разовых задач,
скриптов и нагрузочного теста.

## Контроль ресурсов

- Модель загружается **один раз** за жизнь процесса (singleton), не на каждый запрос. Движки
  поднимаются лениво — при первом голосе на этом движке, — и дальше остаются тёплыми в памяти.
- Очередь **одна на все движки**: один воркер, следующая задача не стартует, пока не закончится
  текущая, реплики внутри задачи синтезируются по одной — никакого параллельного инференса.
  Это верно и когда в диалоге смешаны голоса на F5 и XTTS: обе модели живут в одном процессе,
  просто реплики обходят их по очереди. Отдельного воркера и IPC для второго движка нет
  намеренно: два параллельных инференса упёрлись бы и в память, и в потолок потоков.
- Потолок потоков задаётся `TTS_THREAD_LIMIT` (по умолчанию 4): значение выставляется в
  `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `VECLIB_MAXIMUM_THREADS`,
  `NUMEXPR_NUM_THREADS` **до** первого импорта numpy/torch/librosa — `torch.set_num_threads()`
  такие пулы не ограничивает, они инициализируются по числу ядер. `TTS_TORCH_THREADS`
  переопределяет только `torch.set_num_threads()`.
- `run.sh` держит pidfile (`.voice_syntez.pid`) и не даёт запустить второй инстанс; при запуске
  в обход него приложение само проверяет занятость порта и падает с понятным сообщением.
- Каждый кусок синтеза ограничен по времени (`TTS_CHUNK_TIMEOUT_SEC`): зависший инференс
  переводит задачу в `error`, а не висит в `processing` вечно.
- Watchdog (`resource_guard.py`) следит за RSS процесса и при устойчивом превышении
  `TTS_MAX_RSS_MB` прерывает текущую задачу — сам процесс при этом не останавливается.
  **Оговорка:** на Apple Silicon память, выделенную моделями через Metal (MPS), psutil в RSS
  процесса не показывает — с двумя-тремя поднятыми движками RSS остаётся десятками мегабайт,
  тогда как реальный физический след процесса (`footprint`) измеряется гигабайтами. Поэтому
  этот лимит ловит буферы пайплайна и нативные аллокации, но не сами веса, и по факту
  не срабатывает. Практически значимая защита — проверка памяти системы ниже.
- Вторая, независимая проверка — **заполненность памяти всей системы** (порог `TTS_SYSTEM_MEM_THRESHOLD`,
  по умолчанию 85 %): она видит нагрузку чужих процессов и не зависит от того, как учтена
  память моделей. Проверяется **перед взятием задачи из очереди**, а не в фоновом watchdog'е:
  задача остаётся в `queued` с сообщением «Система перегружена: память занята на N% — ожидание»
  и берётся, когда память освободится. Так перегруженная система не получает сверху ещё и синтез.
- Ориентир по памяти на диске: F5-TTS ~1.4 ГБ, XTTS v2 базовая ~1.9 ГБ, banana-файнтюн ~5.2 ГБ.
  Без выгрузки поднятые движки остаются в памяти до конца жизни процесса, поэтому набор
  «F5 + обе XTTS» занимает порядка 8–9 ГБ физической памяти.
- **Выгрузка движка возвращает память без рестарта.** Ручной способ — кнопка «Выгрузить» во
  вкладке «Модели» или `POST /api/engines/{id}/unload`; обратно — «Загрузить» или
  `POST /api/engines/{id}/load`. Дополнительно работает выгрузка **по простою**:
  `TTS_ENGINE_IDLE_UNLOAD_MIN` (минуты, по умолчанию 15, `0` — выключено) — фоновая задача раз
  в минуту проверяет уже созданные движки и отпускает те, что не участвовали в синтезе дольше
  порога. Настройка читается в момент проверки, а не на импорте.
- **Когда выгрузка запрещена.** Выгрузить движок нельзя, пока он синтезирует (счётчик активных
  синтезов под локом, отказ `409`) и пока очередь занята — есть `queued`/`processing` задачи или
  идёт перегенерация реплики: модель, которая понадобится следующей реплике, выгружать незачем.
  Гонка «выгрузка против стартующей задачи» безопасна: `synthesize()` сам вызывает `load()`, если
  модели нет в памяти, поэтому худший исход — лишняя загрузка, а не падение. Ошибка выгрузки не
  роняет backend: она логируется, состояние движка остаётся согласованным, и его можно поднять
  или выгрузить снова.
- **Память после выгрузки действительно освобождается** (обнуляются ссылки на модель и латенты,
  затем `gc.collect()` и `torch.mps.empty_cache()`), но точные цифры по MPS не обещаются:
  `tools/memory_check.py` измеряет их на живых моделях, а на Apple Silicon счётчики torch и RSS
  расходятся. `/api/status` отдаёт best-effort `mps_memory` (`current_allocated_mb`,
  `driver_allocated_mb`) или `null`, если torch/MPS недоступны.
- **Замеры на живом сервисе** (18 ГБ, `mps`, оба движка прогреты — подробности в «Нагрузочном
  тесте»): холодный старт XTTS — 23.2 с на первую задачу, из них ~21 с занимает загрузка движка;
  на прогретом XTTS реплика прибавляет +7…9 с против +1.3…1.5 с у F5, то есть XTTS в 5-6 раз
  медленнее. RSS процесса во время такого прогона доходил до 4.2 ГБ (после прогона остаётся
  ~1.8 ГБ), а в режиме `strict` заполненность системной памяти доходила до 86 %:
  порог гарда при этом достигается, и следующая задача возьмётся из очереди не сразу.
- Распознавание референса идёт **в отдельном процессе** (`transcribe_worker.py`): Whisper
  large-v3-turbo в памяти тяжелее самой F5-TTS, и в общем процессе он упирался бы в лимит
  watchdog'а. Память воркера возвращается ОС сразу после расшифровки, а падение распознавания
  не уносит с собой модель синтеза.
- Дефолт `nfe_step=32` — максимум качества; если ноутбук греется, поставьте 16 в Панели 2.
- Аудио не держится в памяти после склейки — результат сразу пишется в `output/`; сами куски
  реплик держатся в памяти лишь до финальной склейки. Файлы старше `TTS_OUTPUT_TTL_HOURS`
  (по умолчанию 24 ч) удаляются при старте приложения.
- Жёсткого потолка памяти на уровне ОС нет: macOS отвергает `setrlimit` для `RLIMIT_AS`/
  `RLIMIT_DATA`/`RLIMIT_RSS` (`ValueError: current limit exceeds maximum limit`), а cgroups
  здесь недоступны. Поэтому единственный потолок памяти — watchdog `TTS_MAX_RSS_MB`, а
  `run.sh` дополнительно запускает процесс с пониженным приоритетом (`taskpolicy -c utility`).

## Очередь и отмена

Очередь приоритетная, но воркер по-прежнему **один**: приоритет меняет только порядок, в котором
задачи доходят до модели, а не число одновременных прогонов. Элемент очереди — `(priority, seq, task)`,
где `seq` — монотонный счётчик постановки: при равном приоритете порядок строгий FIFO.

| Приоритет | Что это | Точки входа |
|---|---|---|
| `0` | Прослушивание голоса | `POST /api/preview` |
| `1` | Перегенерация реплики | `/api/jobs/{id}/replicas/{index}/regenerate`, `/api/projects/{id}/replicas/{index}/regenerate` |
| `2` | Обычный рендер | `POST /api/generate`, `POST /api/render-text`, `POST /api/projects/{id}/render` |
| `3` | Фоновая работа | сравнение движков; рендер с `background: true` |

Длинный рендер больше не делает приложение неинтерактивным «на уровне очереди»: пока он считается,
поставленное следом прослушивание или пересинтез одной реплики уходят вперёд. Внутри одного
приоритета порядок не меняется — две реплики, поставленные подряд, синтезируются в том же порядке.

**Отмена** — `POST /api/jobs/{job_id}/cancel`. Поведение зависит от состояния:

- `queued` → задача сразу становится `cancelled` («Отменено до запуска»); воркер, достав её из
  очереди, пропускает её и **синтез не начинается вовсе**;
- `processing` → выставляется флаг `cancel_requested`, и задача прерывается **кооперативно** —
  на ближайшей безопасной точке: между репликами, между попытками QA-цикла или между движками
  в сравнении. Поток внутри вызова модели **не убивается**: небезопасно вырывать поток из
  инференса, а остановка на границе куска ничего не ломает и оставляет движок в согласованном
  состоянии. Пока задача не дошла до такой точки, она остаётся `processing` с
  `cancel_requested: true` — интерфейс показывает «останавливаю…»;
- `done` / `error` / `cancelled` → ничего не меняется: повторная отмена **идемпотентна** и не
  является ошибкой. Неизвестный id — 404 с текстом «Задача не найдена».

Отменённая задача **остаётся в реестре**: её видно через `GET /api/jobs/{job_id}` со статусом
`cancelled`, и она больше не считается занятостью — выгрузка движка (`/api/engines/{id}/unload`)
из-за неё не залипает.

**Частичный результат убирается.** Готовый файл задачи пишется только в самом конце, поэтому
недописанного трека не остаётся; если отмена пришлась на пересборку реплики, удаляются и
транзитные варианты куска, снятые этой задачей. **Данные проекта не портятся**: уже сохранённые
в SQLite и `output/projects/{id}/` варианты реплик остаются на месте, а статус проекта
возвращается в согласованное `draft` (а не остаётся «рендерится» навсегда). Отмена не портит и
следующую задачу: воркер выходит из неё в чистом состоянии (сброс текущей задачи и флага отмены),
и следующий рендер проходит целиком.

## Если что-то не работает

**Сначала — `./venv/bin/python tools/doctor.py`.** Инструмент одной командой проверяет Python и venv,
`ffmpeg`, наличие и размер моделей, свободное место, права на `data/` и `output/`, порт и замок,
путь проекта и MPS, а затем печатает, что именно не так и что с этим делать (см. «Диагностика
окружения»). Код возврата `1` означает, что есть проблемы. Если запуск вообще не доходит до
браузера, тот же отчёт покажет причину раньше, чем вывод лаунчера: `logs/voice_syntez.log`.

**Лаунчер не открывает браузер / окно терминала закрылось** — смотрите `logs/voice_syntez.log`:
там полный вывод backend. Частые причины: нет Python 3.11+ (`brew install python@3.11`), не
установились зависимости (нет сети к PyPI) или не скачаны веса моделей (см. ниже).

**`address already in use`** — порт занят. `run.sh` и `VOICE_SYNTEZ.command` ищут свободный порт
сами, начиная с 8000 (или с `PORT`), и печатают выбранный в консоль.

**«Приложение уже запущено (PID …)»** — сработал pidfile-лок `run.sh`. Остановите первый процесс
или удалите `.voice_syntez.pid`, если он остался от упавшего приложения. При запуске напрямую
(`uvicorn backend.main:app`) приложение само проверяет порт и не стартует вторым инстансом.

**Задача зависла в `processing`** — через `TTS_CHUNK_TIMEOUT_SEC` (по умолчанию 10 минут) она
перейдёт в `error` с текстом про таймаут, в логе будет WARNING с текстом проблемной реплики.
Если задача прервана с «превышен лимит памяти» — сработал watchdog `TTS_MAX_RSS_MB`.

Таймаут пайплайна и ошибка самого движка различимы и **не подменяют друг друга**: если внутри
инференса упало собственное исключение движка (например, `Read timed out` в XTTS), задача падает
с настоящим типом и текстом ошибки, а в логе будет ERROR с именем класса исключения. Формулировка
«возможно, завис инференс» означает ровно одно — кусок действительно не уложился в лимит.

**У карточки голоса жёлтый бейдж `⚠ проверьте пол`** — измеренный F0 записи не сходится
с выбранным полом (мужской ≈ 85–155 Гц, женский ≈ 165–255 Гц): например, референс размечен
как женский, а звучит мужским. Загрузку это не блокирует, но синтез унаследует тембр записи,
а не подписи. Пометьте пол верно или загрузите подходящий референс.

**У карточки голоса жёлтый бейдж `⚠ узкая полоса`** — в референсе почти нет верха: уровень
полосы 7–11 кГц ниже −28 дБ относительно ядра речи (300–3400 Гц). Так выглядят записи через
телефонный кодек и сильно сжатые mp3: срезанный верх уходит в тембр, и синтез звучит глухо.
Настройками это не исправляется — запишите референс заново в полной полосе.

**К кнопке «Прослушать» не приходит аудио** — текст ошибки теперь показывается рядом с самой
кнопкой (в том числе `Failed to fetch` при недоступном бэкенде). Если бэкенд не запущен,
чип `BACKEND` в шапке покажет `нет связи`, а точка станет розовой.

**У карточки голоса жёлтый бейдж `⚠ расшифровка`** — текст из поля «Что сказано в референсе»
почти не совпал с тем, что распознано в записи (порог — 60 % слов). Обычно это значит, что
вставлена фраза от другого файла. Наведите курсор на бейдж: в подсказке будет распознанный
текст. Пересоздайте голос с верной расшифровкой (проще всего кнопкой «распознать») — с
несовпадающим `ref_text` F5-TTS тянет длительность и выдаёт невнятную речь.

**API ответил `Не назначен голос для: «Слот N»`** — в задаче есть голос, которому не передан
`voice_id`. Через интерфейс это не воспроизводится: панель голосов следует за текстом, а
«Сгенерировать» неактивна, пока каждому голосу не назначен свой. Ошибка приходит при вызове
`/api/generate` напрямую — добавьте недостающие ключи в `speakers`.

**Долго грузится / «загружаю модель…»** — первый старт скачивает веса (~1.4 ГБ) и вокодер.
Дальше загрузка ~15 с. XTTS грузится отдельно и позже — при первом голосе на этом движке
(в чипе `ENGINE` — `XTTS загружается`, в логе видно путь к чекпоинту); это ещё ~20 с.

**Чип `ENGINE` показывает `ОШИБКА`, задачи на этом движке падают** — смотрите текст ошибки в
подсказке при наведении на `BACKEND`. Типовые причины: не скачаны веса XTTS (`Веса XTTS не найдены в …
нужны model.pth и config.json` — скачайте их кнопкой во вкладке `05` «Модели» или вручную,
см. раздел про веса XTTS)
или несовместимость `coqui-tts` с установленным `transformers` (в `engines/xtts_engine.py`
для этого есть шим `isin_mps_friendly`, в логе будет строка про его включение). F5-TTS
и остальные движки при этом продолжают работать — падает только проблемный.

**Задача долго стоит в `queued` с сообщением «Система перегружена: память занята на N%»** —
сработала проверка памяти перед стартом. Так приложение не добавляет нагрузку поверх уже
загруженной системы; задача возьмётся сама, когда память освободится. Если это повторяется
постоянно, закройте тяжёлые приложения либо поднимите порог `TTS_SYSTEM_MEM_THRESHOLD`.

**XTTS-голос читает с неправильными ударениями** — XTTS не понимает разметку ударений, которую
ставит RUAccent (для него `+` — обычный токен), поэтому ударения в XTTS-голосах не расставляются
вовсе. Если слово читается неверно, попробуйте другой движок (`f5`) или подберите голос/референс.

**Чип `ACCENTIZER` показывает `ОШИБКА`, точка у `BACKEND` розовая** — RUAccent не поднялся (обычно
нет сети при первом запуске или не скачались его модели). Синтез продолжает работать, но
**без ударений**; причина видна в подсказке при наведении на `BACKEND`. Повторная попытка — не
чаще раза в минуту, перезапуск сервера пробует снова сразу.

**В логе `MPS упал (...), перезагружаю модель на CPU`** — часть операций на Metal не
поддерживается, приложение автоматически повторяет синтез на CPU (медленнее, но работает).

**Голос звучит не так, как в референсе** — референс должен быть чистым (без музыки и шума),
5–15 секунд, один говорящий. Расшифровка `ref_text` должна совпадать с записью дословно —
за этим следит проверка при сохранении голоса (бейдж `⚠ расшифровка`). Для русского текста
всегда включайте автоударения: без них акцент-тюн F5 не работает как задумано.

## Что не входит в проект

- Стриминг в реальном времени — это офлайн-рендер диалога
- Авторизация и мультипользовательский режим — локальный инструмент на одного человека
- Облачный деплой — только localhost
- Автоопределение пола и эмоции по тексту — голос и параметры назначает пользователь
  (пол записи только измеряется и сверяется с подписью, см. бейдж `⚠ проверьте пол`)
- Управление кешем `huggingface_hub` (Whisper, вокодер Vocos): менеджер их показывает, но
  не скачивает и не удаляет — это делают сами библиотеки. Граница не изменилась и после
  появления очистки кеша приложения: та чистит **свои** транзитные файлы (`output/`,
  `output/benchmarks/`, временные файлы пайплайна) и не касается ни чужого кеша, ни весов —
  см. «Очистка кеша приложения»
