# Установка, запуск и окружение

Страница о том, как поставить TTS-дашборд на macOS, запустить его и убедиться, что окружение
готово к работе. Она нужна при первом развёртывании, после обновления зависимостей и при разборе
проблем с Python, ffmpeg, портом или памятью.

## Что устанавливается: движки синтеза

Движок выбирается **отдельно для каждого голоса** — не глобально на приложение. Один и тот же
текст может звучать разными моделями, и в одном диалоге допустимо смешивать голоса на разных
движках: файл всё равно соберётся один. Как устроен синтез и какие у движков ручки — на странице
[Синтез и движки](./synthesis.md).

| Движок | Что это | Ударения | Ручки |
|---|---|---|---|
| `f5` — **F5-TTS Russian** | [F5-TTS](https://github.com/SWivid/F5-TTS) + веса [Misha24-10/F5-TTS_RUSSIAN](https://huggingface.co/Misha24-10/F5-TTS_RUSSIAN) (`F5TTS_v1_Base_accent_tune` — обучен с полной разметкой ударений). Движок по умолчанию | да | CFG strength, NFE steps |
| `xtts` — **XTTS v2 (базовая)** | [Coqui XTTS v2](https://huggingface.co/coqui/XTTS-v2), многоязычная модель, клонирование по 6–15 с референса. Веса ~1.9 ГБ | нет | Температура, штраф за повторы |
| `xtts-banana` — **XTTS v2 + русский файнтюн** | [Ftfyhh/xttsv2_banana](https://huggingface.co/Ftfyhh/xttsv2_banana) — разговорный русский файнтюн базовой XTTS. Обучен преимущественно на женских голосах, поэтому мужские референсы на нём звучат менее предсказуемо | нет | Температура, штраф за повторы |
| `qwen3-tts` — **Qwen3-TTS 1.7B (Base)** | [Qwen3-TTS-12Hz-1.7B-Base](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-1.7B-Base) + [токенизатор 12 Гц](https://huggingface.co/Qwen/Qwen3-TTS-Tokenizer-12Hz). Клонирование по 3 с референса, десять языков. Веса ~4.5 ГБ + токенизатор ~0.4 ГБ. Требует отдельной установки пакета (см. ниже) | нет | Температура, top-p, штраф за повторы, потолок длины; режимы «черновик / качество / эксперимент» |
| `kokoro-ru` — **Kokoro-ru (встроенные голоса)** | Русский файнтюн [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) — [zaakirio/kokoro-ru](https://huggingface.co/zaakirio/kokoro-ru). 82 млн параметров, работает на CPU. Свои встроенные голоса (sveta, masha, dima), **референс не используется**, клонирования нет. Веса ~0.7 ГБ. Требует отдельной установки пакета (см. ниже) | нет | Своих ручек нет — только общий темп; режимы «черновик / качество / эксперимент» |

F5-TTS берёт из записи только первый фрагмент (до ~12 с), XTTS — до 30 с, Qwen3-TTS — 3–15 с
(столько просит карточка модели; короткая запись снижает схожесть, длинная не помогает).
Kokoro-ru не берёт из записи ничего: он говорит встроенным голосом, и референс нужен только
потому, что его требует карточка голоса (см. ниже). Расшифровка референсов — Whisper
(`openai/whisper-large-v3-turbo`), он же проверяет, что введённый текст действительно
соответствует записи.

Длинный текст XTTS режет на предложения сам, потому что у модели есть лимит на длину
входной фразы (для русского — 182 символа, у нас реплики бывают до 600). За это отвечает
spacy: coqui-tts его вызывает, но в зависимостях не объявляет, поэтому он прописан в
`requirements.txt` отдельно — без него любая XTTS-реплика длиннее 182 символов падала
с `ImportError: enable_text_splitting=True requires Spacy`.

Ударения расставляет [RUAccent](https://github.com/Den4ikAI/ruaccent) **только для F5**:
токенизатор XTTS кодирует знак `+` как отдельный токен, поэтому размеченный текст для него —
мусор. Для XTTS-голосов тумблер «автоударения» ни на что не влияет, текст уходит как есть.
Kokoro-ru обходится без пайплайна ударений: текст уходит в модель фонемами, а ударения и «ё»
расставляет произносительный словарь самого движка (`ru_g2p.py` — RUAccent, а в режиме
«черновик» — espeak-ng), поэтому тумблер автоударений на него тоже не влияет.

> **Лицензии.** Код F5-TTS — MIT, но его веса (включая русский файнтюн `Misha24-10/F5-TTS_RUSSIAN`)
> распространяются под **CC-BY-NC-4.0**: обучены на датасете Emilia и некоммерческие.
> Веса XTTS v2 — под **Coqui Public Model License (CPML)**, тоже некоммерческой. Веса
> Qwen3-TTS — под **Apache-2.0**, а веса Kokoro-ru — под **OpenRAIL** (разрешительная, с
> ограничениями на вредное применение), то есть обе коммерчески пригодны. Но проект целиком
> содержит и некоммерческие модели, поэтому годится для личного и исследовательского
> использования, а не для коммерческого продукта без отдельного согласования.

## Требования

- macOS на Apple Silicon (M1/M2/M3), ≥ 16 ГБ ОЗУ. Поднятые движки остаются в памяти до конца
  работы процесса: F5-TTS ~1.4 ГБ, XTTS базовая ~1.9 ГБ, banana-файнтюн ~5.2 ГБ, Qwen3-TTS
  ~4.5 ГБ, Kokoro-ru ~0.7 ГБ — то есть набор «все пять» занимает порядка 14 ГБ. Если памяти
  мало, используйте один-два движка: лишние выгружаются вручную или по простою.
- Python 3.11 (`brew install python@3.11`)
- ffmpeg (`brew install ffmpeg`) — нужен для MP3 и m4a/mp3-референсов

## Установка

```bash
python3.11 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Веса моделей скачиваются отдельно и по желанию: F5-TTS — сам при первом старте, остальные —
кнопкой «Скачать» во вкладке `06` «Модели» (см. [вкладки интерфейса](./guide-tabs.md)). Если веса
уже лежат на диске, приложение работает офлайн и вкладка нужна только для диагностики.

### Движок Qwen3-TTS (необязательно)

Веса Qwen3-TTS не входят в основной набор по размеру, а сам пакет `qwen-tts` — по версии
`transformers`: он объявляет `transformers==4.57.3`, тогда как проект проверен на 5.17.0
(на ней работают Whisper и coqui-tts). Обычная установка откатила бы пятую версию назад
и сломала их, поэтому пакет ставится **без зависимостей**, поверх шима в `qwen_engine.py`:

```bash
source venv/bin/activate
pip install --no-deps -r requirements-qwen.txt
```

Остальные зависимости пакета (`accelerate`, `einops`, `onnxruntime`, `librosa`, `torchaudio`,
`soundfile`) в окружении уже есть — их тянут f5-tts, coqui-tts и librosa, — поэтому `--no-deps`
ничего не ломает. Без установленного пакета движок не поднимается: в логе будет ошибка с этой
же командой, а голос на Qwen можно перенастроить на другой движок.

Веса скачиваются кнопкой «Скачать» во вкладке `06` «Модели» (две записи: `qwen3-tts-base`
и `qwen3-tts-tokenizer`) или вручную:

```
models/
├── qwen3_tts_base/          # Qwen/Qwen3-TTS-12Hz-1.7B-Base
│   ├── config.json
│   └── *.safetensors        # ~4.5 ГБ, шардами
└── qwen3_tts_tokenizer/     # Qwen/Qwen3-TTS-Tokenizer-12Hz
    ├── config.json
    └── *.safetensors        # ~0.4 ГБ
```

```bash
source venv/bin/activate
python -c "
from huggingface_hub import snapshot_download
snapshot_download('Qwen/Qwen3-TTS-12Hz-1.7B-Base', local_dir='models/qwen3_tts_base')
snapshot_download('Qwen/Qwen3-TTS-Tokenizer-12Hz', local_dir='models/qwen3_tts_tokenizer')
"
```

Движок сам ищет каталог с `config.json` и весами на любой глубине, поэтому перекладывать
скачанные файлы руками не нужно.

**Устройство.** Карточка модели документирует CUDA; MPS официально не заявлен. Движок выбирает
устройство сам (на Apple Silicon — MPS) и грузит веса в `bfloat16`, а если операция на MPS
падает — перезагружает модель на CPU и синтезирует кусок заново, а не теряет его. Аварийный
тормоз на всё время работы: `TTS_QWEN_FORCE_CPU=1` — тогда движок сразу работает на CPU.
Что именно получилось на вашей машине, отвечает проба:

```bash
./venv/bin/python tools/qwen_feasibility.py --plan                    # что будет проверено
./venv/bin/python tools/qwen_feasibility.py --ref /путь/к/речи.wav    # замер MPS против CPU
```

**Откат при отсутствии весов.** Пока веса не скачаны, голос, настроенный на Qwen3-TTS, не
роняет рендер: диалог синтезируется движком `f5`, а в лог пишется предупреждение с именем
голоса. Скачайте модель, чтобы услышать выбранное звучание. Такой же откат на `f5` объявлен у
Kokoro-ru; у остальных движков недоступность остаётся ошибкой, а не подменой голоса.

### Движок Kokoro-ru (необязательно)

Kokoro-ru — **пресетный** движок: он говорит встроенными голосами модели (sveta и masha —
женские, dima — мужской), а записанный референс не использует. Встроенный голос выбирается
автоматически по полу из карточки голоса: женский → sveta, мужской → dima, «другой» → masha.
Клонирования у модели нет, поэтому это черновой движок: он в разы быстрее остальных и не
зависит от качества записи, но и не повторяет тембр пользователя.

Официальный Kokoro-82M русского не поддерживает (восемь языков, ни одного славянского), поэтому
движок работает на файнтюне `zaakirio/kokoro-ru`.

Пакет `kokoro` ставится отдельно, но, в отличие от Qwen, **с зависимостями**: конфликтов версий
с основным набором нет, а объявленный им `misaki[en]` тянет `spacy`, `phonemizer-fork` и
`espeakng-loader` — их зовёт произносительный словарь репозитория.

```bash
source venv/bin/activate
pip install -r requirements-kokoro.txt
```

Веса скачиваются кнопкой «Скачать» во вкладке `06` «Модели» (запись `kokoro-ru`) — снимком
репозитория целиком, потому что состав файлов не сводится к двум именам, — или вручную:

```
models/
└── kokoro_ru/                  # zaakirio/kokoro-ru
    ├── config.json             # конфигурация KModel: словарь фонем и архитектура
    ├── kokoro-config.json      # словарь фонем для произносительного словаря
    ├── kokoro-ru-v2-base.pth   # чекпоинт женских голосов (sveta, masha)
    ├── kokoro-ru-v2-dima.pth   # чекпоинт мужского голоса (dima)
    ├── ru_g2p.py               # произносительный словарь: RUAccent + espeak-ng
    ├── espeak-data/ru_dict     # словарь espeak-ng, пересобранный под ударения
    └── voices/{sveta,masha,dima}.pt   # голосовые пакеты
```

```bash
source venv/bin/activate
python -c "
from huggingface_hub import snapshot_download
snapshot_download('zaakirio/kokoro-ru', local_dir='models/kokoro_ru')
"
```

Движок сам ищет каталог с `config.json` и остальными обязательными файлами на любой глубине,
поэтому перекладывать скачанное руками не нужно. Каталог `espeak-data/` обязателен: штатный
словарь espeak-ng игнорирует комбинирующий знак ударения, и ударения терялись бы молча.

**Устройство.** По умолчанию движок работает на CPU: 82 млн параметров синтезируются быстрее
реального времени и без GPU, а комплексные операции декодера на MPS поддержаны не везде — вне
CPU движок считает их вещественно. `TTS_KOKORO_DEVICE=mps` это разрешает явно, но проверялся
только CPU.

**Без референса.** Голос на Kokoro-ru всё равно создаётся с записью: карточка голоса в проекте
устроена так у всех движков, и запись нужна остальным. Kokoro-ru её не читает — при выборе этого
движка интерфейс прямо предупреждает, что референс не используется.

### Очистка референса (необязательно)

Если референсы пишутся в шумном помещении, можно поставить DeepFilterNet — тогда при
сохранении голоса появится тумблер «очистить запись от шума и реверба»:

```bash
source venv/bin/activate
pip install --no-deps -r requirements-denoise.txt
```

`--no-deps` здесь обязателен: пакет тянет `numpy<2.0` и `packaging<24.0` и откатил бы уже
проверенные версии из `requirements.txt`. Без установленного пакета тумблер просто погашен,
всё остальное работает как раньше.

### Веса F5-TTS

Веса скачиваются автоматически при первом старте (~1.4 ГБ) в `./models`:

```
models/
├── F5TTS_v1_Base/vocab.txt
└── F5TTS_v1_Base_accent_tune/model_last_inference.safetensors
```

Чтобы поставить их вручную (или заранее, до запуска) — но проще нажать «Скачать» во вкладке
`06` «Модели» (см. [вкладки интерфейса](./guide-tabs.md)):

```bash
source venv/bin/activate
python -c "
from huggingface_hub import hf_hub_download
for f in ['F5TTS_v1_Base_accent_tune/model_last_inference.safetensors', 'F5TTS_v1_Base/vocab.txt']:
    print(hf_hub_download('Misha24-10/F5-TTS_RUSSIAN', f, local_dir='models'))
"
```

Ещё один файл докачается при первом запуске — вокодер Vocos (`charactr/vocos-mel-24khz`, ~54 МБ)
в стандартный кэш Hugging Face. RUAccent также скачивает свои модели при первом использовании.
Whisper для расшифровки референса (`openai/whisper-large-v3-turbo`, ~1.6 ГБ) докачивается при
первом распознавании — то есть при первом сохранении голоса или нажатии «распознать».

### Веса XTTS v2

Веса XTTS **внутри задачи не подкачиваются**: подкачивать ~1.9 ГБ посреди синтеза нельзя,
поэтому без файлов движок не поднимется вовсе (в логе будет понятная ошибка с ожидаемым путём).
Поставить их заранее можно двумя способами — кнопкой «Скачать» во вкладке `06` «Модели»
(см. [вкладки интерфейса](./guide-tabs.md)) или вручную, командой из блока ниже.

```
models/
├── xtts_v2/                              # coqui/XTTS-v2 — базовая модель
│   ├── config.json
│   ├── model.pth                         # ~1.9 ГБ
│   ├── dvae.pth
│   ├── mel_stats.pth
│   ├── speakers_xtts.pth
│   └── vocab.json
└── xtts_v2_banana/model_banana/v2.0.2/   # Ftfyhh/xttsv2_banana — русский файнтюн
    ├── config.json
    ├── model.pth                         # ~5.2 ГБ
    └── speakers_xtts.pth
```

```bash
source venv/bin/activate
python -c "
from huggingface_hub import snapshot_download
snapshot_download('coqui/XTTS-v2', local_dir='models/xtts_v2')
snapshot_download('Ftfyhh/xttsv2_banana', local_dir='models/xtts_v2_banana')
"
```

Ручной запуск нужен только там, где дашборд недоступен (например, при первом развёртывании на
чистой машине): в остальных случаях то же самое делает вкладка «Модели» с прогрессом и ошибками.

У banana-файнтюна чекпоинт лежит в подпапке (`model_banana/v2.0.2`), и `huggingface_hub`
раскладывает репозиторий по своим путям — движок сам ищет в каталоге пару `config.json` +
`model.pth` на любой глубине, так что перекладывать файлы руками не нужно.

Веса поднимаются **лениво**: при старте приложения в фоне грузится только F5-TTS, а XTTS —
при первом голосе на этом движке (в шапке дашборда чип `ENGINE` показывает `XTTS загружается` →
`XTTS готов`). Обе модели остаются тёплыми в одном процессе, пока их не выгрузят вручную или по
простою (см. [эксплуатацию и контроль ресурсов](./operations.md)), а память под них считается в
лимите watchdog'а.

## Запуск

Самый простой способ — **двойной клик по `VOICE_SYNTEZ.command` в Finder** (то же самое:
`bash VOICE_SYNTEZ.command` в терминале). Специально готовить окружение не нужно: лаунчер сам
находит Python 3.11+, создаёт `venv`, ставит зависимости, запускает backend и открывает браузер.

Что происходит при **первом** запуске:

1. лаунчер определяет каталог проекта по своему пути (а не по текущему каталогу), поэтому
   корректно работает и из Finder, и из любого места терминала, в том числе если путь содержит
   пробелы или кириллицу;
2. ищет Python 3.11+ (`python3.11`, затем `python3`, затем `python`) и объясняет, что поставить,
   если его нет;
3. создаёт `venv` и ставит `requirements.txt` — сеть нужна только к PyPI; веса моделей лаунчер
   не трогает;
4. проверяет `ffmpeg` и предупреждает, если его нет (без него не работает MP3-экспорт), но не
   падает;
5. поднимает backend на свободном порту (`PORT=8010 bash VOICE_SYNTEZ.command` — начать поиск
   с 8010) и открывает браузер.

При **повторных** запусках зависимости не переустанавливаются: лаунчер сравнивает хеш
`requirements.txt` с сохранённым в `venv/.requirements.sha256` и ставит их только если файл
изменился. Если приложение уже запущено (замок `.voice_syntez.lock` или отвечающий
`/api/status`), второй инстанс не поднимается — лаунчер просто открывает браузер на уже
работающий сервер и говорит об этом.

**Логи.** Весь вывод backend пишется в `logs/voice_syntez.log` и одновременно показывается в окне
терминала, чтобы оно не выглядело зависшим, пока грузится модель. Файл дописывается между
запусками; каталог `logs/` в git не попадает.

**Остановка.** `Ctrl+C` в окне лаунчера — backend получает сигнал, завершает текущую задачу,
закрывает сокет и освобождает замок; процессов после этого не остаётся.

Старый способ тоже работает и никуда не делся — для тех, кто уже активировал venv и хочет
видеть вывод в консоли:

```bash
./run.sh
# Открыть http://localhost:8000
```

Порт по умолчанию 8000; если он занят (частый случай — на нём может слушать другой проект),
лаунчер и `run.sh` сами берут следующий свободный и печатают выбранный. При необходимости можно
запустить backend напрямую:

```bash
./venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Диагностика без запуска сервера: `bash VOICE_SYNTEZ.command --paths` печатает все пути, которыми
пользуется лаунчер (`PROJECT_DIR`, `VENV_PY`, `LAUNCHER_PY`, `LOG_FILE`, маркер зависимостей);
`bash VOICE_SYNTEZ.command --help` показывает краткую справку.

Модель грузится в фоне при старте — индикатор в шапке дашборда показывает готовность.

### Почему лёгкий лаунчер, а не упаковка Python-рантайма

Выбран **lightweight launcher**: он готовит venv и запускает тот же `uvicorn backend.main:app`,
что и `run.sh`, — просто без ручной активации окружения. Упаковка (PyInstaller и подобные) эту
задачу здесь ухудшает, а не решает:

- **размер и обновление.** torch, `f5-tts`, `coqui-tts` и `transformers` вместе весят десятки
  гигабайт; их запекание в один бинарь превращает каждое обновление зависимостей в новую
  многогигабайтную сборку, тогда как `pip install -r requirements.txt` обновляет только
  изменившееся;
- **MPS.** Metal-контекст и нативные библиотеки torch плохо переносят замороженный рантайм:
  PyInstaller не умеет надёжно собирать динамически подгружаемые `.dylib` и Metal-шейдеры, а
  отладка «почему MPS не поднялся» в собранном бинаре заметно дороже;
- **ffmpeg.** Это внешний бинарник, которым пользуются pydub и чтение референсов. Его всё равно
  пришлось бы либо тащить внутрь (и терять обновления), либо требовать отдельно — то есть
  «одного файла» не получается;
- **локальные модели и логи.** Веса (`models/`, кеш `huggingface_hub`) должны лежать рядом и
  обновляться независимо от кода; понятные текстовые логи в `logs/voice_syntez.log` полезнее
  «тихого» GUI-приложения.

Лаунчер при этом не скачивает ничего, кроме pip-зависимостей при первом запуске: backend остаётся
локальным, offline-first и без облачных требований.

## Диагностика окружения

`tools/doctor.py` — самопроверка одной командой: она отвечает, что настроено не так, **до** первого
синтеза. Модели при этом не поднимаются, сеть не трогается, запущенный дашборд не мешает.

```bash
./venv/bin/python tools/doctor.py            # человекочитаемый отчёт
./venv/bin/python tools/doctor.py --json     # тот же отчёт машинночитаемым JSON
```

Проверяется: версия Python и venv, актуальность зависимостей, `ffmpeg`, наличие и размер каждой
модели (через реестр `model_manager`), свободное место, права на запись в `data/` и `output/`,
состояние порта и замка единственного инстанса, пробелы/не-ASCII в пути проекта и доступность MPS
(best-effort). Каждый пункт — со статусом `ok`/`warn`/`ОШИБКА` и подсказкой, что делать.
**Код возврата: 0 — всё в порядке, 1 — есть проблемы.**
