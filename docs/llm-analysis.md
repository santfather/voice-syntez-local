# Лингвистический анализ локальной LLM

Проект умеет готовить русский текст к синтезу **до** движка: восстанавливать `ё`, различать
омографы по контексту, подсказывать чтение имён, топонимов, аббревиатур, чисел и латиницы.
Часть этой работы может взять на себя локальная LLM под управлением Ollama: она **предлагает
аннотации**, а не переписывает реплику.

Эта страница описывает benchmark, которым выбиралась модель, устройство анализатора, кеш
разборов, политику памяти и то, какие числа получены на сохранённых прогонах. Ollama —
**опциональная** зависимость: без неё TTS работает как раньше.

## Что делает LLM, а что нет

Анализатор возвращает только аннотации: участок исходной строки и предложение по нему. Он:

- **не возвращает текст** — в контракте ответа нет поля с новым текстом, а лишнее поле
  (например `final_text`) отвергает ответ целиком (`unknown_field`);
- **не доверяет своим границам** — benchmark показал, что модели находят нужное слово, но
  почти не считают символы, поэтому backend сам ищет `source` в тексте, а
  `span_start/span_end` использует только как подсказку;
- **не ставит ударения** — знак `+` от модели снимается (`markup_stripped`), ударения
  остаются за RUAccent и словарём произношения;
- **не пишет в словарь** — принятие предложения это явное действие человека (review);
- **не подменяет отказ успехом** — недоступная Ollama, таймаут, отсутствующая модель, мусор
  вместо JSON или блокировка по памяти дают `FAILED` с причиной.

`final_text` принадлежит детерминированному слою и engine adapter'у; LLM в него не пишет.
Подробности подготовки текста — в [text-pipeline.md](text-pipeline.md).

## Инфраструктура (`backend/llm/`)

- **`ollama_client.py`** — единственное место, где проект говорит с Ollama: HTTP API
  (`/api/version`, `/api/tags`, `/api/ps`, `/api/show`, `/api/chat`), таймауты, потоковый
  ответ, отмена, выгрузка модели (`keep_alive: 0`) с подтверждением по `/api/ps`. Адрес по
  умолчанию — `http://127.0.0.1:11434` (`TTS_OLLAMA_URL`), таймаут запроса 180 с
  (`TTS_OLLAMA_TIMEOUT_SEC`), health-запрос 3 с. Только стандартная библиотека
  (`urllib.request`): новая зависимость не добавлялась.
- **`schemas.py`** — контракт анализа: аннотации со `span_start/span_end`, `source`, типом,
  `meaning`, `suggested_form`, `confidence`, `needs_review`, `reason_code`; словари типов,
  классов реплики, речевых актов и эмоций; JSON-схема для Ollama (`analysis_json_schema()`) и
  валидация (границы, совпадение `source` с текстом, известные типы, отсутствие перекрытий).
  В схеме **нет поля для нового текста**: переписать реплику невозможно на уровне протокола.
- **`prompt.py` + `benchmarks/russian_linguistics/prompts/`** — версионный prompt: один и тот
  же текст для benchmark'а и для анализатора. Схема ответа подставляется плейсхолдером
  `{{schema}}` из того же `analysis_json_schema()`, по которому backend проверяет ответ,
  поэтому prompt и валидатор не могут разойтись. Файл prompt'а состоит из секций `[system]` и
  `[user]`, заголовка `# version:` и плейсхолдеров `{{schema}}` / `{{case}}`.
- **`versioning.py`** — паспорт прогона (версии benchmark/dataset/prompt/schema, git-коммит, ОС,
  чип, память, версия Ollama, тег и **digest** модели, контекст, temperature, seed) и сравнение
  с baseline.
- **`fake_client.py`** — подставной клиент для тестов и `--dry-run`: настоящие модели в обычном
  `pytest` не поднимаются.
- **`analyzer.py`**, **`integration.py`**, **`analysis_cache.py`**, **`scheduler.py`**,
  **`settings_store.py`**, **`metrics.py`**, **`runner.py`** — адаптер, встраивание в подготовку
  проекта, кеш, общий тяжёлый слот, настройки, метрики и прогон benchmark'а.

## Gold-корпус

Корпус лежит в `benchmarks/russian_linguistics/`:

- **`dataset.v1.jsonl` — 339 кейсов по 12 категориям**: `homograph` 40, `yo` 40, `morphology`
  24, `name` 30, `toponym` 25, `abbreviation` 30, `number` 30, `latin` 25, `term` 20,
  `dialogue_context` 25, `short_replica` 20, `no_issue` 30. Разметка написана руками (таблицами
  в `tools/build_llm_dataset.py`) и **никогда не порождается tested-моделью**: иначе benchmark
  измерял бы согласие модели с самой собой, а не качество.
- Границы каждого span считает генератор при сборке, поэтому `source` всегда посимвольно
  совпадает с текстом; `tools/build_llm_dataset.py --check` падает, если это перестало быть
  правдой, а `expected/summary.json` хранит сводку по категориям.
- **87 негативных кейсов** нужны для false positive rate: 30 в `no_issue` плюс намеренные
  «здесь `ё` не нужно» и «короткая реплика — правок нет» внутри своих категорий. Признак
  негатива — явный флаг `expect_no_issue`, а не пустой `expected` (иначе забытая разметка
  неотличима от пробы).
- **70 аннотаций помечены `needs_review`**, а 12 кейсов — флагом `ambiguous`: у редких фамилий,
  топонимов и опечаток-терминов произношение не выводится из контекста, и gold требует
  `needs_review` вместо уверенной правки. Спорные кейсы вынесены в `expected/summary.json` и
  `expected/review.md` для ревью человеком **до** полного прогона.
- Короткие реплики (`short_replica`) хранят контекст, но не правки: ожидаемый ответ — класс
  реплики (`CONFIRMATION`, `NEGATION`, `QUESTION`, …), а не переписанный текст.

## Метрики прогона

Метрики живут в `backend/llm/metrics.py`:

- **качество**: `homograph_accuracy`, `yo_precision/recall/f1`, `issue_precision/recall/f1`,
  `span_accuracy`, `utterance_accuracy`, `needs_review_precision`, `recovered_annotations`;
- **риск**: `false_positive_rate` (лишние правки на чистых текстах) и `critical_error_rate` —
  изменение смысла, уверенный неверный омограф, выдуманное имя/число/произношение, правка вне
  разрешённого span, ответ про чужую реплику, уверенный ответ там, где gold требует проверки, и
  невалидный JSON, который не спас даже повторный запрос;
- **надёжность протокола**: `valid_json_rate`, `schema_valid_rate`, `source_preservation_rate`;
- **ресурсы**: `latency_p50/p95/mean/max`, `tokens_per_second`, `peak_process_memory`,
  `peak_system_memory_percent`, `memory_pressure_events`.

Единого score нет намеренно: у моделей разный компромисс качества, скорости и памяти, и одна
свёртка спрятала бы именно то, ради чего benchmark делается. Омограф считается распознанным
только при верном **чтении** (по ключевым словам значения в gold), а не только по верному
месту: для TTS опасна именно уверенная неверная постановка. Чтение сравнивается по основам
слов, чтобы «строение» в gold совпадало со «строении» в ответе.

Каждый ответ оценивается отдельно (это же даёт `--repeat`): кейс без ответа — ноль по всем
метрикам, а не пропуск в отчёте. Схема ответа закрыта и на лишние поля: попытка вернуть
`final_text` или `normalized` отвергает ответ целиком (`unknown_field`).

## Версии и контракт

- **`SCHEMA_VERSION = "3"`** (`backend/llm/schemas.py`). Версия 2 добавила эмоцию и речевой акт,
  версия 3 — блок `prosody` (эмоция, рекомендуемый профиль, интенсивность, темп, уверенность).
- **`PROMPT_VERSION = "4"`** (`backend/llm/versioning.py`). Рабочий одиночный prompt —
  `analyzer.v4.txt` (`ANALYZER_PROMPT`), оконный для сцены — `analyzer.v5.txt`
  (`ANALYZER_WINDOW_PROMPT`). Версии v1–v3 оставлены на диске: по ним получены сохранённые
  benchmark-результаты, и удалять их значило бы сделать прошлые отчёты невоспроизводимыми.
- Ответ модели передаётся как `format="json"` + схема **текстом в prompt**. Грамматический
  режим (`format=<json schema>`) на этом корпусе ломал ответы qwen3: та же модель возвращала
  `items: []` при схеме в `format` и верную аннотацию при `format="json"`. Режим сохранён
  параметром `--response-format json|schema` и записывается в паспорт прогона.
- Словари (`EMOTION_VALUES`, `PROSODY_PACES`, `CONTEXT_DEPENDENCIES`, `ANNOTATION_TYPES`,
  `DIALOGUE_ACTS`) проверяются при разборе. Поля переписанного текста запрещены
  (`REWRITE_FIELDS`). Ошибки ответа кодируются машинно: `not_json`, `schema_version`,
  `unknown_type`, `span_bounds`, `source_mismatch`, `overlap`, `unknown_field`,
  `unknown_emotion`, `duplicate_replica` и другие.

Обе версии — prompt и схема — входят в ключ кеша, поэтому их смена автоматически инвалидирует
сохранённый разбор. Как интонация и профили связаны со схемой — в [prosody.md](prosody.md).

## Память и очередь

Машина здесь одна и известная: Apple Silicon с общей памятью, где LLM, TTS, Whisper и система
делят одни и те же страницы. Поэтому у LLM-задач отдельная политика, а не «пока не упадёт».

Пороги (`backend/llm/memory_policy.py`, значения по умолчанию; меняются переменными
окружения):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_MEMORY_NORMAL_MAX_PERCENT` | 70 | выше — режим роста: задача разрешена, событие логируется |
| `LLM_MEMORY_WARNING_PERCENT` | 75 | WARNING: новую тяжёлую задачу не запускать |
| `LLM_MEMORY_CRITICAL_PERCENT` | 82 | CRITICAL: новых задач не запускать, выгрузить неиспользуемые модели |
| `LLM_MEMORY_HARD_STOP_PERCENT` | 88 | HARD STOP: ничего не начинать, идущую работу прервать |
| `LLM_MEMORY_RESERVE_GB` | 4.0 | целевой резерв под macOS и UI |
| `LLM_MEMORY_RESERVE_MIN_GB` | 3.5 | жёсткий минимум свободной памяти |

Дополнительно проверяются давление памяти macOS (`kern.memorystatus_vm_pressure_level`: жёлтое —
не ниже WARNING, красное — HARD STOP) и то, влезает ли модель вместе с резервом. Давление
**важнее процента**: система может экономить память при формально низком проценте. «Не
начинать» и «прервать» — разные вещи (`must_abort_running`): процентный CRITICAL запрещает
новую работу, но идущий прогон не убивает, иначе замер посередине модели даст обрезанные
данные; прерывают только HARD STOP или исчерпанный абсолютный резерв. Если датчики не
прочитались, политика **не применяется**, но флаг `sensor_ok: false` остаётся в отчёте —
сломанная метрика не доказательство нехватки памяти.

Тяжёлые ресурсы не конкурируют: одновременно выполняется не более одной тяжёлой задачи
(`HeavyGate`: `HEAVY_LLM`, `HEAVY_TTS`, `HEAVY_WHISPER`), внешняя занятость (очередь синтеза)
подключается через `external_busy`. Лёгкие действия — API, UI, SQLite, детерминированная
подготовка текста — слот не занимают. `backend/llm/scheduler.py` сводит политику памяти и слот
вместе: `check()` отвечает «можно ли», `hold()` выдаёт слот и гарантированно возвращает его в
`finally` — при ошибке, таймауте и отмене тоже.

Важное различие путей: **у LLM-анализа ожидания нет** — если слот или память заняты, проход
завершается отказом (`HeavyBlockedError`) с причиной в `blocked_reason`, а не встаёт в очередь.
Очередь синтеза, наоборот, ждёт тяжёлый слот и память. Проход анализа проверяет память
**перед каждой репликой** и при HARD STOP останавливается с причиной, сохраняя уже полученные
разборы и выгружая модель.

## Запуск benchmark'а и артефакты

Прогон — одним CLI `tools/llm_benchmark.py`:

```bash
# верхняя граница без моделей и сети: проверяет gold, prompt, метрики и отчёты
./venv/bin/python tools/llm_benchmark.py --dry-run

# smoke на 15 кейсах: модели отвечают, память в норме, JSON стабилен
./venv/bin/python tools/llm_benchmark.py --smoke

# полный прогон четырёх обязательных моделей (с продолжением после сбоя)
./venv/bin/python tools/llm_benchmark.py --full --resume

# выбрать одну модель, категорию или ограничить объём
./venv/bin/python tools/llm_benchmark.py --model qwen3:8b --category yo,homograph --limit 40

# baseline для будущих сравнений: сохранить и потом сравнивать
./venv/bin/python tools/llm_benchmark.py --full --save-baseline --baseline-model qwen3:8b
./venv/bin/python tools/llm_benchmark.py --full --compare-baseline
```

Полный прогон, smoke и `--dry-run` пишут в разные подкаталоги
(`benchmarks/russian_linguistics/results/{full,smoke,dry-run}/`), поэтому smoke не портит
baseline. В каталоге модели — `raw.jsonl` (сырые ответы, они же состояние для `--resume`),
`metrics.json` (метрики + паспорт прогона) и `run.json` (версии, git-коммит, ОС, чип, память,
версия Ollama, тег и digest модели, контекст, temperature, seed); сводка по всем моделям —
`benchmark.json`. Код возврата неполного прогона (модель отсутствует, память запретила запуск,
HARD STOP) — 1, ошибки запуска — 2, поэтому автоматика не примет частичный прогон за полный.

`--dry-run` идёт через подставной клиент и **не поднимает моделей**: политика памяти к нему не
применяется, иначе проверка gold зависела бы от того, что ещё запущено на машине. Ответ
идеальной модели обязан давать ровно 100 % по всем метрикам — это проверка gold и метрик, а не
модели; тест `test_benchmark_dry_run_full_corpus_is_a_clean_upper_bound` прогоняет так весь
корпус (339 кейсов × 4 модели) и уже нашёл одну ошибку в gold.

Отчёт со всеми таблицами пересобирается из сохранённых результатов:

```bash
./venv/bin/python tools/llm_benchmark_report.py
```

Baseline лежит в `benchmarks/russian_linguistics/results/full/baseline.v1.json`, сравнение —
флаг `--compare-baseline`.

Кроме benchmark'а есть **живой smoke** анализатора — `tools/llm_analyzer_smoke.py`: он гоняет
настоящую модель по выборке gold-корпуса и складывает отчёты в `output/llm-smoke/`. Смысл
именно в живом прогоне: класс дефектов вида «модель выдумала код причины» (`unknown_reason`) на
подставном клиенте не воспроизводится, а на реальной модели воспроизвёлся с первого раза.
Сохранённые отчёты сняты на prompt v2 и схеме v1, поэтому как замер текущего контракта они не
годятся — это проверка пути «реплика → Ollama → валидация → кандидаты», а не benchmark.

## Сохранённый прогон и выбранные модели

Полный прогон выполнен на Apple M3 Pro (18 GB) по всем 339 кейсам каждой моделью, условия:
benchmark v1, dataset v1, **prompt v2 и schema v1**, `num_ctx = 8192`, `temperature = 0`,
`seed = 0`, Ollama 0.34.1. Артефакты — `benchmarks/russian_linguistics/results/full/`
(`benchmark.json`, `baseline.v1.json` и каталог на каждую модель).

| Модель | `issue_f1` | `critical_error_rate` | `false_positive_rate` | `latency_p50/p95`, с | пик памяти |
|---|---|---|---|---|---|
| `qwen3:8b` | **0.1928** | 0.3422 | 0.0115 | 2.6 / 22.0 | 86.0 % |
| `qwen3:4b-instruct-2507-q8_0` | 0.1538 | 0.3481 | 0 | 2.0 / 16.2 | 82.7 % |
| `qwen3:4b-instruct-2507-q4_K_M` | 0.1333 | 0.3628 | 0 | 1.3 / 10.9 | 79.3 % |
| `gemma3:4b` | 0.1304 | 0.8938 | 0.069 | 5.5 / 6.2 | 80.6 % |

**Важно про условия:** эти числа сняты на prompt v2 и схеме v1. Текущий код работает на prompt
v4 и схеме v3, поэтому таблица описывает именно сохранённый прогон, а не повторный замер на
текущем контракте. Выбор моделей в коде (`DEFAULT_PRIMARY_MODEL`, `DEFAULT_FALLBACK_MODEL`)
опирается на этот прогон.

- **Primary: `qwen3:8b`** — лучший `issue_f1` (18 совпавших аннотаций из 252 против 13
  у 4B-моделей) при сопоставимом риске. Цена: файл 4.87 GiB, загруженная модель 6.17 GiB,
  пик 86.0 %, p95 22 с.
- **Fallback: `qwen3:4b-instruct-2507-q8_0`** — та же полоса качества, что у `q4_K_M` (разница
  в один-два кейса), чуть надёжнее по схеме; `q4_K_M` — самый лёгкий вариант (2.33 GiB,
  p95 10.9 с), если памяти мало.
- **`gemma3:4b` не рекомендуется**: `critical_error_rate` 0.89 — она почти всегда уверенно
  ставит неверные границы и иногда придумывает `source`, которого нет в тексте.

Главный вывод прогона: **модели не умеют считать границы аннотаций**. Из 339 ответов каждой
модели точные границы дали лишь 18–28, тогда как слово найдено, но границы неверны, в
97–271 ответе. Значит, backend обязан искать слово в тексте сам, а `span_start/span_end` от
модели использовать только как подсказку — иначе почти каждый ответ будет отвергнут
валидатором. Второе наблюдение: у слабых моделей самый частый исход — пустой ответ
`items: []` (210 из 339 у `q4_K_M`), то есть провал по полноте, а не по точности.

## Память на практике

Файл модели — не её след в памяти. Замеры на Apple M3 Pro (18 GB) при контексте 8192:

| Модель | файл, GiB | загружено (`ollama ps`) | пик занятой памяти |
|---|---|---|---|
| `qwen3:4b-instruct-2507-q4_K_M` | 2.33 | ~3.6 GiB | 79.3 % |
| `gemma3:4b` | 3.11 | ~3.6 GiB | 80.6 % |
| `qwen3:4b-instruct-2507-q8_0` | 3.99 | ~5.2 GiB | 82.7 % |
| `qwen3:8b` | 4.87 | 6.17 GiB | 86.0 % |

Фактический след больше размера файла примерно в 1.3 раза из-за KV-кэша и накладных расходов,
поэтому проверять «влезает ли модель» по размеру из `/api/tags` недостаточно. После выгрузки
память возвращается полностью, но не мгновенно: `/api/ps` пуст раньше, чем macOS отдаёт
страницы, поэтому runner ждёт возврата памяти. Ответы моделей детерминированы
(`temperature = 0`, `seed = 0`): повторный прогон `qwen3:8b` дал те же метрики качества, а
разброс пика памяти (84.7 % → 86.0 %) — свойство машины, а не модели.

**Какую модель ставить рядом с дашбордом.** Дашборд прогревает F5 (~3–4 GB), и вместе с
пользовательскими приложениями на 18 GB остаётся 2–4 GB при жёлтом давлении macOS — под это не
проходит **ни одна** из четырёх моделей, и анализатор корректно отказывается запускаться, не
ослабляя guard. Поэтому:

- сначала анализ, потом синтез: перед анализом выгрузите движок
  (`POST /api/engines/{engine_id}/unload`), модель освобождается сама сразу после прохода
  (`unload_after`), и только затем идёт рендер;
- при типичной загрузке машины практичный primary — benchmark-approved
  `qwen3:4b-instruct-2507-q4_K_M` (2.33 GiB, ~3.6 GiB в памяти, p95 10.9 с) или `-q8_0`;
  `qwen3:8b` остаётся primary для «тихой» машины (~6.17 GiB, пик 86 %);
- пороги памяти не ослабляются ради прохождения задачи, и отказ анализа виден в интерфейсе
  как «ошибка» с причиной.

## Анализатор: встраивание и хранение

Анализ идёт **внутри** того же канонического прохода подготовки, что и раньше: сначала LLM
предлагает аннотации по репликам, затем детерминированный слой считает стадии, а кандидаты LLM
добавляются к словарным. Второго pipeline нет, и текст при этом не меняется ни в источнике, ни
в `final_text`.

- **Границы ищет backend.** `locate_annotations` находит `source` в тексте (ближайшее к
  подсказке вхождение, без учёта регистра), а несуществующее слово отбрасывает с причиной.
- **Ответ применяется целиком или не применяется.** Один ограниченный повтор (repair) с
  перечислением конкретных ошибок; факт повтора виден в разборе (`repaired`).
- **Сцена вместо строки.** `ProjectLlmAnalyzer.run(scene=True)` режет диалог `plan_windows`
  (`DEFAULT_SCENE_REPLICAS = 6`, `overlap = DEFAULT_CONTEXT_REPLICAS = 2`, шаг 4) — один
  запрос на окно, а не на реплику; ответ привязан к `replica_id`, неизвестный id отбрасывается.
  Сплошной текст идёт прежним путём — по одному фрагменту с `build_context` (±2 соседа, бюджет
  4000 символов), потому что его фрагменты не сцена с говорящими.
- **Кеш на сравнении входа.** Разбор действителен, только если совпали `source_text_hash`,
  `context_hash`, `dictionary_hash`, `model_digest`, `prompt_version`, `schema_version`.
  Правка соседней реплики делает устаревшим разбор соседа автоматически (в его контексте
  изменился текст), а явная инвалидация (`mark_stale`) метит реплику и по два соседа с каждой
  стороны, не удаляя историю. `FAILED` и повреждённый JSON из кеша не отдаются.
- **Хранение.** Миграция 7 создаёт таблицу `llm_analyses` (одна запись на реплику проекта,
  ключ `(project_id, replica_index)`, входные хеши, статус, модель, ошибка), миграция 8 —
  отдельную ось состояния анализа у проекта (`projects.llm_analysis_status/model/error/
  updated_at`). Обе аддитивные: старые базы обновляются, данные сохраняются.

Состояния анализа (`analyzer.STATUS_*`) и их подписи в интерфейсе: `DISABLED` — выкл,
`PENDING` — ожидает, `RUNNING` — анализ, `READY` — готов, `NEEDS_REVIEW` — требует проверки,
`FAILED` — ошибка, `STALE` — устарел.

Предложение LLM — кандидат с `source=llm`, типом, чтением, уверенностью и сверкой с
детерминированным слоем (`agreement`: `agree` / `conflict` / `none`). Решения по нему идут
через существующую ручку `POST /api/projects/{id}/pronunciation/review`: принять в проект,
принять глобально (явный `scope: global`), изменить или отклонить (выключенное правило —
память о решении). Проектный словарь приоритетнее глобального, конфликт требует человека.
Каждое решение пересчитывает затронутые реплики вместе с LLM-разбором, поэтому массовый разбор
десятков слов подряд занимает минуты — лучше идти по репликам, а не по всему списку сразу.

## Включение и настройка

По умолчанию анализатор **выключен**: это отдельная модель рядом с TTS, и её включение —
осознанное действие. Окружение задаёт значения по умолчанию, а файл `data/llm_settings.json`
(путь переопределяется `TTS_LLM_SETTINGS_PATH`) хранит то, что переключили в интерфейсе, и
**важнее окружения** — иначе галочка не пережила бы перезапуск.

```bash
export LLM_ANALYZER_ENABLED=1                     # включить анализ
export TTS_OLLAMA_URL=http://127.0.0.1:11434      # адрес Ollama
export LLM_PRIMARY_MODEL=qwen3:8b                 # победитель benchmark'а
export LLM_FALLBACK_MODEL=qwen3:4b-instruct-2507-q8_0
export LLM_ANALYZER_REQUIRED_FOR_RENDER=0         # 1 — рендер без анализа запрещён
```

Имена `LLM_*` принимаются и с проектной приставкой `TTS_`. Прочие настройки:
`LLM_ANALYZER_NUM_CTX` (8192), `LLM_ANALYZER_TEMPERATURE` (0.0), `LLM_ANALYZER_SEED` (0),
`LLM_ANALYZER_TIMEOUT_SEC` (90 с), `LLM_ANALYZER_MAX_REPAIRS` (1),
`LLM_ANALYZER_CONTEXT_REPLICAS` (2), `LLM_ANALYZER_CONTEXT_CHARS` (4000),
`LLM_ANALYZER_SCENE_REPLICAS` (6), `LLM_ANALYZER_RESPONSE_FORMAT` (`json`),
`LLM_ANALYZER_THINK` (`auto` — скрытое рассуждение thinking-моделей выключается, если модель
это умеет).

**Включение в приложении.** В блоке «Лингвистический анализ» есть переключатель, выбор модели
Ollama и флаг «требовать анализ перед рендером»; настройка сохраняется в
`data/llm_settings.json` и переживает перезапуск. Подписи состояний — из списка выше.
При `LLM_ANALYZER_REQUIRED_FOR_RENDER=1` рендер без успешного анализа отвечает 409 с причиной.

## API и интерфейс

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/llm/status` | готовность, выбранная модель, версии |
| `GET` | `/api/llm/models` | скачанные модели и роли primary/fallback |
| `POST` | `/api/llm/settings` | включение, модель, `required_for_render`, контекст |
| `POST` | `/api/projects/{id}/analyze` | канонический проход подготовки проекта |
| `GET` | `/api/projects/{id}/linguistic-analysis` | состояние, модель, причины отказов, кандидаты |
| `POST` | `/api/projects/{id}/linguistic-analysis` | запуск анализа (тот же проход) |
| `GET` | `/api/projects/{id}/analysis` | сохранённая подготовка реплик |
| `POST` | `/api/projects/{id}/pronunciation/review` | решения по предложениям |

Статус и модели можно посмотреть без запуска анализа и без поднятия моделей синтеза:

```bash
curl -s localhost:8000/api/llm/status | python3 -m json.tool
curl -s localhost:8000/api/llm/models | python3 -m json.tool
```

В интерфейсе лингвистический анализ показан отдельным блоком в обеих вкладках озвучки
(«Озвучка диалога» и «Сплошной текст»): состояние, модель и предложения с решениями «только в
этот проект / во все проекты / пропустить». Обе вкладки работают через один бэкенд: сплошной
текст анализируется тем же анализатором (проект для этого не создаётся, ключ кеша — хеш
текста), а его аннотации возвращаются в ответе рендера и не применяются к тексту без решения
человека. У сплошного текста нет проекта, поэтому решения по его предложениям идут через общий
словарь или через вкладку диалога.

## Ограничения

- Качество анализа — модельное: `issue_f1` выбранной модели 0.19 на gold-корпусе (прогон на
  prompt v2 / схеме v1). Модели почти не считают границы точно — это компенсировано поиском
  слова на backend'е, но не устранено.
- `reason_code` 4B-модели иногда выдуман; в анализаторе он справочный, в benchmark — строгий
  (метрика измеряет следование контракту).
- Массовый review дорог: каждое решение пересчитывает затронутые реплики вместе с разбором.
- Рядом с прогретым F5 на 18 GB при пользовательской загрузке анализ недоступен — это
  осознанный отказ guard'а, а не дефект; рабочий режим — выгрузить движок, проанализировать,
  отрендерить.
- Жёлтое давление macOS запрещает запуск анализа даже при низком проценте занятой памяти.
- Класс реплики от модели — подсказка, а не решение: стратегию синтеза коротких реплик выбирает
  отдельный слой (см. [dialogue.md](dialogue.md)).
