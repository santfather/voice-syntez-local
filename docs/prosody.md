# Эмоции, интонация и референс-профили

У одного голоса в проекте может быть **несколько** эталонных записей — по одной на интонацию.
Эмоция реплики выбирает, **какой референс** уйдёт в движок, а не правит произносимый текст:
F5 и XTTS переносят на синтез интонацию эталона, поэтому «строгий приказ» и «лёгкая ирония»
лучше получаются, когда для них есть своя запись, а не одна нейтральная на всё.

Эта страница описывает словарь интонаций, запись профилей, детерминированный выбор референса
и то, какие измерения переноса интонации ещё **не** сделаны.

## Эмоция — метаданные, а не текст

Ни `[восторг]`, ни `<emotion=…>` в произносимую строку не попадают: `source_text`,
`normalized_text`, `dictionary_text`, `accentized_text` и `final_text` остаются текстом, а
интонация живёт отдельными полями реплики. Это не стилистическое требование, а защита от
класса дефектов: тег, ушедший в модель, читается вслух, ломает словарь и расходует контекст.
Поэтому эмоция выбирает референс и ничего не дописывает в текст.

Правило действующей эмоции (`emotions.emotion_effective`, `backend/emotions.py`):

```text
emotion_effective = override → detected → NEUTRAL
```

Ручной выбор всегда важнее автоматического, а выключенная или недоступная LLM не оставляет
реплику без эмоции — она получает `NEUTRAL`. Ручная смена эмоции не требует повторного
анализа: это правка metadata, а не текста.

## Словарь интонаций

Словарей два, и они намеренно разные (`backend/emotions.py`):

- **`PROFILE_KEYS` (11)** — то, что можно **записать** как референс-профиль голоса. Ровно под
  эти значения есть 11 фраз `RECORD_PHRASES`.
- **`EMOTIONS` (13)** = `PROFILE_KEYS` + `SURPRISE` и `FEAR`. Это то, что модель может
  **определить**: испуг и удивление остаются различимыми, хотя отдельной записи под них нет —
  резолвер уводит их в ближайший доступный профиль (по умолчанию — нейтральный) с явным откатом.
- **`SELECTABLE_EMOTIONS` (14)** = `AUTO` + `EMOTIONS` — то, что видно в выпадающем списке.
  `AUTO` — не эмоция, а «реши сам».

Подписи берутся из `EMOTION_TITLES`; порядок `PROFILE_KEYS` — он же порядок в интерфейсе:

| Ключ профиля | Подпись в интерфейсе |
|---|---|
| `NEUTRAL` | Нейтрально |
| `CALM` | Спокойно |
| `QUESTION` | Вопрос |
| `NEUTRAL_QUESTION` | Вопрос + нейтрально (в компактных местах — «Вопрос») |
| `EXCLAMATION` | Восклицание |
| `DELIGHT` | Радость / восторг |
| `SAD_SYMPATHETIC` | Огорчение / сочувствие (в компактных местах — «Сочувствие») |
| `IRONIC` | Ирония |
| `STRICT` | Строго |
| `ENUMERATION` | Перечисление |
| `EXCITED` | Взволнованно |
| `SURPRISE` | Удивление (профиль не записывается) |
| `FEAR` | Испуг (профиль не записывается) |
| `AUTO` | Авто (только выбор пользователя) |

## Как записать несколько референсов одного голоса

Голос хранится в `voices/voices.json`, и профили лежат **внутри** его записи — в SQLite их нет.
Поэтому «голос → профили» — это 1:N по структуре, а не связь по внешнему ключу. Отдельной
миграции данных не нужно: голос, сохранённый до появления профилей, читается как нейтральный
профиль «Основной» (`Voice.neutral_profile()`, `id = "{voice_id}-neutral"`), а `voices.json`
при этом не переписывается. Все интонационные поля аддитивны, старые голоса и проекты
работают как раньше.

Порядок записи:

1. Вкладка **«Голоса»** → у нужного голоса раскройте **«Референсы эмоций»**.
2. Выберите интонацию в списке (11 записываемых профилей) и нажмите **«Загрузить запись»** —
   приложение запишет фразу с микрофона или примет файл. Каждая запись становится отдельным
   профилем **того же** голоса, а не новым голосом; основной референс остаётся нейтральным и
   не перезаписывается.
3. Повторная запись **той же фразы** заменяет прежний профиль этого голоса, а не создаёт дубль:
   позиция фразы в списке — устойчивый идентификатор `source_record_phrase_id`.
4. Референс, расшифровка которого расходится с записью, получает отметку **«проверить»**
   (`quality_status = warning`); резолвер такой профиль не берёт — сначала исправьте запись или
   расшифровку.
5. Подтверждённый прослушиванием профиль помечается галочкой **«авто»**
   (`enabled_for_auto`) — только тогда его берёт автоматическая маршрутизация. По умолчанию
   флаг **выключен**: свежая запись не становится автоматикой сама по себе.

Таблица «фраза → ключ профиля» (`RECORD_PHRASE_PROFILES`, `frontend/app.js`):

| Подпись фразы | Ключ профиля |
|---|---|
| Вопрос и утверждение | `NEUTRAL_QUESTION` |
| Восклицания, много шипящих | `EXCLAMATION` |
| Спокойная просьба (короче) | `CALM` |
| Только вопросы | `QUESTION` |
| Сложные сочетания согласных | `NEUTRAL` |
| Радость, восторг | `DELIGHT` |
| Огорчение, сочувствие | `SAD_SYMPATHETIC` |
| Лёгкая ирония | `IRONIC` |
| Строгий тон, короткий приказ | `STRICT` |
| Перечисление, ровный ритм | `ENUMERATION` |
| Быстрая, взволнованная речь | `EXCITED` |

Правило начитки: одна эмоция и ровный темп на всю фразу, разнообразие — между фразами.
Внутри одной фразы интонацию не меняем — рваный темп и скачки эмоции портят референс сильнее,
чем узкий набор звуков.

## Как выбирается референс

`backend/reference_resolver.py` — единственное место, которое отвечает на вопрос «какой файл и
какая расшифровка уйдут в движок». Порядок решений детерминирован:

1. **Явный выбор пользователя** (`profile_id`) — если профиль принадлежит **этому** голосу,
   прошёл проверку качества и совместим с движком. Флаг `enabled_for_auto` здесь не проверяется:
   человек вправе выбрать неподтверждённый профиль вручную.
2. **Цепочка отката** под запрошенную интонацию (см. режимы ниже).
3. **`NEUTRAL` того же голоса** — с пометкой `fallback_used`, но **без отказа**: отсутствие
   интонационного референса не блокирует синтез.
4. Иначе — `ReferenceUnavailableError`: без референса синтезировать нельзя, и причина
   называется словами.

Автоматический выбор (шаги 2–3) берёт только **подтверждённые** профили
(`enabled_for_auto = true`). Профиль чужого голоса взять нельзя **структурно**: профили лежат
внутри записи голоса, и резолвер физически не может обратиться к чужой. LLM файл не выбирает:
она называет только намерение (`prosody_effective`), а путь к аудио получается здесь.

Кандидаты сортируются детерминированно: сначала прошедшие проверку (`quality_status = ok`),
затем профиль по умолчанию (`is_default`), затем по `created_at`.

### Качество и совместимость профиля

Профиль пригоден, только если он включён (`enabled`), у него есть файл, проверка «референс ↔
расшифровка» не дала `warning` и он совместим с движком. Причины отказа называются словами
(«профиль выключен», «файл референса отсутствует», «профиль не подтверждён для автоматического
выбора», «профиль не проверен для движка …»).

- **Сверка записи с расшифровкой** — Whisper и `transcribe.check_ref_text_match`
  (`MATCH_THRESHOLD = 0.6`). Это и есть источник `quality_status`: расхождение даёт `warning`
  и `quality_note`, совпадение — `ok`, отсутствие сверки — `unknown`.
- **Подсказки о самой записи** — `audio_analysis` измеряет F0 против заявленного пола
  (`MALE_RANGE = (85, 155)` и `FEMALE_RANGE = (165, 255)` Гц), перегруз
  (`CLIPPING_LEVEL = 0.99`, `CLIPPING_MIN_RATIO = 0.001`) и полосу частот. Они показываются в
  карточке голоса как предупреждения и **ничего не блокируют**: решение остаётся за
  прослушиванием.
- `quality_status`: `ok` / `warning` / `unknown` (запись без сверки). Профиль с `warning`
  резолвер не берёт **вовсе** — ни автоматикой, ни явным выбором: расхождение расшифровки с
  записью нельзя обойти, его нужно исправить.
- **Совместимость с движком** (`engine_compatibility`) — список id движков (`f5`, `xtts`, …).
  Пустой список — «годится для любого движка голоса». Нейтральный профиль проверкой движка не
  ограничивается: это и есть сам голос, и отказ запретил бы синтез там, где раньше всё
  работало. Следствие: профиль, подтверждённый на F5, автоматика не возьмёт на XTTS, пока он
  не помечен совместимым и с XTTS.

### Режимы отката

Режим задаётся константой `config.PROSODY_FALLBACK_MODE`, переменной окружения
**`TTS_PROSODY_FALLBACK_MODE`**; по умолчанию — `neutral_only`.

| Режим | Что делает |
|---|---|
| `neutral_only` (по умолчанию) | нужного профиля нет → `NEUTRAL` **того же** голоса, с пометкой отката |
| `chain` | идёт по таблице родственных интонаций `FALLBACK_CHAINS`, всегда заканчиваясь `NEUTRAL` |

Цепочки `chain` (`reference_resolver.FALLBACK_CHAINS`; последний элемент всегда `NEUTRAL`):

| Запрошено | Цепочка |
|---|---|
| `CALM` | `CALM → NEUTRAL` |
| `QUESTION` | `QUESTION → NEUTRAL_QUESTION → NEUTRAL` |
| `NEUTRAL_QUESTION` | `NEUTRAL_QUESTION → QUESTION → NEUTRAL` |
| `EXCLAMATION` | `EXCLAMATION → EXCITED → NEUTRAL` |
| `DELIGHT` | `DELIGHT → EXCLAMATION → NEUTRAL` |
| `SAD_SYMPATHETIC` | `SAD_SYMPATHETIC → CALM → NEUTRAL` |
| `IRONIC` | `IRONIC → NEUTRAL` |
| `STRICT` | `STRICT → NEUTRAL` |
| `ENUMERATION` | `ENUMERATION → NEUTRAL` |
| `EXCITED` | `EXCITED → EXCLAMATION → NEUTRAL` |
| `SURPRISE` | `EXCLAMATION → EXCITED → NEUTRAL` |
| `FEAR` | `STRICT → NEUTRAL` |

`neutral_only` — консервативный производственный режим: откат на соседний профиль допускается
только после подтверждения benchmark'ом, а его пока нет. Поэтому по умолчанию **ни один профиль
не разрешён для Auto** (`enabled_for_auto = false`): он доступен вручную, но автоматика его не
берёт. Неизвестное значение режима не подменяется молча — оно логируется и трактуется как
`neutral_only`. Откат виден в ответе реплики (`reference.fallback_used` и
`reference.fallback_reason`), а не происходит тихо.

## Ручное управление и пересинтез

Во вкладке **«Озвучка диалога»** у каждой реплики есть селектор интонации. `AUTO` показывает
фактический результат («Авто → Вопрос»), ручной выбор важнее автоматического, а рядом видно,
каким референсом реплика озвучена и был ли откат на нейтральный.

- Ручной выбор интонации — это `emotion_override`; рядом можно явно выбрать профиль
  (`reference_profile_id`). Правка не требует повторного анализа: это metadata, а не текст.
- **Regenerate** (`POST /api/projects/{id}/replicas/{index}/regenerate`) принимает
  `emotion_override` и `reference_profile_id`, берёт **сохранённый** текст и меняет только
  интонацию. Он требует подготовленной реплики (`analysis_status = done`), иначе отвечает 409.
  Соседние реплики и их варианты не трогаются, а у нового take сохраняется паспорт: с каким
  профилем и интонацией он получен и был ли откат.
- Подтверждение профиля для автоматики — `PATCH /api/voices/{voice_id}/references/{profile_id}`
  с `{"enabled_for_auto": true|false}` (галочка «авто» в карточке голоса).

## Автоматическая маршрутизация: что делает `AUTO`

`AUTO` — не эмоция, а «реши сам». Действующий профиль считает `emotions.prosody_effective`
(`backend/emotions.py`):

```text
prosody_effective = override → recommended → emotion
```

Модель называет не только эмоцию, но и **записываемый** профиль (`recommended_profile`):
если он есть, именно он и есть цель маршрутизации, и резолверу не нужно выводить замену
самому. Пустая рекомендация не ошибка — тогда работает прежнее правило
`override → detected → NEUTRAL`, а семантические значения уводит в ближайший профиль таблица
отката. `prosody_effective` **не хранится**: это правило, а не поле.

Анализирует сцену, а не строку, тот же лингвистический анализатор (`backend/llm/`):

- контекст одной реплики — до двух реплик до и после цели с бюджетом 4000 символов;
- диалог режется на окна сцены по 6 реплик с перекрытием 2 (шаг 4), один запрос на окно, а не
  на реплику; ответ на перекрывающуюся реплику берётся из первого окна, поэтому у каждой
  реплики ровно один разбор;
- по каждой реплике модель возвращает класс, `context_dependency`, `dialogue_act`, эмоцию и
  блок `prosody` (`profile`, `recommended_profile`, `intensity`, `pace`, `confidence`);
- текст модель **не переписывает**: ответ с новым текстом отвергается целиком, а теги
  интонации в произносимую строку не попадают. `intensity`, `pace` и `confidence` —
  информация, а не ручки движка: они не меняют `nfe_step`, `cfg_strength` или скорость синтеза.

Без Ollama приложение работает: анализатор выключен или недоступен → интонация берётся
безопасной эвристикой по тексту (`emotions.heuristic_emotion`: знак вопроса, слова радости или
испуга) с низкой уверенностью. Источник честно называется в API (`emotion.source`:
`llm` / `heuristic` / `none`), а отказ анализа **не блокирует** обычный рендер — причина
остаётся в `blocked_reason`.

Слой коротких реплик учитывает регистр интонации при выборе контекста
(`emotions.prosody_compatible`, регистры `calm` / `high` / `marked`): контекст берётся только
у реплики того же спикера и совместимого регистра, чтобы спокойная фраза и крик не склеились
в одно звучание. Вопрос и спокойный ответ — один регистр: это одна интонационная линия.
Без анализа проверка пропускает — отказ функциональности ради политики недопустим.

## Модель данных

```text
Voice  1 ──── N  ReferenceProfile   (voices/voices.json)
  │               ├ emotion / profile_key
  │               ├ label, audio_file + ref_text
  │               ├ source ("legacy" | "record")
  │               ├ quality_status / quality_note / transcription_status
  │               ├ engine_compatibility[]
  │               ├ source_record_phrase_id
  │               └ is_default / enabled / enabled_for_auto  (по умолчанию false)

Project ──── Replica
               ├ prosody_profile / prosody_intensity / prosody_pace / prosody_confidence
               ├ emotion_detected / emotion_confidence
               ├ emotion_override  (ручной выбор интонации)
               ├ dialogue_act / context_dependency
               ├ reference_profile_id / reference_emotion / reference_fallback_used
               ├ reference_profile_key / reference_fallback_reason
               └ Takes (варианты звучания с паспортом профиля)
```

Интонационные колонки реплики добавлены аддитивными миграциями 9 (эмоция, `dialogue_act`,
`context_dependency`, `reference_profile_id`, `reference_emotion`, `reference_fallback_used`)
и 10 (`prosody_profile`, `prosody_intensity`, `prosody_pace`, `prosody_confidence`,
`reference_profile_key`, `reference_fallback_reason`). `prosody_intensity` и
`prosody_confidence` допускают `NULL`: «модель не сказала» честно отличается от `0.0`.
Колонок-дубликатов `prosody_override` и `prosody_effective` нет: ручной выбор хранится в
`emotion_override`, а действующий профиль вычисляется.

В ответе API у реплики два блока: `prosody` (`profile`, `profile_title`, `intensity`, `pace`,
`confidence`, `override`, `effective`, `effective_title`, `source`, `dialogue_act`,
`context_dependency`) и `reference` (`profile_id`, `profile_key`, `emotion`, `fallback_used`,
`fallback_reason`).

## Перенос интонации: что измерено, а что нет

Для проверки переноса в репозитории есть инструмент и корпус:

```bash
./venv/bin/python tools/prosody_benchmark.py --check                # корпус, без моделей
./venv/bin/python tools/prosody_benchmark.py --plan --voice <id>    # матрица, без моделей
./venv/bin/python tools/prosody_benchmark.py --voice <id>           # прогон на движке голоса
./venv/bin/python tools/prosody_benchmark.py --voice <id> --engine xtts
./venv/bin/python -m pytest tests/test_prosody_benchmark.py -q
```

`tools/prosody_benchmark.py` запускается в процессе и поднимает **настоящую** модель — дашборд
перед прогоном лучше остановить. Он берёт корпус `benchmarks/prosody/corpus.v1.jsonl`
(36 реплик, 9 категорий по 4: `neutral`, `question`, `delight`, `sad_sympathetic`, `irony`,
`strict`, `enumeration`, `excited`, `ambiguous`; порог валидности — не меньше 30), строит
матрицу «реплика × доступные профили» (голос, движок, сид, скорость и текст зафиксированы,
меняется только `ReferenceProfile`), синтезирует каждую ячейку и пишет WAV на ячейку плюс
`report.json`, `report.md` и `review.md` в `output/benchmarks/prosody/<run_id>/`.

Автоматические метрики ячейки отвечают только на «текст не сломался»: `wer`, `first_word_ok`,
`last_word_ok`, `extra_words`, `repetition`, `duration_sec`, `generation_sec`, `text_qa`. WER
берётся у существующего `transcribe.word_error_rate`, второй формулы нет. Перенос интонации
оценивает человек по `review.md` — ASR его не заменяет.

**Состояние на текущем коде: перенос не измерен.** В `voices/voices.json` ни у одного голоса
нет записанных профилей (`profiles: []`), завершённого прогона в `output/benchmarks/prosody/`
нет, заключений прослушивания нет. Поэтому верно следующее:

- ни один профиль не разрешён для автоматического выбора (`enabled_for_auto = false`);
- `chain`-откат не производственный, пока benchmark не подтвердит цепочки;
- выводы одного движка нельзя переносить на другой: F5 и XTTS оцениваются раздельно.

Инфраструктура при этом готова и проверена без моделей: корпус проходит `--check`, матрица и
отчёты строятся на стабе, резолвер детерминирован и не выходит за пределы голоса.

## Ограничения

- Отдельных фраз для «Удивления» и «Испуга» в списке нет — до своей записи эти эмоции звучат
  нейтральным референсом (или ближайшим профилем в режиме `chain`) с явной пометкой отката.
- Эмоциональный референс может изменить тембр: проверка сверяет запись с расшифровкой, но не
  «похожесть на себя», поэтому решение остаётся за прослушиванием.
- «Авто» — это предложение модели (или эвристики), а не подтверждённый факт: уверенность и
  источник показаны рядом.
- Перенос просодии не подтверждён **ни на одном** движке — см. предыдущий раздел.
