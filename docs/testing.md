# Тесты и прогоны

> **Прогоняйте тесты изоляции и любые замеры памяти из системного Terminal.app, а не из IDE.**
> Песочница TraeCode (и подобных редакторов) перехватывает дочерние процессы: отчёты `.ips`
> не появляются, в выводе мелькает `TRAE Sandbox Error: process crashed`, а тесты с жёстким
> таймаутом падают из-за замедления спавна. Подробности — в абзаце про изоляцию ниже.

Страница о том, чем и как проверяется проект: что покрывает обычный `pytest`, как гонять набор по
частям и какие прогоны поднимают живой сервер и настоящие модели. Она нужна тем, кто меняет код и
хочет убедиться, что ничего не сломал, и тем, кто разбирает падение, провал benchmark'а или
непонятное поведение рендера.

## Юнит- и интеграционные тесты

Основной набор запускается обычным pytest; модели при этом не поднимаются. `pytest.ini` задаёт
`testpaths = tests`, `pythonpath = .` и `addopts = -q`, поэтому из корня проекта достаточно
`./venv/bin/python -m pytest`.

```bash
# Весь набор
./venv/bin/python -m pytest

# Один файл или несколько
./venv/bin/python -m pytest tests/test_job_queue.py -v
./venv/bin/python -m pytest tests/test_prosody_resolver.py tests/test_prosody_benchmark.py -q

# По имени теста
./venv/bin/python -m pytest -k queue -q
```

Полный прогон на момент уборки документации: **1396 passed, 0 failed, 0 errors, 2 skipped,
0 xfailed**. Оба `skipped` — gated-прогоны на реальных весах: Qwen3-TTS (`TTS_RUN_REAL_QWEN`) и
Kokoro-ru (`TTS_RUN_REAL_KOKORO`). Без флага такой тест пропускается с причиной — см. разделы про
эти движки ниже.

Модели при прогоне pytest не поднимаются: реестр движков подменяется заглушкой `StubEngine`
(`tests/conftest.py`), которая отдаёт синусоиду и ведёт журнал вызовов, а каталоги `voices/`
и `output/` уводятся в `tmp_path`. Поэтому тесты идут секунды, не требуют весов и не трогают
рабочие файлы проекта. Поведение проверяется настоящее — реальные функции пайплайна, очереди
и роутов, — подменяется только сама модель. Изоляция синтеза в отдельном процессе по умолчанию
выключена (автофикстура `_no_worker_isolation`), чтобы ни один тест случайно не запустил дочерний
процесс с torch и весами; тесты самой изоляции включают её сами и подставляют лёгкую фабрику
движка.

Тесты изоляции и восстановления (`test_worker_isolation.py`, `test_worker_recovery.py`,
`test_crash_report_acceptance.py`, `test_memory_and_shutdown.py`) роняют воркер **намеренно**:
`tests/fake_worker_engine.py` по маркерам `CRASH`/`краш`/`SEGV` вызывает `os.abort()` или
`ctypes.string_at(0)` в дочернем процессе. macOS на каждый такой SIGABRT пишет отчёт в
`~/Library/Logs/DiagnosticReports/` (архив — в `Retired/`), поэтому десятки файлов `Python-*.ips`
после прогонов — ожидаемый шум, а не дефект: в `backend/` вызовов `os.abort()` нет ни одного, и
продуктовый воркер сам себя не роняет. Если до падения реплика успела пройти нормальный синтез, в
отчёте будет и `libtorch`: уборка в `synthesize()` (`release_torch_memory(light=True)`) импортирует
torch в процессе воркера. Сами отчёты накапливаются и троттлятся системой, поэтому их число — не
метрика падений.

Прогонять эти тесты и, тем более, мерить память MPS нужно в обычном терминале: под TraeCode
песочница перехватывает дочерние процессы — отчёты `.ips` не появляются, в логе видно
`TRAE Sandbox Error: process crashed`. В обычном терминале тот же набор проходит, а отчёты
пишутся штатно.

**Тесты с жёстким таймаутом и холодный спавн.** `test_worker_timeout_kills_process_and_restarts`
проверяет реакцию супервизора на зависший воркер, а не скорость импорта torch. Поэтому он сначала
прогревает воркер с щедрым таймаутом (10 с из фикстуры), и только затем ужимает бюджет до 1 с и
шлёт команду `HANG`; перед последней репликой бюджет возвращается — её выполняет уже новая,
только что поднятая замена, и ужимать её спавн снова было бы той же ошибкой. Прогонять такие тесты
всё равно полезнее из обычного терминала, но падать из-за скорости спавна они больше не должны:
под песочницей TraeCode холодный спавн занимает больше секунды, поэтому любой тест, включающий
подъём воркера в бюджет таймаута, обязан быть устроен так же — прогрев вне бюджета.

### Как отличить тестовый SIGABRT от продуктового за 1 минуту

Отчёт `Python-*.ips` пишут и тесты, и настоящие падения, и в самом файле они выглядят одинаково
(тот же SIGABRT, тот же путь через `os_abort`). Порядок проверки, который снимает вопрос:

1. Открыть отчёт и взять из заголовка `procLaunch` (время запуска процесса) и `coalitionName`.
2. Открыть `logs/voice_syntez.log` и посмотреть строки в окне ±120 секунд от `procLaunch`.
   Продуктовый бэкенд опрашивает `/api/status` каждые ~4 секунды, поэтому живое приложение в
   этом окне следы оставляет; пустое окно — признак теста.
3. Сверить `.pytest_cache/v/cache/lastfailed` и `nodeids`: если файлы обновлены в то же окно,
   падение принадлежит прогону pytest.
4. Искать в журнале метку `FAKE-WORKER-CRASH` — её печатает заглушка `tests/fake_worker_engine.py`
   перед `os.abort()`, а родитель переносит stderr воркера в свой лог (`supervisor._start_drains`).
   Есть метка — падение тестовое, вопрос закрыт. Оговорка: у самого прогона pytest фикстура
   `workspace` уводит журнал в `tmp_path`, поэтому метки в `logs/voice_syntez.log` там не будет —
   для падений из `tests/` работают шаги 3 и 5, а убирает их не `--delete`, а `--retire`.
5. Открыть `logs/worker_faulthandler.log`: воркер пишет туда Python-стек нативного падения, и по
   нему видно, на какой строке процесса всё оборвалось. Этот файл ведёт сам процесс воркера, а он
   свой `LOG_PATH` не подменяет, поэтому стек остаётся в рабочем `logs/` и после тестов.

Наличие `libtorch_cpu.dylib` в отчёте признаком продукта не является: уборка в `synthesize()`
(`release_torch_memory(light=True)`) импортирует torch в воркер, поэтому тестовый «тёплый» прогон
тоже даёт дамп с torch. Забрать отчёты, оставленные прогоном, можно командой
`./venv/bin/python tools/retire_test_crashes.py --since-min 60 --retire`.

## Benchmark-корпуса

Оба корпуса лежат в репозитории, проверяются валидатором и тестами и не требуют моделей на этапе
проверки. Полные прогоны по ним поднимают модели (см. следующий раздел).

### `benchmarks/russian_linguistics` — gold-корпус русской лингвистики

Корпус из 339 кейсов для benchmark'а локальных LLM: проверяет, умеет ли модель **контекстно**
анализировать русский текст перед синтезом и возвращать аннотации, а не переписанный текст.
Файлы: `dataset.v1.jsonl`, `schema.json`, `prompts/`, `expected/` (схема ответа, счётчики и список
кейсов на проверку человеком). Подробности — в `benchmarks/russian_linguistics/README.md`.

```bash
./venv/bin/python tools/build_llm_dataset.py --check                  # валидация корпуса без записи
./venv/bin/python -m pytest tests/test_llm_benchmark_dataset.py -q    # та же проверка внутри pytest
./venv/bin/python tools/llm_benchmark.py --dry-run                    # прогон без моделей и сети
./venv/bin/python tools/llm_benchmark.py --smoke                      # короткий прогон на Ollama (15 кейсов)
./venv/bin/python tools/llm_benchmark.py                              # полный корпус (Ollama, четыре модели)
./venv/bin/python tools/llm_benchmark_report.py --stdout              # отчёт по сохранённым результатам
```

Результаты прогонов складываются в `benchmarks/russian_linguistics/results/` — этот каталог
в `.gitignore`, потому что сырые ответы и метрики конкретного запуска не часть проекта.

### `benchmarks/prosody` — корпус переноса просодии

Корпус из 36 реплик для benchmark'а переноса просодии: проверяет, меняет ли смена
`ReferenceProfile` интонацию, **не ухудшая текст и голос**. Файлы: `corpus.v1.jsonl`,
`schema.json`. Категории, список реплик для ручной проверки и порядок подтверждения профилей
описаны в `benchmarks/prosody/README.md`.

```bash
./venv/bin/python tools/prosody_benchmark.py --check                 # корпус без моделей
./venv/bin/python tools/prosody_benchmark.py --plan --voice <id>     # матрица без моделей
./venv/bin/python tools/prosody_benchmark.py --voice <id>            # полный прогон на моделях
./venv/bin/python -m pytest tests/test_prosody_benchmark.py tests/test_prosody_benchmark_cli.py -q
```

Прогон матрицы синтезирует реплики настоящим движком голоса (F5 или XTTS) и расшифровывает их
Whisper'ом для метрик текста; `--plan` и `--check` обходятся без моделей. Отчёты и аудио остаются
в `output/benchmarks/prosody/<id>`.

### Нагрузочный тест

`tools/loadtest.py` — отдельный инструмент поверх живого сервера: ничего не мокает, ходит по
сети и поднимает настоящие модели. Нужен запущенный дашборд; в репозитории не является частью
pytest.

```bash
./venv/bin/python tools/loadtest.py               # все фазы
./venv/bin/python tools/loadtest.py light queue   # только выбранные
./venv/bin/python tools/loadtest.py --base-url http://127.0.0.1:8001 engines
```

| Фаза | Что меряет |
|---|---|
| `light` | Латентность `/api/status`, `/api/engines`, `/api/voices` и `/api/parse` последовательно |
| `load` | Те же ручки при 1/5/20/50 одновременных клиентах: RPS, p50/p99, счёт ошибок |
| `heavy` | Отзывчивость API, пока идёт настоящая задача с `qa=strict` |
| `queue` | Шесть задач разом: серийность очереди, ожидание и время работы каждой |
| `qa` | Один и тот же текст в режимах `qa=off`, `qa=smart` и `qa=strict`: время, число запусков Whisper и попытки |
| `engines` | XTTS холодный и прогретый плюс смешанный диалог F5 + XTTS |

Параллельно фоновый сэмплер снимает RSS сервера, RSS его дочерних процессов (Whisper-воркер),
CPU и занятость памяти системы, а в конце печатает пики отдельно по каждой фазе. Голоса для
прогона заданы константами `F5_VOICE` и `XTTS_VOICE` в начале файла — это id из `voices/voices.json`.

**Замеры** (Mac, 18 ГБ, `mps`, F5 и XTTS прогреты):

| Что | Результат |
|---|---|
| Лёгкие ручки, 50 одновременных клиентов | ~5200 RPS, p50 9.5 мс, p99 10.2 мс, 0 ошибок из 1250 запросов |
| Тяжёлая задача под опросом `/api/status` десятью потоками | 16 944 запроса за 92 с, p99 4.4 мс, 0 ошибок — цикл событий синтезом не блокируется |
| Очередь из 6 задач | строго по одной (максимум 1 в работе, пересечений 0), ожидание растёт на ~6.5 с на задачу |
| QA на чистом диалоге, 3 реплики (16 с аудио) | `off` 30.0 с · `smart` 28.5 с (0 запусков Whisper) · `strict` 83.9 с (3 запуска) — ×2.9 к `smart` |
| XTTS: холодный и прогретый старт | 23.2 с на первую задачу (21 с из них — загрузка движка) против 1.8 с на прогретом |
| XTTS против F5 на одной реплике | XTTS +6.9…9.4 с, F5 +1.3…1.5 с — разница в 5-6 раз |
| Память | в режиме `strict` системная до 86.2 %, RSS сервера до 2.4 ГБ, RSS Whisper-процесса до 0.85 ГБ; в `smart` на чистом диалоге Whisper не поднимается вовсе |

Отсюда же видно, что дефолт `qa=off` выбран верно: `strict` стоит почти ×3 по времени даже когда
все куски проходят порог с первой попытки, а его настоящая задача — ловить редкий брак. `smart`
на нормальном тексте по времени не отличается от `off`: Whisper не запускается ни разу.

### Замер памяти

`tools/memory_check.py` — отдельный инструмент памяти: по шагам поднимает F5, затем XTTS,
выгружает их и печатает RSS, заполненность системы и счётчики MPS у torch после каждого шага,
а в конце — таблицу «до/после». Тоже не входит в pytest и запускается вручную. Дашборд перед
прогоном лучше остановить: два процесса с поднятыми моделями не влезут в память Apple Silicon.
Движки инструмент собирает **в своём процессе** (`create_local_engine`), а не через реестр: при
включённой изоляции реестр вернул бы прокси, модель поднялась бы в воркере, и замер показывал бы
пустой процесс инструмента. Живой RSS воркеров виден в `/api/status`
(`memory_state.workers_rss_mb` — сумма по всем процессам синтеза, `memory_state.worker_peak_rss_mb`
— самый тяжёлый из них: именно по пику идёт классификация NORMAL/WARNING/CRITICAL).

```bash
./venv/bin/python tools/memory_check.py                          # F5 + базовая XTTS
./venv/bin/python tools/memory_check.py --xtts-engine xtts-banana
```

Инструмент не утверждает, сколько памяти вернётся: `current_allocated_memory()` учитывает то,
что видит сам torch, `driver_allocated_memory()` — то, что Metal выделил процессу, а в RSS на
Apple Silicon память MPS не попадает вовсе. Освобождение измеряется, а не предполагается.

### Прогон Qwen3-TTS на реальных весах

Обычный `pytest` поднимает Qwen только на подставном пакете (`tests/test_qwen_engine.py`);
настоящие веса подключает отдельный gated-прогон — один из двух `skipped` в полном наборе (второй —
Kokoro-ru, см. ниже).

```bash
# Без флага тест пропускается с причиной
./venv/bin/python -m pytest tests/test_qwen_engine.py -q

# Реальный прогон: веса из models/, запись голоса 3–15 с
TTS_RUN_REAL_QWEN=1 \
TTS_REAL_REF_AUDIO=/путь/к/речи.wav \
TTS_REAL_REF_TEXT="Текст этой записи" \
./venv/bin/python -m pytest tests/test_qwen_engine.py -k real -q
```

| Переменная | Смысл |
|---|---|
| `TTS_RUN_REAL_QWEN` | `1`/`true`/`yes` — включить прогон; иначе тест пропускается |
| `TTS_REAL_REF_AUDIO` | Путь к записи голоса для клонирования (3–15 с) |
| `TTS_REAL_REF_TEXT` | Дословный текст записи; без него клонирование идёт только по эмбеддингу |

Тест идёт путём load → synthesize → unload и проверяет частоту, форму и непустоту куска. Причины
для пропуска печатаются словами: нет флага, не скачаны веса (см. [Установку](install.md)) или не
задан и не найден файл референса.

Числа по устройству — загрузка, синтез, RTF, память — снимает отдельный инструмент: он поднимает
движок в своём процессе и пробует обе рабочие комбинации, `auto` и `cpu`.

```bash
./venv/bin/python tools/qwen_feasibility.py --plan                      # план и окружение, без моделей
./venv/bin/python tools/qwen_feasibility.py --ref /путь/к/речи.wav --ref-text "Текст записи"
```

Без `--ref-text` проба идёт в режиме «эксперимент» (клонирование только по эмбеддингу), `--json`
печатает результат машинночитаемо. В конце инструмент выносит вердикт: годится ли MPS для Qwen или
практичнее оставить `TTS_QWEN_FORCE_CPU=1`.

### Прогон Kokoro-ru на реальных весах

Обычный `pytest` поднимает Kokoro только на подставных пакете `kokoro` и произносительном словаре
(`tests/test_kokoro_engine.py`); настоящие веса подключает отдельный gated-прогон. Референс ему не
нужен — движок пресетный, встроенный голос выбирается по полу.

```bash
# Без флага тест пропускается с причиной
./venv/bin/python -m pytest tests/test_kokoro_engine.py -q

# Реальный прогон: веса из models/kokoro_ru
TTS_RUN_REAL_KOKORO=1 \
./venv/bin/python -m pytest tests/test_kokoro_engine.py -k real -q
```

Тест идёт путём load → synthesize → unload с пустыми `ref_audio_path`/`ref_text` — это и есть
проверка того, что путь клонирования не задействован, — и смотрит на контракт звука (частота, тип,
непустота), а не на качество произношения: его оценивают слухом, и автотест «проверяющий» его числом
создавал бы ложную уверенность. Причины пропуска печатаются словами: нет флага или не скачаны веса
(см. [Установку](install.md), раздел про Kokoro-ru). Первый запуск дополнительно платит за
инициализацию произносительного слоя, поэтому идёт заметно дольше последующих.

### Финальная проверка

`tools/smoke.py` — ручной end-to-end прогон по финальному сценарию roadmap на **живом** сервере и
реальных моделях. Инструмент проходит путь пользователя целиком: создать проект → назначить два
голоса (F5 и XTTS) → разобрать диалог со смешанными спикерами → рендер F5 + XTTS → Smart QA →
перегенерировать реплику → вернуть старый take → перезапустить backend → открыть проект заново →
выгрузить WAV → выгрузить MP3 (файл проверяется по содержимому, а не по расширению) → выгрузить
SRT → экспортировать проект → импортировать его → отрендерить снова.
Шаги печатаются по одному, в конце — сводка PASS/FAIL/SKIP.

Инструмент ничего не мокает и не поднимает модели сам: их поднимает сервер. Если сервер
недоступен, полный прогон завершается понятной ошибкой **до** первого синтеза. Порты не
узурпируются: без `--base-url` адрес ищется по уже отвечающему `/api/status`.

```bash
./venv/bin/python tools/smoke.py --dry-run        # план шагов и проверка доступа к API, без синтеза
./venv/bin/python tools/smoke.py                  # полный прогон (реальные модели, долго)
./venv/bin/python tools/smoke.py --no-restart     # без шага ручного перезапуска backend
./venv/bin/python tools/smoke.py --base-url http://127.0.0.1:8001
```

Два голоса берутся из уже созданных в дашборде — по одному на `f5` и на `xtts`/`xtts-banana`
(можно задать явно: `--f5-voice ID --xtts-voice ID`). Файлы экспорта складываются в
`output/smoke/`, созданные проекты по умолчанию остаются в дашборде для осмотра (`--cleanup`
удаляет их). Шаг «перезапуск backend» выполняется человеком: инструмент печатает приглашение,
ждёт Enter и проверяет, что сервер снова отвечает и проект восстановился. `--dry-run` — единственный
режим, который безопасно запускать без сервера и без моделей.
