# Local LLM Russian Linguistic Analyzer: база знаний (Task 2)

Документ описывает, как локальная модель встроена в подготовку русского текста к
синтезу: что она делает, чего не делает никогда, как проверяются её ответы, где
хранятся разборы и как всё это уживается с TTS на 18 GB. Числа живого smoke —
в `llm_analyzer_report.md`, политика памяти — в `ollama_memory_policy.md`.

Дата: 2026-09-18. Код: `backend/llm/analyzer.py`, `backend/llm/integration.py`,
`backend/llm/analysis_cache.py`, `backend/llm/scheduler.py`, `backend/db/repositories/llm_analyses.py`.

## 1. Место в pipeline

```text
SOURCE → разбор диалога → проект (SQLite)
      → POST /api/projects/{id}/analyze | /linguistic-analysis
            LLM-анализ (аннотации)  →  детерминированная нормализация → «ё» → словарь → ударения
            ↓                                              ↓
        кандидаты LLM  ────────────────►  кандидаты словаря (review)
      → PROJECT/GLOBAL DICTIONARY (только решением человека)
      → final_text → engine adapter (F5 «+», XTTS без «+») → Short Utterance → TTS
```

Второго pipeline нет: анализ идёт **внутри** того же прохода подготовки, что и
раньше, и читает тот же текст, который уходит в синтез. Сплошной текст
(`POST /api/render-text`) анализируется тем же классом (ключ кеша — хеш текста),
проект для этого не создаётся.

## 2. Что Analyzer делает и чего не делает

Делает: находит места, которые могут быть прочитаны неверно (омографы, `ё`, редкие
имена/топонимы, аббревиатуры, числа, латиница, термины), возвращает по каждому
аннотацию с типом, чтением (`meaning`), предложенной формой, уверенностью и
`needs_review`, а также подсказку о реплике (класс и релевантные соседи).

Не делает никогда:

- не возвращает текст: в контракте ответа нет поля с новым текстом, а лишнее поле
  (например `final_text`) отвергает ответ целиком (`unknown_field`);
- не доверяет своим границам: benchmark показал, что модели находят нужное слово, но
  почти не умеют считать символы (18–24 точных границы из 339 ответов), поэтому
  backend сам ищет `source` в тексте (ближайшее к подсказке вхождение, без учёта
  регистра), а несуществующее слово отбрасывает с причиной;
- не ставит ударения: `+` от модели снимается (`markup_stripped`), ударения остаются
  за RUAccent и словарём; разметка движка — ответственность engine adapter'а;
- не пишет в словарь: принятие предложения — явное действие человека (review);
- не управляет аудио: подсказки коротких реплик — информация, а не команда;
- не подменяет отказ успехом: недоступная Ollama, таймаут, отсутствующая модель,
  мусор вместо JSON или блокировка по памяти дают статус `FAILED` с причиной.

## 3. Контракт и валидация

- Схема: `schemas.analysis_json_schema()`, `SCHEMA_VERSION = 1`; prompt v2
  (`benchmarks/russian_linguistics/prompts/analyzer.v2.txt`) получает ту же схему
  плейсхолдером `{{schema}}` — prompt и валидатор не могут разойтись.
- Ответ передаётся как `format="json"` + схема текстом в prompt (грамматический
  режим `format=<schema>` ломает ответы qwen3 — см. `llm_russian_benchmark.md`).
- `parse_analysis(check_spans=False)` в Analyzer'е: структура, типы, версия схемы,
  диапазон уверенности и отсутствие лишних полей проверяются строго; границы и
  перекрытия — забота backend'а (`locate_annotations`).
- Один ограниченный повтор (repair) с перечислением конкретных ошибок; факт повтора
  виден в разборе (`repaired`).
- Ответ применяется целиком или не применяется: частичный разбор хранится для review,
  но текст не меняется.

## 4. Хранение, кеш, инвалидация

Таблица `llm_analyses` (миграция 7): одна запись на реплику проекта, ключ —
`(project_id, replica_index)` (индекс стабилен, id реплики меняется при повторном
разборе). Хранится JSON разбора, статус и **входные хеши**.

Разбор действителен, только если совпали: `source_text_hash`, `context_hash`,
`dictionary_hash`, `model_digest`, `prompt_version`, `schema_version`. Любое
расхождение → `STALE`; `FAILED` и повреждённый JSON из кеша не отдаются. Правка
соседней реплики делает устаревшим разбор соседа автоматически (в его контексте
изменился текст), а явная инвалидация (`store.invalidate_analysis`, смена правила
словаря) метит реплику и по два соседа с каждой стороны — история при этом
сохраняется.

## 5. Review и словари

Предложение LLM — кандидат с `source=llm`, типом, чтением, уверенностью и сверкой с
детерминированным слоем (`agreement`: `agree` / `conflict` / `none`). Решения те же,
что у детерминированных кандидатов, и идут через существующую ручку
`POST /api/projects/{id}/pronunciation/review`:

| Действие | Что происходит |
|---|---|
| принять в проект | включённое правило project dictionary |
| принять глобально | включённое правило global dictionary (явный `scope: global`) |
| изменить | правило с правкой пользователя |
| оставить как есть / отклонить | выключенное правило — память о решении |

Согласие с детерминированным слоем снимает необходимость решения
(`resolved_by: agreement`), отклонённое слово больше не спрашивается
(`resolved_by: rejected`), но остаётся видимым. Конфликт (словарь даёт другое чтение)
требует решения человека. Сверка чтений учитывает, что `зам+ок` и `з+амок`
отличаются позицией знака.

## 6. Тяжёлые ресурсы

`HeavyScheduler` — единая точка: политика памяти (NORMAL/WARNING/CRITICAL/HARD STOP,
резерв 3.5–4 GB, приоритет macOS pressure) плюс один тяжёлый слот на LLM/TTS/Whisper.
Очередь синтеза занимает `HEAVY_TTS` и **ждёт** слот, если идёт анализ; распознавание
референса — `HEAVY_WHISPER`; анализ — `HEAVY_LLM`. Лёгкие действия (review, API,
SQLite, детерминированная подготовка) слот не занимают.

Проход анализа проверяет память **перед каждой репликой** и при HARD STOP
останавливается с причиной, сохраняя уже полученные разборы и выгружая модель. После
прохода модель выгружается (`unload_after`): память возвращается рендеру, а не висит
«на всякий случай».

## 7. Интерфейс

В обеих вкладках озвучки — блок «Лингвистический анализ»: состояние (`выкл / ожидает
/ анализ / готов / требует проверки / ошибка / устарел`), модель, счётчики
(предложений, на проверку, конфликтов) и список предложений с решениями. Ручки:
`GET /api/llm/status`, `GET /api/llm/models`, `GET|POST
/api/projects/{id}/linguistic-analysis`.

## 8. Ограничения и известные особенности

- Модель ошибается в границах и в чтениях; backend это ловит и превращает в
  предложения, но качество остаётся модельным: `issue_f1` выбранной модели — 0.19 на
  gold-корпусе (см. benchmark).
- Массовый review на большом проекте дорог: каждое решение пересчитывает затронутые
  реплики вместе с LLM-разбором (правило продакшена «пересчитать сразу»). Для
  десятков слов подряд это минуты; оптимизация — отдельная задача.
- Класс реплики от модели — подсказка, а не решение: стратегию выбирает Short
  Utterance Strategy.
- При жёлтом давлении macOS анализ не запускается даже при низком проценте: это
  осознанное поведение, а не ошибка настройки.
