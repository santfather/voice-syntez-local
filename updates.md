# Инструкция для ИИ-агента: автопополнение словаря, буква Ё, очистка кеша

## Перед началом — что уже есть, не дублировать

Прочитан текущий `README.md` проекта VOICE_SYNTEZ. В нём уже реализовано то, что легко принять
за отсутствующее и начать строить заново — **не делать этого**:

- **Словарь произношения** (вкладка `04`) — глобальный, в `data/voice_syntez.db`
  (таблица `pronunciation_entries`), CRUD через `/api/pronunciation`, применяется до RUAccent,
  умеет и обычные замены («OpenAI → оупен эй-ай»), и ударения («звонит → звон+ит»). Логика — в
  `backend/pronunciation.py`.
- **Общий пайплайн нормализации текста** — `backend/text_normalization/pipeline.py`,
  порядок шагов: технические строки → числа/даты/время/деньги → словарь произношения → (только
  для F5) RUAccent.
- **Preview «Что услышит модель»** — `audio_pipeline.preview_text(...)`, показывает текст по
  стадиям `original → normalized → dictionary → accentized → final`; синтез и preview зовут одну
  и ту же функцию, поэтому показанное не расходится с реальным результатом.

Все три задачи ниже — это **расширение** перечисленного, а не новая параллельная система.

## Задача 1 — Автоматические предложения в словарь произношения из «Сплошного текста»

Сейчас словарь пополняется только вручную, через вкладку `04`. Нужно: при обработке текста в
режиме «Сплошной текст» приложение само находит слова-кандидаты (сложные, редкие, омографы) и
предлагает добавить их в уже существующий словарь — а не спрашивает каждый раз заново на
похожем тексте.

### 1.1 Источники кандидатов

- Слова, на которые RUAccent (модель омографов, `TTS_OMOGRAPH_MODEL_SIZE`) даёт низкую
  уверенность предсказания, если библиотека отдаёт confidence per-word
- Слова из курируемого списка известных омографов по ударению (за+мок/замо+к и т.п.), которых
  ещё нет ни в одном правиле `pronunciation_entries`
- Слова вне частотного списка русского языка (редкие/сложные) — эвристический fallback, если
  прямой confidence от RUAccent недоступен

Не предлагать слово, если оно уже покрыто существующим правилом словаря (`whole_word`-проверка
по тем же правилам сопоставления, что уже использует `pronunciation.py`) — иначе одно и то же
слово будет предлагаться на каждом новом тексте.

### 1.2 Поток подтверждения

После обработки текста в режиме «Сплошной текст» (используя уже существующий
`preview_text`/этап нормализации) — отдельный экран/панель «Предложения для словаря»:
список найденных кандидатов, у каждого — слово и предлагаемый вариант (ударение или, для
Задачи 2 ниже, буква ё). Пользователь подтверждает, редактирует или отклоняет по одному.

При подтверждении — вызов уже существующего `POST /api/pronunciation` с готовой парой
«источник → замена» (`молок+о`, `все → всё`), **без нового хранилища**: подтверждённое
предложение — это просто ещё одна запись в `pronunciation_entries`, которая дальше работает
для всех будущих текстов и диалогов автоматически, как и любое другое ручное правило.

**Критерий готовности:** текст с намеренно неоднозначным словом при первом прогоне через
«Сплошной текст» показывает это слово в панели предложений; после подтверждения оно появляется
в списке словаря на вкладке `04` как обычное правило; повторный прогон **другого** текста с тем
же словом больше не предлагает его — оно уже разрешено правилом.

## Задача 2 — Восстановление буквы Ё

### Почему это не решается ударением само по себе

Даже когда RUAccent верно определяет, что гласная ударная, это не превращает «е» в «ё» — для
модели это разные символы на входе. Если в тексте физически стоит «е» (стандартная практика
русской типографики), никакая метка ударения не заменит саму букву — модель произнесёт «е»,
даже стоящую под ударением.

### 2.1 Новый детерминированный шаг нормализации

Добавить в `backend/text_normalization/` новый модуль (например, `yo_restoration.py`) —
восстановление «ё» по словарю **гарантированных** случаев: слов, где «е» на месте «ё» — это
исключительно опечатка типографской традиции, а не другое слово (таких слов подавляющее
большинство, порядка тысяч; открытые словари такого рода уже существуют — например, у проектов
вида `YoRZ`/`Wikipedia-Yofication`, можно взять их списки за основу, не собирать с нуля).

Встроить этот шаг в `pipeline.py` **до** словаря произношения — чтобы явное ручное правило
пользователя (если он всё же захочет переопределить конкретный случай) всегда оставалось
приоритетнее автоматики, как это уже работает для остальных шагов.

Добавить стадию «Восстановление ё» в список стадий `preview_text` — по тому же принципу, что и
остальные шаги: пользователь должен видеть эту замену в панели «Что услышит модель», а не
только слышать её постфактум в готовом аудио.

### 2.2 Омографы е/ё — через ту же систему, что и Задача 1, без нового механизма

Настоящие неоднозначные случаи (все/всё, небо/нёбо, узнаем/узнаём) — **не гарантированные**
замены, их нельзя разрешать автоматически. Технически это тот же тип задачи, что и в Задаче 1:
слово с неопределённостью, требующее разового подтверждения пользователем. Никакого нового поля
или таблицы не нужно — существующий словарь произношения уже умеет пары вида «источник →
замена» буквально: `все → всё` — валидное правило `pronunciation_entries`, ничем не отличающееся
от `звонит → звон+ит`. Добавить список известных е/ё-омографов как ещё один источник кандидатов
в Задаче 1.1, и поток подтверждения из 1.2 отработает без изменений.

**Критерий готовности:** текст со словом с гарантированной «ё» (например, «ежик», если написано
как «ежик») озвучивается с «ё» без участия пользователя; текст со словом-омографом («все» в
контексте, где нужно «всё») предлагается на подтверждение через тот же экран, что и обычные
кандидаты по ударению из Задачи 1, и после подтверждения работает как обычное правило словаря
на любых будущих текстах.

## Задача 3 — Очистка кеша приложения

### ⚠️ Явный конфликт с уже задокументированным решением — не обходить молча

В разделе README «Что не входит в проект» прямо сказано: *«Управление кешем `huggingface_hub`
(Whisper, вокодер Vocos): менеджер их показывает, но не скачивает и не удаляет — это делают сами
библиотеки»*. Это было осознанное архитектурное решение, а не забытая фича. Прежде чем
реализовывать очистку кеша — явно решить границу, а не расширять её по умолчанию заодно с
остальным:

- **По умолчанию — не трогать `models/` и кеш `huggingface_hub`.** Это дорогой в
  восстановлении кеш (гигабайты, требует интернета на повторную загрузку); удаление весов уже
  доступно осознанно, через вкладку `05` «Модели» с явным подтверждением, менять это поведение
  не нужно.
- **Область новой функции — то, что действительно накапливается бесконтрольно:**
  - `output/` сверх текущей TTL-очистки (`TTS_OUTPUT_TTL_HOURS`) — ручная кнопка «очистить
    сейчас», не дожидаясь срока
  - `output/benchmarks/` — README прямо отмечает, что эти файлы **не** попадают под
    TTL-очистку вообще; это первый кандидат на ручную очистку
  - временные/промежуточные файлы пайплайна (если такие остаются на диске сверх сборки
    финального файла)

### 3.1 Реализация

Новый эндпоинт, аналогичный по духу уже существующим `/api/models/*`:

```python
# main.py
@app.post("/api/cache/clear")
async def clear_cache(targets: list[Literal["output", "benchmarks", "temp_files"]]):
    freed = {}
    if "output" in targets:
        freed["output"] = _clear_dir(OUTPUT_DIR, keep_recent=False)
    if "benchmarks" in targets:
        freed["benchmarks"] = _clear_dir(OUTPUT_DIR / "benchmarks")
    if "temp_files" in targets:
        freed["temp_files"] = _clear_temp_files()
    return {"freed_mb": freed}
```

На вкладке `05` «Модели» (она уже отвечает за подобное обслуживание весов) — соседняя секция
«Очистка кеша приложения» с чекбоксами по трём категориям выше и суммой освобождённого места
после нажатия. **Не давать в этой же форме опцию удаления весов моделей или кеша HF** — для
этого уже есть отдельный, осознанно устроенный поток в этой же вкладке.

**Критерий готовности:** нажатие «Очистить» с выбранными `output`+`benchmarks`+`temp_files`
освобождает место на диске и не трогает ни файл `data/voice_syntez.db` (в т.ч. словарь
произношения), ни `voices/`, ни `models/`, ни кеш `huggingface_hub` — это должно быть верно
даже при выборе всех трёх чекбоксов сразу, ни один из них физически не может задеть эти пути.
