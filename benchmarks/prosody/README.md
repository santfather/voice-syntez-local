# Reference Prosody Transfer Benchmark — корпус (v1)

Корпус реплик для benchmark'а переноса просодии (UPDATE 3 §30–§33): проверяет,
меняет ли смена `ReferenceProfile` интонацию target, **не ухудшая текст и голос**.

## Происхождение

Реплики написаны вручную по примерам §31; ни одна модель корпус не порождала.
Примеры из спецификации взяты дословно, остальные подобраны так, чтобы категория
читалась по тексту без контекста — иначе провал «интонация не та» нельзя было бы
отличить от «эта реплика и не должна звучать так».

## Состав (v1, 36 реплик)

| Категория | Реплик | Что проверяет |
|---|---|---|
| `neutral` | 4 | база: профиль не должен ломать ровное чтение |
| `question` | 4 | вопросительная интонация |
| `delight` | 4 | радость, восторг |
| `sad_sympathetic` | 4 | огорчение, сочувствие |
| `irony` | 4 | ирония (в тексте не выражена) |
| `strict` | 4 | строгость, приказ |
| `enumeration` | 4 | перечисление |
| `excited` | 4 | взволнованность, спешка |
| `ambiguous` | 4 | интонация решается контекстом |

Реплик с пометкой `ambiguous: true` — 4. У них `expected_intent` описывает
намерение, которое подразумевает контекст из поля `note`, а не однозначное
прочтение текста: для них `prosody_match` в listening review оценивается с учётом
этой подсказки (§34).

## Файлы

| Файл | Что внутри |
|---|---|
| `corpus.v1.jsonl` | сами реплики, одна строка — один кейс |
| `schema.json` | схема кейса: по ней читается формат и сверяются словари |

Поля кейса: `id`, `category`, `text`, `expected_intent`, `ambiguous`, `note`.
`expected_intent` — ожидаемое намерение (`prosody_effective`) из словаря эмоций:
корпус не вводит свой словарь, а ссылается на боевой (`backend/emotions.py`).

## Проверка

```bash
./venv/bin/python tools/prosody_benchmark.py --check          # корпус без моделей
./venv/bin/python tools/prosody_benchmark.py --plan --voice <id>   # матрица без моделей
./venv/bin/python -m pytest tests/test_prosody_benchmark.py -q
```

`--check` дополнительно печатает число реплик по категориям; корпус считается
неполным, если реплик меньше 30 (§31), категория пуста или `expected_intent` вышел
за словарь эмоций.

## Что проверяет человек перед полным прогоном

1. `ambiguous: true` — согласиться, что контекста в `note` достаточно для
   единственного прочтения, или перенести реплику в однозначную категорию.
2. Однозначные категории — нет ли реплик, которые сами по себе звучат нейтрально:
   такая реплика наказывает профиль за правильную интонацию.
3. `expected_intent` у реплик «не своей» категории (например, вопрос в
   `enumeration`) — корпус не обязан быть монотонным, но расхождение должно быть
   осознанным.

## Подтверждение профилей (§35)

Прогон отвечает на вопрос, какие профили дают устойчивый перенос, а какие портят
дикцию. Ответ — не приговор, а **разрешение**: пока профиль не подтверждён, он не
попадает в автоматическую маршрутизацию (флаг `enabled_for_auto = false`), но
остаётся доступным вручную — его можно выбирать у реплики и слушать.

Что делает человек:

1. Прогоняет матрицу на нужном движке и слушает записи (Whisper прослушивание не
   заменяет, §34) — в `review.md` рядом с каждой ячейкой есть форма отзыва.
2. Смотрит `report.md`: `Δ` метрик к NEUTRAL по профилям и категориям.
3. Подтверждает только те профили, чья польза слышна и не ломает текст и голос:
   в карточке голоса — галочка «авто» (PATCH `/api/voices/{voice_id}/references/{profile_id}`
   с `{"enabled_for_auto": true}`).
4. Профили, которые не подтвердились, оставляет без галочки — они продолжат
   работать при ручном выборе, но автоматика их больше не возьмёт.

Подтверждение применяется к голосу **и движку**: профиль, проверенный на F5,
XTTS-проверкой не считается — за это отвечает `engine_compatibility` (§28).
