## P0 — критично

### P0-1. `DELETE /api/models/f5` удаляет **весь** каталог `models/`

Где: `backend/model_manager.py:181` (`local_dir=config.MODELS_DIR` у F5), `:249-261`
(`_inside`), `:264-281` (`validate_model_path`), `:777-784` (`delete`).

Что происходит. У XTTS и banana `local_dir` — подкаталоги внутри `models/`, а у F5 —
сам `MODELS_DIR`:

```python
"local_dir": config.MODELS_DIR,          # F5
```

Граница проверяется функцией `_inside`, которая считает путь «внутри» и тогда, когда он
**равен** корню:

```python
return resolved == resolved_root or resolved_root in resolved.parents
```

Поэтому `validate_model_path` для F5 возвращает `models/` как допустимый путь, а `delete`
делает `shutil.rmtree(path)` — то есть сносит весь каталог моделей вместе с XTTS, banana и
всем, что там лежит. Комментарий в `delete` («удаляется ровно каталог модели… за его
пределами ничего не пострадает») для F5 просто неверен.

Почему это достижимо у пользователя: кнопка «Удалить» рисуется во фронтенде для всех
локальных моделей (`frontend/app.js:461-463`, `kind === 'local'`), а роут
`DELETE /api/models/{id}` задокументирован в README как «удалить файлы модели».

Оценка: единственная операция в приложении, которая безвозвратно уничтожает многогигабайтные
веса, к которым не относятся действия пользователя. Восстановление — повторная загрузка
моделей.

Как чинить: у F5 должен быть **подкаталог** (`models/f5` или `models/f5-tts`), либо
`validate_model_path` обязан отклонять путь, равный корню (`resolved_root in resolved.parents`
без равенства), а `delete` — дополнительно отказываться удалять `MODELS_DIR`. Первое
предпочтительнее: оно убирает саму возможность, а не сужает окно. Тест
`tests/test_model_manager.py` («удаление только своего каталога») сейчас проверяет чужой
каталог, но не корень — добавить кейс `model_id == 'f5'` → `models/` цел.

## P1 — серьёзно

### P1-1. Watchdog-ветка пересинтеза реплики оставляет задачу «занятой» навсегда

Где: `backend/job_queue.py:1621-1636` (`_project_take`), контраст — `:1718-1719`
(`_benchmark`), `:985-988` (`_render`), `:582-595` (`is_busy`).

При прерывании пересинтеза из-за нехватки памяти ветка `ABORT_WATCHDOG` выставляет
`regen_error`, `message` и вызывает `_drop_variants`, но **не** переводит задачу в
`JobStatus.ERROR` и **не** сбрасывает статус реплики, выставленный в `REPLICA_STATUS_RENDERING`
(`:1556`). В соседних ветках это делается: `_benchmark` явно ставит `job.status = JobStatus.ERROR`,
`_render` сбрасывает статус реплики.

Последствия:
- задача навсегда остаётся `PROCESSING` → `is_busy()` всегда `True`;
- `POST /api/engines/{id}/unload` навсегда отвечает 409;
- `POST /api/reset` со `scope=full` навсегда отвечает 409 (см. README, «Почему полный сброс
  отказывает при занятой очереди»);
- `_prune` (`:710-717`) не вытесняет зависшую задачу.

Как чинить: в watchdog-ветке выставить `job.status = JobStatus.ERROR`, `job.error =
job.regen_error` и сбросить статус реплики так же, как это делает `_render`.

### P1-2. `add_voice_reference` блокирует event loop

Где: `backend/main.py:1165-1177`.

`async def` читает файл и **синхронно** вызывает `get_store().add_reference(...)`, внутри
которого — распознавание референса Whisper (`subprocess.run`). Пока идёт распознавание
(секунды-десятки секунд), uvicorn не обслуживает другие запросы: `/api/status`, прогресс,
отмена, отдача аудио — всё встаёт.

Контраст «сделано правильно» в том же файле: `create_voice` и `/analyze` уходят в
`asyncio.to_thread`.

Как чинить: обернуть вызов в `await asyncio.to_thread(...)`.

### P1-3. `render_text` синхронно зовёт LLM в async-роуте

Где: `backend/main.py:1831` → `_analyze_text_chunks` → LLM.

`llm_report = _analyze_text_chunks(text, chunks)` выполняется прямо в обработчике
`POST /api/render-text`. Лингвистический анализ сплошного текста — тяжёлая операция
(секунды, при холодной модели — минуты). Event loop заморожен ровно на это время.

Как чинить: `await asyncio.to_thread(_analyze_text_chunks, text, chunks)`.

### P1-4. Неатомарная запись `voices.json` → потеря всех голосов

Где: `backend/voices_store.py:292-296`, чтение — `:255-262`.

`_write` вызывает `write_text` напрямую: прерывание (выключение питания, SIGKILL, ошибка
диска) между truncate и полной записью оставляет обрезанный JSON. `_read` на битом JSON
логирует ошибку и возвращает `[]` — то есть **все** голоса исчезают из UI, а следующая
запись затрёт файл насовсем.

Для сравнения: аудио в проекте пишется атомарно (см. `test_recovery.py`), а `voices.json` —
нет.

Как чинить: писать во временный файл рядом, `os.replace` на место, `fsync` при необходимости.
Плюс — при битом `voices.json` не затирать его, а сохранять копию `voices.json.corrupt`.

### P1-5. `audio_file` из JSON не валидируется → удаление вне `voices/`

Где: `backend/voices_store.py:125-126,188-189` (чтение), `:558,598` (`unlink`).

Поле `audio_file` берётся из `voices.json` как есть и подставляется в `VOICES_DIR / audio_file`.
Файл, отредактированный вручную или восстановленный из чужого архива, с `audio_file:
"../../../Users/x/Documents/important.wav"` приведёт к `unlink` за пределами каталога голосов.

Как чинить: при чтении отклонять значения с `..`, абсолютные пути и всё, что после
`resolve()` не лежит внутри `VOICES_DIR` (та же проверка `_inside`, что в `model_manager`,
но без пропуска корня).

### P1-6. Миграции неатомарны

Где: `backend/db/migrations.py:288-303`.

`apply_migrations` делает `executescript(script)`, затем отдельно `DELETE FROM schema_version`
и `INSERT`. При обрыве между ними схема уже изменена, а версия — старая, либо версия
записана дважды. `executescript` дополнительно сам коммитит перед выполнением, что ломает
транзакционность внешнего контекста.

Как чинить: обернуть каждую миграцию в `BEGIN IMMEDIATE … COMMIT` (или выполнять через
`executescript("BEGIN; …; COMMIT;")` с `UPDATE schema_version`) и обновлять версию тем же
`UPDATE`-запросом внутри одной транзакции.

### P1-7. `ALTER TABLE ADD COLUMN` без `IF NOT EXISTS`

Где: `backend/db/migrations.py:251-256` (миграция 8), `:264-273` (миграция 9), а также
ранние `_MIGRATION_*`.

SQLite не поддерживает `ADD COLUMN IF NOT EXISTS`. Если база по любой причине получила
колонки, но не записала версию (см. P1-6), повторный прогон падает с
`duplicate column name` — сервис не стартует, и починить это из UI нельзя.

Как чинить: перед `ALTER` проверять наличие колонки через `PRAGMA table_info(...)` и
пропускать уже существующие (либо разбирать текст миграции на отдельные `ALTER` и
обрабатывать `duplicate column name` как no-op).

### P1-8. `llm_analyses` без `REFERENCES` → разборы остаются навсегда

Где: `backend/db/migrations.py:219-245` (миграция 7).

Таблица `llm_analyses` хранит `project_id`/`replica_id` **без** внешних ключей и каскада, в
отличие от `replicas`/`takes`/`speakers`. Удаление проекта не удаляет его разборы: база
растёт неограниченно, а мёртвые строки попадают в выборки.

Косвенно: `llm_analyses.delete_for_replicas` не вызывается нигде в коде (мёртвый API).

Как чинить: пересоздать таблицу с `REFERENCES ... ON DELETE CASCADE` (SQLite требует
table-rebuild) и вызывать очистку при удалении реплик.

### P1-9. Мусор в валидном JSON роняет весь проход анализа

Где: `backend/llm/schemas.py:244-256,436`, `backend/llm/analyzer.py:584-586`.

`Annotation.from_dict` приводит типы без защиты:

```python
int(raw.get("span_start", -1))
float(raw.get("confidence") or 0.0)
```

Ответ модели — валидный JSON, но `{"span_start": "abc"}` даёт `ValueError`,
`{"confidence": {}}` даёт `TypeError`. Ловится только `OllamaError`, поэтому исключение
всплывает до самого верха и роняет целый проход анализа, вместо того чтобы пометить одну
аннотацию недействительной.

Как чинить: обернуть разбор аннотации в `try/except (TypeError, ValueError)` и отбрасывать
запись с причиной (как уже сделано для неверного `source`).

### P1-10. Игнорируется `must_abort_running`

Где: `backend/llm/integration.py:474-491`, `backend/llm/memory_policy.py:257-259`.

Политика памяти различает «новую тяжёлую задачу не запускать» и «идущую нужно прервать»
(`must_abort_running = level == HARD_STOP or available_gb < reserve_min_gb`), но
интеграция проверяет только `abort.memory_level == memory.LEVEL_HARD_STOP`. В сценарии
«памяти мало, доступный объём ниже жёсткого резерва, но порог HARD STOP не достигнут»
проход продолжается.

Как чинить: проверять `abort.must_abort_running` (или `abort.blocked`), а не только
уровень.

### P1-11. TOCTOU в `HeavyGate.try_acquire`; `HeavyResourceBusy` в воркере не ловится

Где: `backend/llm/memory_policy.py:414-424`, `backend/job_queue.py:749-753`.

`try_acquire` проверяет `busy()` **вне** лока, после чего берёт лок и захватывает слот —
два потока могут оба решить, что слот свободен. Практический эффект сглаживает
`external_busy`, но инвариант «один тяжёлый инференс» не гарантирован конструкцией.

Рядом: в `job_queue.py:749-753` синтез в воркере может получить `HeavyResourceBusy` и не
поймать его — воркер завершается, хотя это не падение модели.

Как чинить: перенести проверку внутрь лока (или использовать сам лок как проверку);
`HeavyResourceBusy` в очереди обрабатывать как ожидание/повтор, а не как смерть воркера.

## Прогон тестов

Полный прогон: `venv/bin/python -m pytest -p no:warnings` (macOS, Python 3.11,
`ORT_DISABLE_TELEMETRY=1 PYTHONHASHSEED=0`).

Результат: **4 failed, 1110 passed** из 1114, время — 22:33.

| Тест | Причина |
|---|---|
| `tests/test_llm_analyzer.py::test_analyzer_disabled_by_default` | Ожидает `enabled is False`, получает `True`: `settings_from_env()` накладывает **сохранённые** настройки из рабочего `data/llm_settings.json` (`{"enabled": true}`), а `workspace` этот путь не подменяет (P2-19) |
| `tests/test_llm_analyzer.py::test_llm_status_and_models_endpoints` | Та же причина: `GET /api/llm/status` отдаёт `enabled: true` из того же файла |
| `tests/test_dialogue_continuous_parity.py::test_same_text_continuous_vs_dialogue_normalized_text` | Плавающий: при включённом анализаторе и живом Ollama LLM-кандидаты в разборе не снимаются хелпером `analyze_project`, и проект остаётся `needs_review` вместо `ready` |
| `tests/test_dialogue_continuous_parity.py::test_preview_final_equals_render_input` | Та же причина, что выше |

Проверка причины:

- `pytest tests/test_dialogue_continuous_parity.py` — **9 passed** (в изоляции);
- `pytest tests/test_llm_analyzer.py tests/test_dialogue_continuous_parity.py` — падают только два
  теста анализатора, парность проходит;
- `pytest tests/test_app_reset.py tests/test_dialogue_continuous_parity.py` — воспроизводит
  падение парности, но нестабильно (повторные запуски то падают, то проходят);
- `TTS_LLM_SETTINGS_PATH=/tmp/llm_off.json pytest tests/test_app_reset.py tests/test_dialogue_continuous_parity.py`
  (анализатор принудительно выключен) — **17 passed**;
- `TTS_LLM_SETTINGS_PATH=/tmp/llm_off.json pytest tests/test_llm_analyzer.py …` — два «настроечных»
  падения исчезают.

Вывод: это **не регрессия** функционала сброса, а дефект изоляции тестов (P2-19):
набор зависит от рабочего `data/llm_settings.json` и от того, отвечает ли Ollama на
`127.0.0.1:11434`. На «чистой» машине без включённого анализатора те же тесты проходят.

Рекомендация (тестовая, не продуктовая): в фикстуру `workspace` добавить подмену
`config.DATA_DIR` на `tmp_path` (или `monkeypatch.setenv` для

анализатора, как и голоса с базой, не протекали из рабочего каталога и не зависели от
поднятой Ollama.

Побочно: заявленные в README «~1.7 минуты» на весь набор не подтверждаются — локальный
прогон занял 22:33. Причина не исследована отдельно; кандидат — тест полного `--dry-run`

## Итоги

**Сильные стороны.** Архитектура изоляции синтеза в отдельном процессе, таксономия ошибок
воркера, канонический проход подготовки с запретом рендера вне `READY`, детерминированный
пайплайн текста с preview, воспроизводимость LLM-прогонов (паспорт, digest модели, версия
prompt'а и схемы), границы очистки кеша и сброса вкладки, объём и дисциплина тестов
(58 файлов, ~22,7 тыс. строк).

**Главные риски** — в порядке приоритета исправления:

1. **P0-1** — удаление F5 сносит `models/`. Единственная необратимая потеря данных;
   чинится малой правкой.
2. **P1-1** — зависшая задача привносит «вечную занятость» и блокирует `unload` и полный
   сброс; пользователь не может восстановиться из UI.
3. **P1-4, P1-5** — целостность и безопасность `voices.json`: потеря всех голосов и
   `unlink` вне каталога голосов.
4. **P1-6, P1-7, P1-8** — атомарность и идемпотентность миграций: либо отказ старта, либо
   неограниченный рост базы.
5. **P1-2, P1-3** — блокировка event loop на «тяжёлых» async-роутах: сервис выглядит
   зависшим на время операции.
6. **P1-9, P1-10, P1-11** — устойчивость LLM-прохода к мусорному ответу и корректность
   политики памяти.

**Рекомендуемый порядок работ.** Сначала P0-1 и P1-1 (потеря данных и «кирпич» из UI),
затем целостность данных (P1-4…P1-8), затем устойчивость LLM-слоя (P1-9…P1-11), затем
P2 по областям. P3 — косметика, её разумно брать попутно с правками рядом.

**Чего аудит не проверял.** Нагрузочное поведение на реальных моделях (только чтение кода
и тестов), корректность самого лингвистического качества моделей (это предмет benchmark'а,
а не аудита), а также полный прогон GUI-сценариев в браузере — фронтенд проверялся чтением
кода и сверкой с API.
